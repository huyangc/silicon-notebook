# Knowhow 新表导入方向设计

**日期：** 2026-07-20  
**状态：** 已确认，待实现  
**范围：** 仅 Knowhow“导入并新建表”流程

## 1. 目标

Knowhow 整表导入目前只接受“属性按列”的源表：第一行是属性名，后续每一行是一条记录。对于“属性按行”的源表，用户必须先在 Excel 中手工转置。

本功能在导入向导中让用户明确选择源表方向：

- `columns`：属性按列。第一行是属性名，每一行是一条记录。
- `rows`：属性按行。第一列是属性名，每一列是一条记录。

后端在解析文件后把两种输入统一规范化为内部现有的“属性按列”网格，再复用后续校验、预览、建表、落库和投影流程。用户不再需要在外部工具中手工转置。

## 2. 范围边界

本次只修改“导入并新建 Knowhow 表”：

- `POST /api/notebooks/{notebook_id}/knowhow/import/preview`
- `POST /api/notebooks/{notebook_id}/knowhow/import`
- 对应的前端 `KnowhowImportWizard`

以下内容不在本次范围：

- 向已有 Knowhow 表追加导入；
- Excel 模板下载与往返；
- 建空表向导；
- 自动猜测源表方向；
- 数据库表结构或持久化导入方向。

追加导入继续只接受与目标表相同的“属性按列”表头结构。

## 3. 源表语义

### 3.1 属性按列

现有格式保持不变：

| 属性 A | 属性 B | 属性 C |
|---|---|---|
| 记录 1 的 A | 记录 1 的 B | 记录 1 的 C |
| 记录 2 的 A | 记录 2 的 B | 记录 2 的 C |

### 3.2 属性按行

用户确认的输入约定如下：

| 属性 | 记录 A | 记录 B |
|---|---|---|
| 现象 | A 现象 | B 现象 |
| 根因 | A 根因 | B 根因 |

规范化后的内部网格为：

| 属性 | 现象 | 根因 |
|---|---|---|
| 记录 A | A 现象 | A 根因 |
| 记录 B | B 现象 | B 根因 |

转换规则是完整矩阵转置：

- 原始第一列成为规范化网格的表头；
- 原始第一行成为规范化网格的第一列；
- 原始左上角单元格同时是规范化网格第一列的列名；
- 原始第一行除左上角外的每个单元格标识一条记录；
- 原始第一列除左上角外的每个单元格标识一个属性。

## 4. 后端设计

### 4.1 请求契约

两个整表导入接口都增加 multipart 表单字段：

```text
orientation = columns | rows
```

`orientation` 默认值为 `columns`。不发送该字段的旧客户端与现有测试继续按属性列解析。

预览和正式导入必须接收并使用同一个方向参数。正式导入仍重新读取并解析原始文件，不信任客户端回传的预览矩阵。

非法方向值返回 HTTP 400 和中文错误：

```text
非法的属性排列方式
```

### 4.2 解析与规范化边界

`grid_parser.py` 继续负责 xlsx、xlsm、csv、md 和 markdown 的原始单元格提取。方向规范化发生在原始矩阵提取之后、现有 `_build_grid` 校验之前。

规范化函数只承担一个职责：把原始二维字符串矩阵转换成内部“属性按列”矩阵。

- `columns`：原样返回矩阵。
- `rows`：
  1. 以原始矩阵的最大行宽为目标宽度；
  2. 每个短行在右侧补空字符串，形成矩形；
  3. 对矩形做完整转置；
  4. 把转置结果交给现有 `_build_grid`。

在 `_build_grid` 前转置是必要条件。若先把原表解释成 `ParsedGrid`，原始第一列会被错误地当作数据而不是最终表头，且现有表头校验可能在转换前提前拒绝合法的属性行表。

规范化之后继续复用现有行为：

- 空表、表头、重复列名和无数据行校验；
- 空白数据行过滤；
- 内容类型猜测；
- 列定义数量校验；
- 行标题列前向填充；
- 建表、逐行插入和 mutation sequence 更新；
- 后台知识投影调度。

### 4.3 行标题建议

属性按列时继续使用现有 `guess_kinds()` 的列名关键词建议，不增加首列兜底。

属性按行时，规范化后的第一列保存原始记录名称，因此预览响应强制返回：

```json
{
  "anchor_suggestion": 0
}
```

这只是默认建议。前端预览页仍允许用户改选其他列或选择“不设置”。

### 4.4 错误提示

现有 `_looks_transposed()` 会识别疑似“第一列是字段名”的源表，并要求用户去 Excel 手工转置。保留形状识别，但把提示改为产品内可执行动作：

```text
这张表看起来是属性按行排列，请返回并选择“属性按行”后重新导入。
```

属性按行转置后若出现空属性名、重复属性名或没有记录，走统一网格校验并返回中文 400。后端不静默生成属性名或记录名，也不自动切换用户选择的方向。

## 5. 前端设计

### 5.1 选择步骤

导入向导第一步从“选文件”调整为“选择排列方式与文件”。上传区上方增加单选控件：

- **属性按列**：第一行是属性名，每一行是一条记录。
- **属性按行**：第一列是属性名，每一列是一条记录。

默认选择“属性按列”，保证现有用户路径和旧文件行为不变。方向必须由用户明确选择或接受默认值，不做自动识别后静默切换。

用户返回第一步重新选文件时保留当前方向选择。关闭并重新打开向导后重新使用默认值 `columns`，不做跨会话持久化。

### 5.2 预览与提交

前端调用预览接口时同时提交文件和 `orientation`。第二步只展示后端返回的规范化结果，因此无论源表方向如何，用户看到的都是最终内部“属性按列”形态。

正式提交必须发送同一个 `orientation`，并继续发送：

- 原始文件；
- 表标题；
- 规范化后列序对应的 `columns_json`；
- 用户最终确认的 `anchor_index`。

属性按行时，前端消费后端返回的 `anchor_suggestion=0`，默认选中第一列作为行标题列。用户可以更改或取消。

提交期间维持当前不可关闭规则，防止不可取消的建表请求在后台成功但前端未刷新。

### 5.3 前端模型

前端使用稳定协议值：

```ts
type KnowhowImportOrientation = "columns" | "rows";
```

显示文案只存在于导入 UI 或其专用选项注册表中，不把中文文案作为协议值发送。

`importKnowhowPreview()` 和 `importKnowhow()` 都显式接收方向参数并写入 `FormData`，避免调用方只在预览或只在提交阶段携带方向。

## 6. 数据流

```text
用户选择方向并上传文件
  → 前端发送 file + orientation 到 preview
  → 后端提取原始矩阵
  → 按 orientation 原样保留或转置
  → 统一 _build_grid 校验
  → 返回规范化列、前五行、总行数、类型和行标题建议
  → 用户确认标题、内容类型和行标题列
  → 前端发送原文件 + 同一 orientation + 列定义
  → 后端再次提取并按同一方向规范化
  → 校验列定义与规范化列数一致
  → 复用现有建表、落库和投影流程
```

## 7. 测试策略

### 7.1 后端解析单元测试

覆盖：

- 不传方向或传 `columns` 时保持当前解析结果；
- `rows` 把属性行表正确转为属性列表；
- 不等长原始行右侧补空后转置，不发生数据错位；
- xlsx/xlsm、csv、md/markdown 共享同一规范化行为；
- 非法方向被拒绝；
- 用户误选 `columns` 且形状明显为属性行时，错误提示引导其在产品内改选；
- 转置后重复属性名、空属性名和无记录继续被校验拒绝。

### 7.2 后端 API 集成测试

覆盖：

- 预览接口接收 `orientation=rows`，返回规范化后的列、数据行、总行数和 `anchor_suggestion=0`；
- 正式导入接口接收 `orientation=rows`，落库后的列和行与预览一致；
- 不发送 `orientation` 的旧请求仍按 `columns` 成功；
- 非法方向返回中文 HTTP 400；
- 预览与提交使用相同规范化列数校验。

### 7.3 前端测试

覆盖：

- 方向选项值、说明和默认值；
- 预览请求携带当前方向；
- 正式提交携带同一方向；
- 属性按行预览采用后端第一列行标题建议；
- 返回文件选择步骤后保留方向；
- 现有标题、内容类型和行标题列组装契约不回归。

## 9. 兼容性与迁移

- `orientation` 是请求级解析参数，不写数据库；
- 不新增 schema migration；
- 默认 `columns` 保持旧客户端和旧测试兼容；
- 已导入的 Knowhow 表不受影响；
- 追加导入协议与行为不变。
