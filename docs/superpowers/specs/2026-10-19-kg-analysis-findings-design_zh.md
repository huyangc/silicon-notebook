# 图谱分析「问题清单」— 设计

2026-10-19。**状态：已拍板（2026-10-19），按 §14 的裁决实施。**

本文承接 [2026-07-25 知识图谱质量分析视图设计](./2026-07-25-kg-analysis-view-design.md)（下称「原设计」）。原设计的批 1 与 #488 已经落地，面板能如实回答三件事：这些数字建于哪一代、落后多少、口径是什么。但「先看结论」四张卡里，只有「报告可信度」一张在做判断，其余三张是模板句。本规格把面板主体改成**问题清单**。每条问题指向具体来源或概念组，附证据数字、影响面和建议动作。

**数据来源。** 凡标「本机实测」的，都是在本机 PostgreSQL 开发库 `silicon_notebook_local_pg16_live` 的 `nb-b37185f4ae` 上只读测得。该库有 41,713 个可用可见对象、51,617 条非 rejected 关系、84 个来源。探针脚本 `kg_probe.py`–`kg_probe6.py` 不在仓库里，存在开发者本机的会话记忆目录 `kg-analysis-probe-2026-10-19/` 下（只读，psycopg + igraph）。生产规模取原设计 §二·五：878 万对象、836 万边、4.9 万来源。**本机没有生产规模的 PG 库。** 凡涉及生产耗时或内存的数，都是按已知基数推算，必须在 §14③ 的生产只读演练里实测，不得当成实测引用。

## 一、为什么改：现有统计答不了的问题

| 现象（本机实测） | 现有面板怎么说 | 实际情况 |
|---|---|---|
| 1,217 个主题板块里，1,137 个（93%）恰好是一整个孤立连通块 | 「当前分为 1,217 个主题板块」 | 主连通块占 72.8% 的节点，内部只有约 80 个主题。其余全是孤岛，这个数数的其实是「有多少块互不相连的碎片」 |
| 「与主体板块关联度」最低的来源 | 「最先值得复核的是 X，关联度 0%」 | 「主体」指覆盖 50% 成员的 29 个头部板块。真混入的来源与正常文档并列在 0%（Mamba2 有 92–96% 在主连通块里），排第一的不一定有问题 |
| 「与非重复来源共享的概念 < 5%」 | 无 | 筛出 12 个来源。抽查 10 个，10 个都是标题与内容不符的错文件，比如 LMCache 的文件里装的是量子光学，Qwen3 的文件里装的是 SEIR 流行病模型 |
| 两个来源的概念 Jaccard ≥ 0.45 | 无 | 8 对重复导入：`llm_papers_2024_arch__*` 与 `_arch_full__*` 7 对，加 DeepSeek-V2 的两份。J 在 0.48–0.65，下一对只有 0.20 |
| 去掉空格/连字符后同名的 concept | 「收敛率 31%」 | 14 组没合并，例如 RMS Norm / RMSNorm、Ring attention / RingAttention |
| 没有任何关联的对象 | 「自动补连占 X%」 | 1,830 个（4.4%）。本库已经跑过「补上关联」（还留着 4,980 条 `relink:` 关联），再点一次多半什么都不变 |
| 删掉一个与主连通块零连接的孤岛来源 | 板块整体换了一遍 | 主连通块原有 80 个板块，只剩 18 个原样，16.4% 的节点换了板块。原样重跑则逐字相同 |

用户要的不是更多统计，而是四件事：哪几个来源、哪几组概念有问题；证据是什么；该怎么处理；处理完怎么确认。

## 二、目标与非目标

**目标**

1. 面板主体改为问题清单。每条问题包含规则编号、严重度、定位、证据、影响面、建议动作，并且可以「标为正常」。
2. 按谁能处置分档：
   - **A 档**（§四）：用户能处置的，面板给建议，并跳到既有入口。
   - **B 档**（§五）：只有开发能修的，单列「需要开发处理」，**不放按钮**。
3. 闭环：处置 → 更新分析 → 按问题自身主键核验（§六）。
4. 报告已与当前图谱一致时，「更新分析」直接说明「无需更新」，不让用户空跑（§五 S4）。

**非目标**（实测证伪的，数字见 §十一；其余是刻意不做）

- 单一健康分或总分。
- 换 Leiden 当**质量**杠杆。§五 S2 用 Leiden 热启动是为了**稳定性**，动机不同，见那里。
- 用簇成员名的多样性判过度合并，或只用邻居 Jaccard 判漏合并。
- 度分布幂律拟合。
- 由面板自己执行删除或重新解析。执行仍走既有入口、既有确认框、既有权限，后端是权限的唯一判据。
- 原设计批 2–4 里与本规格无关的统计，例如度分布图、增长曲线、快照对比。

## 三、问题清单框架

### 3.1 一条问题的字段

| 字段 | 含义 | 例 |
|---|---|---|
| `rule_id` | 规则编号：A 档 `F1`–`F5`，B 档 `S1`（见 §五） | `F1` |
| `subject` | 定位，形如 `{kind, key, label}`。`kind` 取 `source` / `source_pair` / `concept_group` / `notebook`。`label` 是发布时的标题或名字快照，来源删了之后仍能说出删的是谁 | `{kind:"source", key:"src-…", label:"06_LMCache_mineru.md"}` |
| `severity` | `high` / `medium` / `low`，只用来排序和配色，不累加（§3.3） | `high` |
| `evidence` | 判据实际用到的数字，加最多 5 个样例名 | `{shared_share:0.0, giant_share:0.0, concepts:84, samples:[…]}` |
| `impact` | 受影响的知识对象数，单位是对象，写明 | `{objects: N}` |
| `action` | 建议动作，形如 `{kind, capability}`。只读成员看得到建议，但没有按钮 | `{kind:"delete_source", capability:"sources:write"}` |
| `first_seen_seq` / `built_at_seq` | 首次出现于哪一代、本次建于哪一代。都含 KG 世代与合并世代两条线 | |
| `status`（读侧派生） | `open`；`handled`（已处理，更新后核验）；`dismissed`（标为正常） | |

证据里**只放判据真正用到的数**。「仅供参考」的数字归诊断数据区。

### 3.2 稳定主键

重建之后要能说「上次 N 条已消失、M 条仍在、K 条新增」，所以主键必须在**无关改动下不变**：

| 规则 | 主键 | 理由 |
|---|---|---|
| F1 / F3 | `source_id` | 来源 id 只在删除时消失，而消失本身就是「已处置」 |
| F2 | 两个 `source_id` 按字典序拼接 | 无序对，与发现顺序无关 |
| F4 | 组的归一化名（§4.4 的 squash key） | 不用 canonical id：合并簇的 id 会随最小成员变化。`governance_store.decided_seed_pairs_from` 的 docstring 写明了这一点，合并决定也因此按 seed 名存。合并修好后整组消失，正好就是要的「已消失」 |
| F5 | `notebook`（全库一条） | 「补上关联」是笔记本级动作（§4.5） |
| 任何规则 | **不用**板块 id | 板块 id 每次全量重建都由 `_new_id("cm")` 重铸，划分本身也不稳定（§五 S2） |

规则逻辑或阈值一改，同一主键在新旧两次之间就不可比了。账本 payload 记 `rules_version`。版本不同时，对比区写「规则已更新，本次不与上次比较」，不硬算。

### 3.3 严重度：排序用，不是分数

| 档 | 含义 | 规则 |
|---|---|---|
| 高 | 这份内容不属于本库，却会被检索出来当证据 | F1 |
| 中 | 内容属于本库，但重复或残缺：会扭曲支持度和引用，或者缺了知识 | F2、F3 |
| 低 | 局部结构缺陷，影响有限 | F4、F5 |

同档内先按 `impact.objects` 降序，再按主键升序，保证顺序确定。**不跨规则累加，不出总分**：一个错文件和二十组没合并的同名概念，没有可比的公共单位。

### 3.4 面板布局：四个区

```
┌ 图谱分析 ─────────────────────────────── [更新分析 / 已是最新] ┐
│ 报告建于变更 #26 · 合并 #8 · 与当前一致                            │
│ 上次更新后：N 条已消失 · M 条仍在 · K 条新增                      │
├ 待处理（N）────────────────────────────────────────────────┤
│ ● 高 F1 疑似内容错配：06_LMCache_mineru.md          N 个对象       │
│      84 个概念里与其它来源共享 0 个；不在主体内容里                 │
│      代表概念：…（5 个）                                           │
│      [打开来源核对] [删除来源…]                    [标为正常]      │
│ ● 中 F2 疑似重复导入：…Mamba2_mineru ⇄ …Mamba2_full   J = 0.65    │
├ 需要开发处理（1）───────────────────────────────────────────┤
│   14 组只差空格/连字符的概念没有合并（例：RMS Norm / RMSNorm）      │
│   这是合并规则的缺陷，修好后会自动合并，不需要逐条处理。            │
├ 诊断数据（默认折叠）────────────────────────────────────────┤
│   报告口径与新鲜度 · 本报告用到的数据 · 构成 · 收敛率 · 最大合并组   │
│   · 关联形成方式 · 主题结构 · 俯瞰图 · 来源画像表                  │
├ 已通过 ────────────────────────────────────────────────────┤
│   ✓ F3 没发现解析残缺（检查了 84 个来源）                          │
│   – F1 有 N 个来源概念太少，没有判断                               │
│   ↺ 已标为正常：… [撤销]                                           │
└───────────────────────────────────────────────────────────┘
```

- **待处理**：A 档里没有标为正常的问题。只读成员看到同样的内容，但没有动作按钮，也没有「标为正常」。
- **需要开发处理**：B 档里**在本库测得到影响**的项，目前只有 S1（§五）。只写现象、规模和「需要开发修复」，不放按钮——看起来能修、按下去不会有任何变化的按钮一律不许出现。测不到影响的 B 档项（S2 板块稳定性）不上屏，留在开发待办里。这与「只显示真影响结果的问题」是同一条原则。
- **诊断数据**：原设计的全部区块原样保留，默认折叠，逐指标的新鲜度标注不变。「先看结论」四张卡里，「来源复核入口」被 F1 取代，删除；「主题结构信号」改报 S3 的口径。
- **已通过**：每条规则一行。下面三种状态必须分开写，不能都画成绿勾：
  - 检查过、没发现（✓），写明检查了多少个来源或概念；
  - 没法检查（–），写明原因。例如库里只有一个来源，F1、F2 就没有可比的对象；没开 KG 抽取时，所有规则都没有输入；或者某些来源的概念太少。**这一档不算通过。**
  - 已标为正常的问题，可撤销。

### 3.5 一条问题的生命周期

```
          处置（删除 / 重新解析 / 确认合并 / 补上关联）
  open ─────────────────────────────────────────► handled（已处理，更新后核验）
   │ ▲                                                 │ 更新分析
   │ │ 撤销                                            ▼
   ▼ │                                        主键还在 → open（仍在）
 dismissed（标为正常）                        主键消失 → 已消失（进对比区）
```

`handled` 是**读侧派生**的：不靠前端记忆，也不靠面板按钮写标记。用户在别处做的处置，比如在来源列表或知识图谱视图里，同样要能被认出来。下面的判据都是按主键的有界点查，只查当前这一页：

| 规则 | 判为「已处理」的条件 | 读法 |
|---|---|---|
| F1 / F3 | 来源已不存在；或来源的解析/抽取在问题建成之后重跑过、或正在跑 | `sources` 主键点查，加该来源最近一次抽取的时间，≤ 一页。不能用 `sources.updated_at`：改标题之类的动作也会推进它。实现时核对哪个字段只随重新解析变化 |
| F2 | 两个来源中任一已不存在 | `sources` 主键点查。重新解析不解决重复，不算处置 |
| F4 | 待确认合并里这一组已被确认。若是**驳回或暂缓**，当场移进「已通过」写「已判定不是同一个」，下次重建也不再报（§4.4）。驳回不置 `dirty`（只有撤销一次确认才置），所以不能靠「更新后消失」来收尾，否则这条会永远「仍在」 | `concept_merge_candidates` 只有 `(notebook_id, status)` 索引，不是主键点查：在本库候选切片里按这一页的组分批过滤 |
| F5 | 「补上关联」在问题建成之后**改变过图谱**（标记记下的 `kg_mutation_seq` 晚于账本行的 seq）。只跑过、什么都没补上（标记世代 = 当前世代）不是「已处理」，而是 §4.5 的「已经跑过、之后没有新内容」：移出待处理（读侧状态 `relink_spent`，进「已通过」区），不放按钮 | 一行点读 |

「问题建成之后」以这一次预计算**开始扫描**的时刻为准（payload 的 `scanned_at`；旧 payload 没有时退回账本行的 `created_at`）：分钟级预计算窗口里完成的重新解析，产物未必看得到它，按发布时刻判会让它一直显示「待处理」。

**实施对齐（PR-2）**：读侧状态的代号与分区——`open`（待处理）/ `handled`（已处理，更新后核验，仍在待处理区；`handled_reason` = `source_deleted` / `source_processing` / `source_reprocessed` / `merge_confirmed` / `relinked`）/ `dismissed`（标为正常）/ `decided_not_same`（F4，驳回或暂缓）/ `relink_spent`（F5，见上）。`GET .../findings` 的 `zone`：`open` = open + handled，`passed` = decided_not_same + relink_spent，`dismissed` = dismissed。分区只依赖标记、F4 的已存决定与 F5 标记；来源点查只做当前这一页（handled 与 open 同区，来源状态不改变分区）。F1/F3 的「重跑过」看来源的 `chunked_at` 与最近一次抽取的 `created_at`（不看 `updated_at`）；「正在跑」= 来源状态 `queued` / `parsing` / `extracting`，或最近一次抽取 `running`。F4 的已存决定**按种子**匹配：发布时把组内每个 canonical 全部成员（含隐藏来源成员）的去重 v1 种子写进证据（`member_seeds`，每个 canonical 至多 `MAX_MEMBER_SEEDS_PER_CANONICAL=32` 个，超出记 `seeds_truncated`——漏掉的种子只会让组留在「待处理」，是安全方向。这两个键只供读侧判定，`/findings` 的响应投影把它们去掉：种子是归一化后的可读名字，含隐藏成员派生的，越过读者可见边界）；读侧只用这些种子（加上 canonical id 去 `K-` 的那一个）在本库决定切片里按候选两侧的**有效种子**过滤（`merge_candidate_states_for_seeds`，空种子的旧行回退到去 `K-` 的 canonical），不读成员对象，两侧 canonical id 都已漂移的决定也匹配得上；再按证据里存的写法分组（`classes`）判定，与发布时引擎的判定同一个函数。一条相关决定都没有时整步跳过。

报告整体落后于数据时（`dirty`，黄色），问题照常列出，但每条都标「基于变更 #N」，免得读者以为那是此刻的状态。

## 四、A 档：用户处置

**阈值都是初值。** 它们只在本机一个库上标定过，要等 §14③ 的生产只读演练看完分布再定。阈值属于产品口径参数，与 `MAINSTREAM_COVERAGE` 同类：写成具名常量，随 `rules_version` 写进账本 payload，让报告能自证用的是哪一套阈值；不做成部署可调的 Settings。成本上限（§7）是另一类，做成 Settings 字段。

**规则有先后：F2 → F3 → F1。** 目的是避免同一来源被两条规则给出互相矛盾的建议。F2 最先算，因为 F1 的「共享」要排除重复伙伴。F3 先于 F1 判定，因为解析残缺的来源也会表现为「不和别人共享」，而重新解析比删除可逆得多。

### 4.1 F1 疑似内容错配 / 混入来源 → 删除来源

**判据**：`shared_share < 5%`，即该来源的 concept canonical 里，至少还出现在一个**非重复伙伴**来源中的比例。重复伙伴指与它构成 F2 的来源。不排除它们的话，一对错文件会互相「共享」100%，F1 就漏了。

**「不在主连通块」只作证据，不作门槛。** 起初的判据还要求 `giant_share ≤ 5%`（该来源**进了图的对象**里，所在 canonical 落在主连通块的比例——按对象计，与 S3 的「主连通块对象占比」同口径，也与校准用的只读探针同口径；主连通块是 canonical 关联图上最大的连通分量，不是原设计那 29 个覆盖 50% 成员的头部板块，见 §五 S3）。本机实测这道门槛会漏掉 12 个命中里的 4 个：它们的概念几乎不与别的来源共享（0%–4.5%），却有 71%–86% 的节点在主连通块里。原因是只要有极少几个共享节点做桥，整篇文档就会被拉进主连通块——Falcon_H1 靠 1 个共享概念，DistServe 靠 2 个，Zamba3 靠 5 个通用公式。所以 `giant_share` 写进证据，帮读者判断，但不决定命中与否。

**不判的情形**

- concept canonical 少于 10 个（初值；本机命中的来源里最少的有 16 个）：进「已通过」，写「概念太少，没有判断」。
- 可比的来源不足两个：整条规则记为「没法检查」。图里没有任何关联时 F1 照常判（它只看概念共享），只是证据里没有 `giant_share`。
- 孤儿引用（来源已删、对象还在）不是 F1 的对象。它们仍在诊断数据里报 `source_missing`。

**证据**：`shared_share`、`giant_share`、concept 数，以及 5 个代表概念名。对象数是影响面，不进证据；图里没有任何关联时证据里干脆不带 `giant_share` 这个键（不写 null）。

- 代表概念取该来源**独有**的 concept 里度数最高的 5 个，因为独有的最能说明它在讲什么。度数直接从边表算，全量路径与补账本路径都有（§7.1 第 ③ 步），不依赖只有全量路径才算的 `deg`。
- 显示的名字取**这个来源自己的对象**的名字，不取 canonical 名。canonical 名是组里成员数最多的那个种子第一次出现时的名字，可能来自别的来源，甚至来自 knowhow 写入的对象（knowhow 的 concept 也参与合并，只有 Memory 被排除）。§8.4 有对应守卫。

**影响面**：该来源的可用对象数（`n_objects`，与来源画像同口径）。

**建议动作**

- 主按钮「打开来源核对」：在面板上层打开来源详情（`openSourceDetailById`）。⚠ 现在来源详情与图谱分析在根弹窗协调器里同属 `primary` 冲突组，打开来源会把面板关掉。实现时要加一条共存例外，关掉来源详情后回到面板原来的位置。

**本机实测**：12 个来源命中，`shared_share` 在 0%–4.5%，下一个来源是 7.1%，间隙清楚。抽查的 10 个都是标题与内容不符的错文件。阈值放宽到 10% 是 15 个、收紧到 2% 是 10 个；概念下限取 5、10 都是 12 个，取 20 是 11 个。其中 Hymba 的两份同时又构成 F2 的一对，也就是两份重复的错文件。这种情形下，F2 挂在 F1 下面作附注（「另有一份重复导入：…」），不单列「删除其一」的建议，因为两份都该删。

### 4.2 F2 疑似重复导入 → 删除其一

**判据**：两个来源的 concept canonical 集合 Jaccard ≥ 0.45。

- 集合取两篇各自的 concept canonical，去掉**通用概念**，即出现在超过 30 个来源里的那些。它们对判断「是不是同一篇」不提供信息。
- 只在其中一篇出现的概念**计入分母**：它们是两篇真实存在的差异。

**算法**：精确的前缀过滤相似连接（all-pairs prefix filtering）。步骤如下：

1. 全局按「出现在几个来源里」升序给概念排序。
2. 每篇只把前 `|A| − ⌈0.45·|A|⌉ + 1` 个概念放进倒排表。
3. 共享至少一个前缀概念的两篇才成为候选。
4. 对候选精确计算 J，验证是否过阈值。

这是精确算法，不是 MinHash 一类的随机草图：同一输入结果逐字相同，没有漏报。本机产生 450 对候选，验证命中 8 对，与暴力两两计算的结果完全一致，耗时 7 ms。

**证据**：J、共享概念数、两边各自的对象数，以及 5 个共享的代表概念。

**影响面**：建议删掉的那份的对象数。

**建议动作**：删除其一，**建议保留对象更多的那份**；对象数相同时保留较早导入的。两份各有一个「打开来源」按钮；删除按钮只放在建议删除的那份旁边，调起既有删除确认框。按钮旁写明理由：「两份内容几乎相同，保留对象更多的一份」。

**本机实测**：命中 8 对，J 在 0.48–0.65。再往下一对是 0.20，是 Qwen2.5 与 Qwen2——同系列的两篇论文，不是重复。

### 4.3 F3 解析残缺 → 重新解析

F3 与 F1 的界线是本规格最要紧的判别：

- **内容连贯，但讲的东西与本库无关** → 错文件 → F1，删除。
- **名字破碎，或者抽出来的东西明显偏少、偏散** → 解析问题 → F3，重新解析。

**判据**：下列子信号任一成立即命中。所有子信号都取「相对本库中位数的偏离」，不用绝对值，因为不同语料的正常产出差别很大。

- **F3a 名字破碎**：该来源的 concept canonical 名里，形如「L l a m a 3 . 1」（4 个以上连续的单字符 token）的占比 ≥ 10%，且至少 5 个。
- **F3b 产出偏低**，下列任一：
  - 每段抽出的对象数低于本库中位数的 1/3；
  - 关联数/对象数低于本库中位数的 1/2。这一项只判对象数**至少 20 个**的来源，中位数也只在这些来源上取：三五个对象的小笔记没有关联，说明不了解析坏没坏，混进中位数还会把它拉到 0；
  - 孤立对象占比高于「本库中位数的 3 倍」与 **10%** 两者中较大的那个，且至少 20 个孤立对象。没有这道 10% 的下限，中位数为 0 时阈值也退化成 0——一个来源只要有 20 个孤立对象就命中，哪怕只占它的 1%。

  两个下限是 2026-10-19 实现评审时补的（主会话裁决），作为具名常量随规则版本写进账本。v1 规则当时尚未发布，没有因此提升规则版本。本机预期仍是 0 命中（孤立占比中位数 4%、最大 11%）。

  比较全部是严格的，并按精确有理数计算：恰好压线不算命中，浮点乘法不会把压线的情形算偏。

两条规则都成立时（解析坏了的文件往往也「不和别人共享」），只报 F3，并附注「重新解析后若仍与本库无关，会转为疑似内容错配」。

**证据**：命中的子信号及其数值（孤立占比一项另带实际生效的阈值）；F3a 另附 5 个破碎名样例。对象数是影响面，不进证据。

**影响面**：F3a 计破碎名对应的对象数。F3b 计该来源的全部对象数，因为重新解析会替换整篇的知识条目。

**建议动作**：「重新解析」。

- 走批量重新解析 `POST /notebooks/{id}/sources/reparse`：需来源写权限，异步执行；体检里的「重新解析」走的也是它。
- **不**走单篇的 `POST /sources/{id}/parse`：它是同步的，要等整条解析加抽取流水线跑完才返回。
- 既有的重新解析入口都没有确认框。但重新解析会重新调用模型，并替换这篇来源现有的知识条目，所以从面板触发时加一个确认框，把这两点说清楚（见 §14 末尾的「默认取舍」）。
- 镜像库与 `promotion` 来源不显示按钮，沿用既有规则。

**本机实测**：

- F3a：只有 1 个来源命中 2 个名字（Minitron，2/73 = 2.7%，低于阈值）。
- F3b：三个分布都很窄。每来源关联/对象比 p10–p90 是 1.08–1.41；对象/段是 4.43–7.27；孤立对象占比 p50 是 4%、p90 是 8%、最大 11%。

本机**没有**解析坏掉的来源，所以 F3 的阈值在本机标定不了，只能看生产分布。这是 §14③ 要量的主要一项。

### 4.4 F4 疑似没合并的同名概念 → 送进待确认合并

**判据**：concept 的名字小写后，去掉空格、连字符、下划线、点、括号等全部分隔符，得到 squash key。squash key 相同、却不是同一个 canonical 的，算作一组。

先说清今天的种子是怎么算的，否则下面的分工会分错：`_norm` 把 `[\w+/ ]` 之外的**所有**字符（连字符、点号、括号……）都先变成空格，再把连续空白折成一个空格。所以「Llama 3.1」得到 `llama 3 1`、「Llama 31」得到 `llama 31`，「Q-Former」得到 `q former`、「Qformer」得到 `qformer`。今天没合并的 squash 同名组，种子之间的差别都只在**空格落在哪里**。

这条规则与 §五 S1 是**一窄一宽**的两半，必须一起看。

- **窄的一半**：差别只来自原文里的空白、连字符、下划线（「Q-Former / Qformer」「RMS Norm / RMSNorm」）。这是合并种子的确定性缺陷，正确的修法是 S1：种子里去掉这几种**原文**分隔符，让它们自动合并，不该让用户逐条点。本机 14 组。
  - S1 修好之前，这一半在「需要开发处理」区报总数。
  - 若 §14② 决定**不修** S1，这一半并入 F4，走人工确认。
- **宽的一半**：还要再去掉点号、括号等才同名（「Llama 3.1 / Llama 31」）。这类自动合并有误合风险，交给人确认。这是 F4 的本体。S1 刻意不碰它们：点号、括号变出来的空格在 S1 的种子里保留，所以 `llama3 1` 与 `llama31` 仍是两个种子。
- 本机的 14 组全部属于窄的一半；用宽口径（再去掉点号、括号、引号）量也是 14 组，没有多出来的宽组。宽的一半在生产上有多少，要在 §14③ 量。
- 用户已经**驳回或暂缓**过的组不再报：那是用户的判断，不是问题。它们进「已通过」，写「已判定不是同一个」。
  - 判定**按 seed 匹配，不按 canonical id**：合并决定按 seed 对存（`decided_seed_pairs_from`），canonical id 会随簇的最小成员漂移。本机 1,344 条驳回或暂缓的决定里，有 183 条引用的 canonical id 已经不存在。
  - 组内两个 canonical X、Y，只要存在一条驳回或暂缓的决定 {a, b}，且 a 是 X 某个成员的 v1 seed、b 是 Y 某个成员的 v1 seed，就判为「不是同一个」。这里的成员包括隐藏来源的成员：seed 只用于判定，不展示。

**建议动作**：跳到知识图谱视图的「待确认合并」，用既有的「合并 / 拒绝」按钮（需图谱写权限）。确认之后，既有前端会自己发起一次重新合并。

⚠ **今天任何调用方都不能往待确认合并里加一对。** 那张表只由两处写入：统一重建的 pending 刷新，与增量融合的桥接检测；`write_merge_candidate` 除了测试没有调用方。所以 F4 需要一处开发改动：

- 在 `rebuild_unified_kg` 的 pending 刷新里，加一档「squash 同名」候选来源；按既有的 seed 对去重，并尊重既有的拒绝和暂缓决定。
- 这会改变 pending 的产出，所以要 bump `CLUSTER_ALGO_VERSION`，否则已部署库的版本闸会把它静默跳过。
- ⚠ 这次 bump **本身就很重**：每个已部署库下一次整理都会全量重新合并，并以 `force=True` 重建主题板块（板块 id 全部重铸）。代价与 S1 相同。所以若 §14② 通过 S1，P3 与 P4 共用**一次** bump，不分两次付。

这样 F4 的问题行可以直接说「已放进待确认合并，N 组」，不用让用户自己去找。

**证据**：组内的名字（≤ 5 个）及各自的成员数。名字必须取自**可见来源**里的成员对象（§8.4）。**影响面**：组内全部成员对象数。

### 4.5 F5 没建立关联的内容 → 补上关联

**判据**：所在 canonical 在关联图上没有任何非自环关联的可用对象。全库一条问题；证据里按来源列出分布，取数量最多的 5 个来源。

**本机实测**：1,830 个，占 4.4%。它们的原始度数全部为 0，没有「合并后只剩自环」的情况。按类型：claim 1,303、formula 220、concept 219、procedure 88。

**但本库已经跑过「补上关联」**：4,980 条 `relink:` 关联都还在。补上关联是确定性、幂等的：上次没能补上的，再跑一次还是补不上。

所以 F5 的按钮只在**补上关联有可能改变结果**时出现：要么从没跑过，要么上次跑完之后又有新内容进来。

**这件事今天判不出来。** `GET /kg/relink/status` 的结果只存在内存里，进程重启后就是 `idle`；「跑过但一条都没补上」也不留任何痕迹。所以需要一个持久标记：补上关联完成时，记下当时的 `kg_mutation_seq`。这个标记与 §8.3 的标记表是同一张表。维护槽只串行维护任务，不挡普通摄取：若跑的过程中世代除了补上关联自己逐来源推进的那几次之外还动过（某来源处理完之后又被摄取改动，那批新内容这次没看过），标记改记**开跑时**的世代，按钮保持可用；没有并发写入时照旧记完成时的世代。

两种状态：

- **可能改变结果** → 待处理，显示「补上关联」按钮。
  - 走既有的 `POST /notebooks/{id}/kg/relink`：需图谱写权限，后台任务，与重新合并、删除知识图谱共用维护槽。槽被占时如实显示「其它图谱任务进行中」。
  - 结果写在按钮旁：「新增 N 条关联，还剩 M 个」。N、M 用补上关联自己返回的计数（`edges_added` / `isolated_after`），并照它的口径说「还剩 M 个没有关联的知识条目」。它数的是**对象**的原始度数（非 deprecated 的对象），F5 数的是 **canonical** 层面的孤立（可用对象），两个数对不上是口径不同，不能拿来互相核对或相减。
- **已经跑过、之后没有新内容** → API 在 `passed` 区返回，读侧状态 `relink_spent`；界面放进「诊断数据」那块，不放按钮，写：「补上关联已经跑过，剩下 M 个没有可自动补上的关联；集中在某几个来源的，见疑似解析残缺」。

## 五、B 档：需要开发处理

### S1 合并种子归一漏洞

`backend/app/domain/kg_merge_seed.py::_norm` 把 `[\w+/ ]` 之外的所有字符变成空格，再把连续空白折成一个空格，**空格保留为分词边界**。于是「Q-Former」得到 `q former`，「Qformer」得到 `qformer`，两个种子不同，永远不会合并。本机 14 组。

**修法**：只去掉来自**原文**空白、连字符、下划线的分隔，且必须在「标点变空格」那一步**之前**做；点号、括号等变出来的空格保留。这样「Q-Former」「Qformer」都得到 `qformer`，而「Llama 3.1」得到 `llama3 1`、「Llama 31」得到 `llama31`，仍是两个种子。

- ⚠ 这个修法**不是只合不拆**。今天的旧种子分不清一个空格来自原文的空白还是来自标点：「Llama 3.1」和「Llama-3-1」的旧种子都是 `llama 3 1`，新种子却分别是 `llama3 1` 和 `llama31`。所以少数旧种子组会被拆开。另一种做法是「旧种子直接去掉全部空格」，那样只合不拆，但会把「Llama 3.1」和「Llama 31」合掉——那正是要留给人确认的一类。本规格选前者：误拆只是让少数本该在一起的写法暂时分开（可以经待确认合并补回），误合会把两个不同的东西揉成一个。本机（9,400 个 concept 对象、7,218 个旧种子）：前者拆开 4 个旧种子组，新种子合并了 75 处旧种子；后者有 4 处属于有风险的合并。1,880 条已存决定里，拒绝或暂缓过、在新种子下撞成同一种子的有 0 对；5 条找不到对应的当前对象。生产上两类各有多少，在只读演练里一起量。
- 改在 `seed_concept`（种子专用）里，**不改 `_norm`**。`_norm` 还被 `kg_merge._discriminative_conflict` 拿来按 token 判「仅差一个对立词」（第一/第二、上/下……），在 `_norm` 里压掉空格会让这道护栏静默失效。
- 缩写剥离与别名表都按词工作：别名映射在压空格之前做，别名表的值同步压空格。

**代价**，必须事先写清：

1. **要 bump `CLUSTER_ALGO_VERSION`**，否则版本闸会静默跳过修复。后果是每个已部署库的下一次「更新分析」都会全量重新合并一次，并以 `force=True` 重建主题板块，簇与板块一次性重排。在生产 878 万对象上，这是一次很重的重聚类。
2. **已存的合并决定是按 seed 名存的**（`seed_a` / `seed_b`）。改了种子之后，旧 seed 对不上新 seed，用户确认过、拒绝过的决定都会失效。需要同批迁移。
   - 新种子**不能**由旧种子字符串推出来（上面那条：空格的来历已经丢了），只能由旧种子组里成员对象的原名重算。一个旧种子可能对应几个新种子。
   - 确认过的对：两侧的新种子两两并起来，保住用户要的合并。拒绝或暂缓过的对：两侧的新种子两两记为不能合并。
   - 迁移要覆盖 `seed_a` / `seed_b` 为空的行：桥接检测写入的候选（`insert_merge_candidate`）与早期行都没有 seed，它们的决定键回退成「去掉 `K-` 的 canonical id」（`decided_seed_pairs_from`）。
   - 有一类要单独处理：用户**拒绝过**（明确说过「不是一回事」），但按新规则 seed 恰好相等的对。种子相同就一定会合并，所以必须给一个例外机制：要么加按对象的「不能合并」约束，要么对这几对保留旧种子。这类对有多少，要在生产上量（§14③）。
3. **canonical id 会成批变化。** 全量重建时，一个合并组的 id 是 `"K-"` + 组内**最小的种子**（`kg_merge.py` 的 `cid = id_prefix + min(grp)`）；增量融合时是 `"K-"` + 经缩写重定向后的种子。最小种子含空格的组，id 都会变。这不是新的不稳定：每次确认合并改变组内最小成员时，id 本来就会变（`decided_seed_pairs_from` 的 docstring 写明了这一点），S1 只是一次性的大面积变化。实现前仍要核实持久化内容里有没有存 `K-` id，例如对话引用、分享快照、经验库；有的话，要么迁移，要么解析时兼容旧 id。
4. 只对 concept 的种子生效；claim、formula、procedure 的归一化器不动。

**实施细化（计划阶段核对代码后补）**

- **只改 `seed_concept` 不够。** 统一重建的种子流、合并后的欠账催收、增量融合都直接写 `_norm(...)`；别名表、`_seed_with_alias`、`bridge_canonical_id` 也都用 `_norm`。这些都要按「种子版本」参数化。新规则记为 v2，旧规则冻结为 v1，squash key 定义为「v2 种子去掉空格」（比种子粗，保留 `+` 与 `/`）。F4 用同一个函数，并排除被覆盖成 `~v1:` 的组。
- **每个库记录自己当前发布的种子空间**：`unified_kg_state.concept_seed_version`，在发布合并结果的同一条语句里写。部署之后、该库重建之前，新上传的对象按**已发布那一代**的空间安置（「Q-Former」仍进旧簇 `K-q former`）；翻转之后才进 `K-qformer`。否则增量融合与已发布的簇会对不上。
- **已存决定的重算不能放进迁移。** PG 迁移是带 checksum 的纯 SQL，调不了 Python 的归一化器；PG 的正则与 NFKC + `\w` 在非 ASCII 上也不逐字一致。所以迁移只给 `concept_merge_candidates` 加一列 `seed_version`（存量记 1），重算放进每个库**第一次 v2 全量重建**里（沿用 Memory 隔离「迁移打标记、之后由 Python 重建」的先例），幂等、失败可重来：
  1. 建簇之前读出所有 v1 行的键（`seed_x`，为空时取去掉 `K-` 的 canonical id）。
  2. 种子流里每个对象另算一次 v1 种子；命中某个键的，把它的 v2 种子记进该键的新种子集合。只在库里还有 v1 行时才付这笔开销。
  3. 翻译：确认过的对 → 两侧新种子两两记为确认（被拆开的旧组靠这些对并回来）；拒绝/暂缓 → 两两记为不能合并；任一侧找不到当前对象 → 悬置，保持 v1，下次重建再试，悬置数发事件。
  4. **撞种子的例外：保留旧种子。** 在 v2 种子上按确认对建并查集；若某条拒绝或暂缓的对在 v2 下落进同一分量、在 v1 下却不同，就把相关的键放进覆盖集，这些键的对象种子改为 `~v1:<旧种子>`（`~` 会被归一化洗掉，不会撞真名）。重复到没有违例；覆盖集只增不减，最坏退化成 v1，一定终止。不另建表，覆盖记在 v2 决定行的 seed 里。「按对象的不能合并约束」做不了：同种子即同组是精确合并的构造前提，约束只能拦相似度边，拦不住同种子。拒绝与暂缓都覆盖，不分人工还是自动判重，行为零变化。
  5. 落库放进既有的 pending 刷新事务（已有认领复读与先删后插的串行化；PG 侧对 v1 行加 `FOR UPDATE`）；行数变化折进聚类输入版本里的决定计数，否则下一次「更新分析」会被迫再全量重聚一次。
- **id 的变化面比「最小种子含空格的组」大得多**：几乎所有多词概念的 canonical id 都会变。两处因此必改：
  - 概念描述缓存今天按 canonical id 复用，不改的话模型会把几乎全部概念描述重写一遍。改成按描述签名复用（今天命中本来就要求签名相等，按签名查是严格超集）。
  - 「待确认合并」前端今天显示的是去掉 `K-` 的 id，也就是种子串；S1 之后会显示成「rmsnorm」「~v1:…」。后端改为返回两侧的 canonical 名（按页有界点查），以及「同名不同写法」的标记。
- **跨库混合期**：按图检索与联邦推理会把活动库与参考库里同一个 canonical id 并成一个枢纽。一边已是 v2、另一边还是 v1 时，多词概念的跨库桥接失效，直到两边都重建完。收敛方式按 §14 裁决⑤：懒收敛，运维文档写明这段混合期，并建议参考库优先、低峰手动重建。
- 对话引用、问答轨迹、回答链接、经验库、Agent 画像只存对象/段 id 或文本，不受影响；派生层（合并后关联、共提、板块、分析产物、视图缓存、规模索引）都按版本键整份重建。
- 部署之后、该库重建之前，「需要开发处理」区的 S1 项改写为「已修复，更新分析后生效」。
- **交付（2026-10-22）**：S1 与 S2 合成**一个 PR-4**：一个迁移（SQLite v102 / PostgreSQL 0083，种子空间两列、分区两列与 `board_key` 回填同一步），`CLUSTER_ALGO_VERSION` 只升一次（到 4），一条 release note（`release-notes/kg-merge-rule-update.md`，种子与板块共用）。

### S2 主题板块划分对无关改动不稳定

**机制**：节点下标按关系 id 的首次出现顺序编号，再加 `seed=42` 的随机访问顺序。任何删改都会让下标整体移位、随机顺序跟着全变，Louvain 于是走出一条完全不同的路径。原样重跑逐字相同，确定性没有问题；问题在于**对输入不连续**：输入改一点，输出改一大片。

**影响**：

- 面板上的板块数字与俯瞰图；
- 以后的快照对比；
- 对比类问题的社区回退检索（`communities.py::community_peers`）：库里删了一篇不相干的文档之后，同一个问题取到的「同类」可能整体换掉。

**问题清单本身不受影响**：它的规则和主键都刻意不依赖板块。§4.1 用的是连通分量，不是板块；主键见 §3.2。

**本机实测**：在主连通块（25,865 个节点）上比较三种删改：

- 删两个与主连通块零连接的孤岛来源（LMCache、Titans）；
- 删一个主连通块里的重复来源（Mamba2_full，它的 339 个 canonical 里有 320 个在主连通块）。

| 方案 | 模块度 | 删孤岛来源 LMCache | 删孤岛来源 Titans | 删主连通块内的重复来源 Mamba2_full |
|---|---|---|---|---|
| A 现状：整图、首次出现序、Louvain seed 42 | 0.9392 | 18/80 原样，16.4% 换板块 | 18/80，16.6% | 18/80，18.0% |
| B 每个连通分量单独跑；分量内按 canonical id 编号；resolution 取「分量边权 / 总边权」 | 0.9402 | 74/80，0.8% | 80/80，0% | 23/80，16.4% |
| B' 同 B，但 resolution 取 1 | 0.9097 | 86/86，0% | — | 23/86，16.6% |
| C 以上一代划分热启动 Leiden（`initial_membership`），从它自己的稳态起步 | 0.9424–0.9427 | 82/84，0.1% | 84/84，0% | 76/84，0.5% |
| 参照：冷启动 Leiden | 0.9430 | | | |

表中「原样」指成员 ≥ 3 的板块成员集逐字相同；「换板块」指节点不在它旧板块的最佳匹配新板块里。

**怎么读这张表**

- **B** 只治孤岛的删改，因为各分量互不影响。主连通块内部的改动照样连锁（16.4%），这是 Louvain 本身的非局部性。B' 完全局部，代价是全局模块度掉 0.03，板块数也变多。
- **C** 对两种删改都稳（≤ 0.5%），模块度还略高于现状，同输入重跑是不动点。
  - 代价是**依赖历史**：划分不再只是当前图的函数，而是「当前图 + 上一代划分」的函数。冷启动得到的划分，与增量演化出来的不同。⚠ **冷启动不能以 `force` 为判据**：每一次真正的重新合并都会以 `force=True` 调 `rebuild_communities`，照那个判据热启动永远不会发生。冷启动只在下列情形：没有已发布的划分；已发布划分的分区版本与当前代码不同（首次切换就是这一档）；走 networkx 回退；运维显式要求（`backend/app/scripts/recluster_kg.py --cold-partition`）。
  - 第一次从 Louvain 切过去，会一次性动约 10% 的节点。
  - `initial_membership` 只有 igraph 的 Leiden 有。`rebuild_communities` 在没装 igraph 时还有一条 networkx 回退路径；那条路径保持今天的冷启动 Louvain，并在账本里记 `partition_mode: cold_fallback`，不假装稳定。igraph 是 `requirements.txt` 的依赖，回退只在缺包时出现。回退的产物不是当前分区算法划出来的，发布时分区版本记 0，所以下一次有 igraph 的重建按「版本不同」冷启动，不会从 Louvain 的结果热启动（S2 评审裁决，2026-10-21）。
- 这与「换 Leiden 当质量杠杆」被证伪并不矛盾。那条证伪的是「换个算法让板块更好」（模块度只 +0.003）。这里用 Leiden，是因为它支持 `initial_membership`，买的是稳定性。

**建议**：以 C 为主。冷启动时按 B 的方式跑（分量 + canonical id 序），这样冷启动本身也是确定的。另外加**板块 id 续用**：新旧板块的成员 Jaccard 互为最佳且 ≥ 0.5 时，沿用旧 id。本机在 C 下 84/84 个板块都找得到这样的继任者。只有 id 能续用，快照对比和检索才谈得上「同一个板块」。

续用的落点是**新增一列 `communities.board_key`**，不是沿用 `communities.id`：后者是单列主键，`community_members` 的主键与同步键都要求它每一代重铸、全库唯一。`board_key` 在续用时沿用旧值，新铸时取成员内容哈希（代内撞键时确定性再散列）；迁移把存量回填为 id。它今天没有消费方，本批在 API 里暴露，供以后的快照对比使用。

**它会推翻原设计的一条不变量**：§3.32「Louvain 输出逐字不变」。

- 那一条当时是约束一次重构（dict 换成数组）不得改变结果。这里是**有意**改算法，必然要一次性重排已部署库的全部板块，以及其后所有依赖板块的产物。
- 新的不变量写成：「同一输入图 + 同一上一代划分 → 逐字相同的输出」，并用真实库逐字比对钉住。

**建议与 S1 合并成一次重排。** 两者都会让已部署库的派生结构整体换一遍；分两次做，用户就要看两次「全部变了」。已落实（2026-10-22）：S1、S2 合成一个 PR-4，同一个迁移 SQLite v102 / PostgreSQL 0083 带两者，每个库升级后的第一次全量重建在同一趟里重新合并并冷启动划分；分区另有独立的 `PARTITION_ALGO_VERSION`（1），不另升 `CLUSTER_ALGO_VERSION`。

### S3 板块口径（随本特性交付，不重排）

本机 1,217 个板块里，1,137 个恰好是一整个孤立连通块。面板改报下面几项：

- **主体内容**：即**主连通块**。报它含多少比例的知识对象，以及内部有多少个主题（主连通块内的板块数）。
- **孤岛**：报另有多少个互不相连的小块、来自多少个来源。孤岛按来源归因，主要成分是 F1 的来源，体现在 F1 证据的 `giant_share` 里。
- 原设计的「主体板块」（覆盖 50% 成员的头部板块）与 `mainstream_share` 留在诊断数据的来源画像表里，不再用来挑「最先复核的来源」。

数据怎么放：

- 只看连通分量的数（主连通块对象占比、孤岛数、孤岛涉及的来源数）放进 `findings` 账本 payload。
- 依赖划分的数（主连通块内的板块数、恰好等于整个分量的板块数）放进本来就依赖板块的 `community_edges` payload。

这样问题清单这份产物始终不依赖板块。S3 只改报告口径与读侧呈现，不改划分本身，不触发重排。

### S4 「更新分析」不再空跑（随本特性交付）

「更新分析」调用 `POST /notebooks/{id}/unified-kg/rebuild`，`force=False`。三道版本闸（聚类输入版本、社区图 seq、分析账本）全部通过时，什么都不重算。面板根据报告里已有的新鲜度字段判断按钮状态：

| 条件 | 按钮 |
|---|---|
| 账本齐全，`dirty=false`，全部在场产物与板块都是 `stale === false` | 置灰，写「已与当前图谱一致，无需更新」 |
| 有在场产物 `stale === null`（合并代次无从判断），其余都一致 | 置灰，写「这一项只有在重新划分主题板块时才能核对，普通更新不会改变它」 |
| `dirty`；或任一 `stale === true`；或账本不齐（包括升级后缺 `findings`） | 可点：「更新分析」 |
| 现有的合并结果建于旧的合并规则（见下） | 可点，写「合并规则已更新，需要更新一次」 |

**刻意不在请求路径上重算聚类输入版本**：`cluster_input_facts` 要对对象表和向量表各做一次 `COUNT(*)`（生产 878 万行），不能每次打开面板都跑。

**合并规则版本必须单独可见，否则 S4 会挡住 S1/P3 的修复。** `cluster_input_version` 是一个 sha1，把 `CLUSTER_ALGO_VERSION`、`embed_dim`、运行时维度和几项数据计数揉在一起；报告里没有任何字段能读出其中的代码分量，而 bump `CLUSTER_ALGO_VERSION` 也不会置 `dirty`。不处理的话，P3/P4 部署之后面板会置灰写「无需更新」，而真点下去恰恰会应用修复。做法：`unified_kg_state` 加一列，存上次合并时的代码分量（算法版本 + 两个维度），与 `cluster_input_version` 在同一次收尾写入；overview 同时返回这一列与当前代码的值，不一致就走上表最后一行。这一列随 P1 的迁移一起加。只在合并收尾写不够：输入未变、走跳过路径的那一次也要补写（带「输入版本仍相等」守卫的 UPDATE），删除知识图谱时清空；否则升级后的库永远到不了「无需更新」。

**已知残留**：只补齐了检索向量（向量数变了、`kg_mutation_seq` 没动）时，面板会说「无需更新」，真点下去却会重聚类。这是原设计新鲜度契约里本来就有的盲区，不是本特性引入的，如实记在这里。

「更新分析」本身**不是**任何问题的处置动作（§六）。

## 六、闭环

```
处置（改变输入）              更新分析（按新数据重算）              按主键核验
删除来源 / 重新解析   ──►   合并 → 板块 → 五份产物 + 问题清单   ──►  F1 的 source_id 还在吗？
确认合并 / 补上关联                                                  F2 的来源对还在吗？……
```

- **处置必须改变输入。** 图谱没变时点「更新分析」只是原样重试，什么问题都不会消失。这也是 S4 要把按钮置灰的理由。
- **按问题自身的主键核验，不按板块核验。** 板块会洗牌（S2），「这个来源还在不在 F1 里」不会。
- 已处置、还没更新的问题标「已处理，更新后核验」（§3.5），不从列表里消失，让用户看得到「我做过的事还没被核实」。
- 更新完成后，报告头部给出对比：「上次 N 条已消失 · M 条仍在 · K 条新增」。已消失的列出名字，用的是发布时存下的 `label` 快照，所以来源删了也说得出是谁。
- `rules_version` 不同的两次之间不做对比（§3.2）。

## 七、计算挂点与生产代价

### 7.1 挂在哪一步

全部新计算都放在 `KnowledgeLifecycleService._compute_kg_analysis`（`backend/app/services/knowledge_lifecycle.py`）里，也就是**写事务之外**；发布仍然是 `_publish_communities_generation` 那**一个**写事务。只在默认层、`_ledger_speaks_for_level` 为真时运行（原设计「方向五」）。

| 步骤（按执行顺序） | 今天在做什么 | 新增 |
|---|---|---|
| ① `rebuild_communities` 逐行读 `community_graph_rows`，建 `can2idx` 与列式边表 | 836 万行，做 canonical 映射 | 每行多取一列 `kr.source_id`，按来源累加关联条数（F3b）。**行序不变**（两个后端都是 `ORDER BY kr.id`），Louvain 的输入逐字不变。⚠ 先决条件：PG 侧这条查询今天走 `db.execute()`，整张结果集会先收进 libpq 的客户端缓冲，正是原设计第 14 轮在 `source_canonical_rows` 上修过的那种失败形态。加列之前先改成 `cursor().stream()`，见下文「顺带发现」 |
| ② 跑 Louvain，或在补账本路径读回已有划分 | | S2 若做：读上一代划分作热启动（见 7.3） |
| ③ 进入 `_compute_kg_analysis`，在折叠跨板块边**之前** | 边表在手 | 用边表求连通分量（`scipy.sparse.csgraph.connected_components`，scipy 已是依赖），并按 `np.bincount` 求每个节点的度数。每节点存一个 int32 分量号、一个 int32 度数；CSR 临时结构用完即放。全量与补账本两条路径共用同一份实现 |
| ④ `fold_cross_community_edges`（同时释放边表） | 不变 | 不变 |
| ⑤ 来源画像那一趟：`source_canonical_rows` + `SourceBoardCounter` | 878 万行，每行存两个 int32。**零板块的库整趟跳过**（`if total_members:`） | SQL 多返回一列「是不是 concept」。concept 行另记（来源序号，canonical 下标）两个 int32；不在图里的 concept canonical 用一张旁路 dict 另编下标，只为 F1/F2 计数，**不扩 `can2idx`**（会与 `SourceBoardCounter` 的下标表越界冲突）。「在不在图里」以 `edge_table.n_nodes` 为界，不以 `can2idx` 为界：补账本路径会把不在图里的板块成员也补进 `can2idx`。另按来源累加孤立对象数（F5、F3b）。⚠ 问题清单是必需产物，所以零板块的库也要跑这一趟扫描，只是不写来源画像。原设计刻意为零板块库省掉了这趟扫描，这里把它加回来了，代价要算进去 |

| ⑧ 发布事务 | 板块 + 五份产物 | 另写 `findings` 账本行与问题明细；读旧账本行与旧明细（≤ 上限行，主键范围读）算出对比摘要、继承 `first_seen_*`；清掉主体已不存在的豁免（§8.3：F1/F3 来源已被删、F2 任一来源已被删；F4/F5 发布时一律不清；该规则在新账本里 skipped 或截断时一律不清）。要清哪些在写事务之外算好：读一次标记表，对涉及的来源主键点查（`kg_finding_source_states`）；`relink_attempted` 从不在这里清 |

第 ⑥ 步的计算顺序：

1. 对 concept 关联对去重；
2. 算出每个 canonical 出现在几个来源里；
3. F2 前缀过滤连接；
4. F1；
5. F3a 正则：对 concept canonical 名跑一遍。名字取自 `rebuild_communities` 已经在手的 `names`，不新读。`names` 今天不是 `_compute_kg_analysis` 的参数，要加一个；它只覆盖已经有 `concept_clusters` 行的 canonical，还没合并过的新对象不参与这一项，数量如实记进账本；
6. F4：把 squash key 哈希成 int64，排序找碰撞，再逐组核对原字符串；
7. 取样例名。canonical 名只在内部用来判定，**显示**的名字一律另取：对不超过上限的问题，按主键有界点查该来源（F4 是组内可见来源成员）自己对象的名字。用 F4 可见成员的名字重算 squash key，复现不出碰撞的组丢掉。点查在写事务之外。`idx2can` 在进入本方法之前已经清空，把下标还原成 canonical id 需要对 `can2idx` 扫一遍，只收需要的那些下标。

**问题清单不依赖板块划分**，只用连通分量与合并结果。因此：

- 它归入 `CLUSTER_DEPENDENT_ARTIFACT_KINDS`（因为读了 `concept_clusters`），**不**归入 `BOARD_DEPENDENT_ARTIFACT_KINDS`；
- 板块重铸时不作废它；
- 在补账本路径上，它的合并世代**可以**如实盖当前值。依赖板块的那两份产物在这条路径上只能记 `null`，它不受这个限制。

**顺带发现的既有问题（与本特性无关，但 P1 必须先修）**：PG 侧 `community_graph_rows`（`postgres/unified_kg_store.py`）用 `db.execute()` 取 836 万行关系，psycopg3 的普通游标会在返回时把整个结果集收进 libpq 的客户端缓冲。这块内存 `tracemalloc` 看不见，只有 RSS 看得见，而且恰好叠在建图的峰值上。原设计第 14 轮在 `source_canonical_rows` 上修的就是这种形态（改为 `cursor().stream()`，实测 RSS 从随行数线性增长变成与行数无关）。这里是代码读法得出的判断，没有在生产规模上实测，修之前先在本机 PG 上量一次 RSS 确认。修法相同：改成流式游标。不修就加 `kr.source_id`，会让这块缓冲每行再大二十来个字节以上（推算）。

### 7.2 生产规模的时间与内存（推算，待 §14③ 实测）

基数取自原设计 §二·五，以及原设计第 13 轮的生产规模实测：

- 可用对象 878 万，其中 concept 占 24%，约 211 万；
- 关联 836 万；进图的 canonical 约 171 万；来源 4.9 万；
- `can2idx` 109.4 MB；`community_of_index` 15.2 MB；`SourceBoardCounter` 构造 17.4 MB；边表 12 B/条，约 100 MB。

| 新增项 | 内存（推算） | 时间量级 | 说明 |
|---|---|---|---|
| ① 每行多一列 `source_id`，按来源计数 | 计数器 O(来源数)，几 MB——**前提是这条查询已改成流式**（§7.1 顺带发现）；否则 libpq 缓冲每行多二十来个字节以上 | 836 万次字典自增，秒级 | 多一列，网络与解析的开销多一点 |
| ③ 连通分量 + 度数 | 分量号、度数与主连通块位图共约 14.7 MB，常驻到 ⑥ 结束；`from_edges` 瞬时约 +107 MB RSS（实测：合成 171 万节点 / 836 万边，tracemalloc 峰值 117 MB，含首次 import scipy 约 11 MB） | O(V+E) 的 C 实现；本机 3.6 万节点 2 ms | 与边表同时在场。全量路径上发生在 igraph 图已经释放之后，不抬全局峰值；**补账本路径没有 Louvain 那个更高的峰，这一步因此把它的峰值抬高约 110 MB** |
| ⑤ concept 关联对 | 211 万 × 8 B，约 17 MB；去重排序时另有临时的 17 MB | 每行开销与 `SourceBoardCounter.add` 同量级，但只落在 24% 的行上 | 参照原设计第 13 轮：同类的每行开销，在 200 万行上让来源画像从 4.2 s 变成 10.4 s |
| ⑥ 每个 canonical 的来源数 | 约 7 MB（int32） | 向量化 | |
| ⑥ F2 前缀过滤连接 | 取决于候选对数，**未知** | 本机 450 对候选，7 ms | 4.9 万个来源上的候选对数推算不出，必须实测。设成本上限 `kg_findings_max_candidate_pairs`（Settings）；触顶时如实记 `truncated`，绝不静默 |
| ⑥ F3a 正则 | 0（复用 `names`） | 每个 concept canonical 跑一次正则，秒级 | |
| ⑥ F4 squash 哈希 | 上界 211 万 × 16 B，约 34 MB | 一次排序 | 只对碰撞组回头比较字符串 |
| F3b 每来源段数 | O(来源数) | 要对 chunks 按来源分组计数，等于新增一次 chunks 全表扫；生产段数未知 | 演练实测后再决定纳不纳入。不纳入的话，F3b 只用关联/对象比与孤立对象占比 |
| ⑧ 问题明细 | 最多上限行（`MAX_PERSISTED_FINDINGS`，具名常量，初值每条规则 500） | 可忽略 | 截断写进账本：`total` / `persisted` / `truncated` |

**峰值判断（推理，未实测）**：新增的结构集中在第 ⑥ 步那一刻，叠在 `can2idx` 与 `community_of_index` 之上，推算约 +80 MB。今天的全局峰值在建图与 Louvain 那一段（边表加 igraph 的 C 结构）；到第 ⑥ 步时，igraph 图早已释放，边表也在第 ④ 步释放了。所以**预计不会抬高全局峰值**。这只是推理，必须在生产演练里实测 RSS。

**SQLite 侧**：按原设计 §3.35，标准是正确、有界、不 OOM、不长时间持锁，不做性能调优；性能结论以 PG 为准。

### 7.3 S2 选 C 时的追加代价（推算）

- 全量路径要先读上一代划分：`community_members` 默认层已发布的那一代，约 171 万行。流式读，映射成每个节点一个 int32 标签，约 6.8 MB。
- Leiden 在 171 万节点、836 万边上的耗时**没测过**；本机 3.6 万节点的规模对生产没有外推价值。
- 板块 id 续用：对（新标签，旧标签）复合键排序一次，约 14 MB。

### 7.4 失败语义

沿用原设计。问题清单是 `_compute_kg_analysis` 的一部分，算失败时与其它产物同档处理：被吞掉，发 `kg_analysis_precompute_failed`，板块照常发布。

`findings` 是**必需**产物，进 `REQUIRED_ARTIFACT_KINDS`。写入口那道「少写一行就硬失败」的守卫照旧生效，所以不会出现「其它几份都在、问题清单悄悄缺席」。

升级后，已部署库的账本里还没有 `findings`，于是判为账本不齐。下一次非 force 的整理会走补账本路径自动补上，这是原设计 B1 的自愈路径。在这一档，S4 的按钮是可点的。

⚠ 但今天的读侧会把「账本非空、却缺一份必需产物」判成 `ABSENCE_UNEXPECTED`（`kg_analysis._absence`），前端随即在**每一个**已部署库上亮红色「暂不可据此下结论」，一直亮到有人跑一次整理。这是误报：缺的那份是新版本才有的，不是数据坏了。所以 `_absence` 要多分一档：账本里的其余行都建于这份产物出现之前，就报「升级后还没生成」，显示灰色并提示点「更新分析」，不报红。今天账本行上没有任何版本标记，所以要新增一个契约版本戳（payload 里的 `ledger_contract` 键）：service 盖，store 写入口查，缺键硬失败；没有这个键的旧行就是「建于 findings 出现之前」。

**零板块的库**也要付第 ⑤ 步那趟对象扫描（§7.1），因为 `findings` 是必需产物。

## 八、存储、端点与契约

### 8.1 账本行 `findings`

`kg_analysis_artifacts` 新增一种 kind。payload 包含：

- `rules_version`，以及各规则的阈值；
- 每条规则的 `{status: ran|skipped, reason?, checked, total, persisted, truncated}`；
- 对比摘要 `{previous_built_at_seq, resolved, persisting, new, resolved_samples≤20}`；
- 只依赖连通分量的结构数（S3）；
- 两条世代线的戳。

### 8.2 明细表 `kg_analysis_findings`

```
kg_analysis_findings(notebook_id, rule_id, subject_key, subject_kind, subject_label,
                     subject_refs, severity, impact_objects, evidence,
                     first_seen_kg_seq, first_seen_cluster_seq)
PRIMARY KEY (notebook_id, rule_id, subject_key)
```

处理方式与 `kg_source_profiles` 相同：与账本行在同一个事务里整表重写；账本行不在，就一行明细都不发（原设计第 3 轮）。两个 `first_seen_*` 在发布事务里从旧行继承。「本次建于哪一代」不逐行记，统一取账本行的 seq，免得两处记同一件事。`subject_refs` 存主体涉及的来源 id 列表（F2 是两个，F4 是可见成员的来源），读侧派生「已处理」时用。

### 8.3 标记表 `kg_analysis_marks`（豁免 + 系统标记）

```
kg_analysis_marks(notebook_id, rule_id, subject_key, kind, at_kg_seq,
                  actor_user_id, created_at, note)
PRIMARY KEY (notebook_id, rule_id, subject_key, kind)
kind ∈ { dismissed（标为正常）, relink_attempted（补上关联完成时的世代，§4.5） }
```

- `relink_attempted` 不论 §14④ 怎么定都需要：F5 要靠它判断「再跑一次有没有用」。`dismissed` 是否存在这张表里，取决于 §14④。
- 标记是**用户的决定**，不是派生产物。重建不清它；只在发布时清掉主体已不存在的标记（比如来源已被删）。
  - **实施口径（PR-2 评审裁决）**：「不在新明细里」不等于「不存在」——删除知识图谱后重抽未完成、已豁免的来源正在重新解析、规则被 500 行上限截断或临时 skipped（可比来源不到两个），主体都会离开明细而本身还在。所以：F1/F3 只在主体来源已不在 `sources` 表时清，F2 任一来源已不在时清；F4/F5 发布时一律不清，只随撤销或删库/删笔记本消失；该规则在新账本里 skipped 或截断时一律不清。
  - 因此豁免可以活过明细、跨多次发布累积，`KG_ANALYSIS_MARKS_MAX`（明细上限的两倍 + 1）是标记表自己的硬上限：写满时「标为正常」端点返回 409 与可展示的提示（先撤销一些），已有标记一条都不动。总览的 `counts.dismissed` 只数主体还在当前明细里的豁免（主键点查）。
- 归属与随行要与 `concept_merge_candidates` 对齐，因为那张表同样存的是用户对图谱的决定。笔记本删除时级联删除。分享拷贝、`merge_dbs`、快照校验、跨环境增量同步要不要带上它，按那张表的现行处理方式核对后决定，不另立口径。

### 8.4 端点

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/notebooks/{id}/kg-analysis` | 笔记本读 | 新增 `findings_summary`。只读账本，沿用既有的记忆化 |
| GET | `/notebooks/{id}/kg-analysis/findings?zone=open\|passed\|dismissed&limit&offset` | 笔记本读 | 返回一页问题，加读侧派生的 `status`（§3.5，最多一页的主键点查）。与 `/sources` 一样不做记忆化 |
| PUT / DELETE | `/notebooks/{id}/kg-analysis/findings/{rule_id}/{subject_key}/dismissal` | 图谱写，与合并确认同级 | 标为正常 / 撤销（§14④ 已选后端持久化）。成功 204；镜像库返回 409（既有围栏）；无权限仍是 404；PUT 的主键不在当前明细里返回 404；DELETE 幂等。`subject_key` 按 `:path` 取（F4 的主键可能含 `/`），两段都由路由解码一次 |

- 响应里只用内部代号，界面词由前端映射，这是原设计 T3 的红线。
- 样例名与标题只来自**可见来源**。`source_canonical_rows` 已经排除 memory/knowhow 来源，但这还不够：canonical 名可能来自 knowhow 写入的对象（knowhow 的 concept 参与合并，只有 Memory 被排除），所以「这个 canonical 有本来源的成员」不能推出「它的名字来自本来源」。显示名一律取可见来源成员对象自己的名字（§7.1 第 ⑥ 步第 7 条）。守卫要检查名字的出处，而不只是来源是否可见：构造一个 canonical 名来自 knowhow 对象的夹具，断言那个名字不出现在 payload 里。

### 8.5 迁移连带清单

要新建两张表，并给 `unified_kg_state` 加一列。即使 §14④ 选浏览器本地，`kg_analysis_marks` 也要建，只是不存 `dismissed`。

1. SQLite 追加 `_migration_N`，并 bump `SCHEMA_VERSION`。编号取实现当时 origin/master 的下一个；PG 同号文件并存不会报冲突，所以开工前先看最新号。
2. PostgreSQL 打包迁移，并 bump MANIFEST；两张表加进 `POSTGRES_BUSINESS_TABLES`。
3. 全仓搜索 `migrate() == N` 一类的断言，一起改。
4. 登记笔记本删除级联、`merge_dbs`、`verify_repository_snapshot`、分享拷贝、增量同步 capture（见 §8.3）。
5. 登记「删除知识图谱」（`delete_notebook_kg`）：它今天会清掉 `kg_analysis_artifacts` 与两张明细表。`kg_analysis_findings` 跟着清；`kg_analysis_marks` 里的 `relink_attempted` 跟着清（图谱没了，「补上关联试过」不再成立）；`dismissed` 保留，因为它是用户对来源的判断，重新整理后同样的问题会被同样地标为正常。
6. `unified_kg_state` 加一列，存合并时的代码分量（§五 S4）。
7. 合并决定的 seed 重算迁移属于 S1，只在 §14② 通过时随那一批做。

## 九、对原设计不变量的遵守

| 原设计不变量 | 本规格怎么守 |
|---|---|
| 重活不进写事务（§3.3 第 13 轮） | 全部新计算都在 `_compute_kg_analysis` 里，新增的重活读方法同样挂 `_reject_inside_write_transaction`，以及按调用时刻记 `write_depth` 的语义守卫。**唯一的例外**是发布事务内那次读旧明细（为对比摘要与继承 `first_seen_seq`）：它必须在事务里读，所以不能挂那道守卫。它比第 16 轮的发布前复核（单行 state 读）大：最多 `MAX_PERSISTED_FINDINGS` × 规则数行的主键范围读。约束改成另一条守卫：这次读的行数有界，并且走 `(notebook_id, rule_id, subject_key)` 主键 |
| 原子发布 | `findings` 账本行与明细，跟板块和其余五份产物在同一个写事务里发布。补账本路径上「划分已被换掉就整份放弃」的规则照旧覆盖它 |
| 两条世代线、三值新鲜度 | 盖 `kg_mutation_seq` 与 `built_at_cluster_seq` 两个戳。因为不依赖板块，补账本那一档也盖得出当前合并世代，不会是 `null`。读侧照旧经 `artifact_is_current` 做三值判定 |
| 隐藏 memory/knowhow 来源排除 | 规则的主体只取可见来源，沿用 `source_canonical_rows` 的 `NOT EXISTS` 判据。孤儿引用不是任何规则的主体，仍在诊断数据里报 `source_missing` |
| 双后端 parity，以 PG 为准 | 规则全部写在后端中性的纯计算模块里（与 `kg_analysis_precompute` 同一套做法），store 只负责流式读与落库。同一份夹具在两个后端上要产出逐字相同的问题行。性能只在 PG 上量 |
| 逐指标新鲜度，不挂整页横幅 | 每条问题都带 `built_at_seq`；报告落后时逐条写「基于变更 #N」 |
| 零板块库 | 问题清单不需要板块，规则照常判；没有输入的规则报「没法检查」，不报「通过」。代价：原设计为零板块库省掉的那趟对象扫描，现在要跑（§7.1 第 ⑤ 步） |
| 账本缺必需产物就报「异常」 | 升级后缺 `findings` 是预期的，单独一档灰色「升级后还没生成」，不报红（§7.4） |
| 截断不静默 | 明细上限、前缀连接的候选上限都写进账本（`total` / `truncated`） |
| 生产路径不写影响结果的字面量上限 | 阈值是具名常量，并随 `rules_version` 记录；成本上限是 Settings 字段；具体数值只写进产品/API 参考 |
| 界面词表 | 见 §十 |
| 原设计 §3.32「Louvain 输出逐字不变」 | 本特性的 S3、S4 与 F1–F5 都**不碰**划分。只有 S2 有意推翻这一条，需要 §14② 拍板 |
| 原设计 §3.3 末尾的边界条款、§二「明确不做：治理动作」 | 本规格与之冲突，需要 §14① 拍板修订 |

## 十一、实测证伪、不做的

| 想法 | 为什么不做（本机实测） |
|---|---|
| 换 Leiden 当质量杠杆 | 模块度只 +0.003；Louvain 内部不连通的板块只有 1 个，Leiden「保证板块内部连通」的好处在这里用不上 |
| 用簇成员名的多样性判过度合并 | 合法的写法变体（缩写、大小写、中英文）都会命中，是假阳 |
| 只用邻居 Jaccard 判漏合并 | 兄弟概念（同一类里的不同成员）邻居高度重合，是假阳 |
| 度分布幂律拟合 | 拟合出的指数不对应任何用户能做的动作 |
| 单一健康分 | 不同规则之间没有公共单位（§3.3） |
| 用「覆盖 50% 成员的头部板块」当主体 | 会把真混入的来源与正常文档并列在 0%（§一） |

## 十二、验证计划

1. **纯函数单测**（不起库）：
   - 每条规则的阈值边界：恰好压线、全空、并列；
   - F2 前缀连接与暴力两两计算结果逐字相等；
   - F1/F2/F3 的先后与嵌套：两份重复的错文件只出一条 F1，附注那份重复；
   - 主键稳定性：删掉一个无关来源，其它问题的主键不变；
   - F4：驳回或暂缓过的组不再报；
   - S1（若做）：「Q-Former / Qformer」合并，「Llama 3.1 / Llama 31」不合并，`_discriminative_conflict` 的对立词护栏照旧生效。
2. **合成夹具**（两个后端各跑一遍）：包含一个孤岛错文件、一对重复、一个名字破碎的来源、一组 squash 同名、一批孤立对象。断言两个后端的问题行逐字相同（parity）。真实库的内容是用户数据，不进仓库。
3. **守卫**：
   - 计算不在写事务里（`write_depth` 语义守卫覆盖新增的读方法）；
   - `findings` 与板块同事务发布，做移动变异时守卫要报红；
   - 隐藏来源的标题和名字不进 payload，包括 canonical 名来自 knowhow 对象的情形；
   - 账本缺 `findings` 时，补账本路径能自愈，且读侧报灰色「升级后还没生成」而不是红色；
   - 合并规则版本不一致时，S4 的按钮可点；
   - 补账本路径上 `findings` 的合并世代不为 `null`。
4. **本机真值回归**（手动执行，结果贴进 PR）：
   - 在 `nb-b37185f4ae` 上：F1 是那 12 个来源，F2 是那 8 对，F4 窄的一半是 14 组，F5 是 1,830 个；

下面保留拍板前的原文，作为这些裁决的依据。

**① 修订原设计的边界条款。**

本规格与下面几处冲突：

- 原设计 §3.3 末尾：「本视图的职责到如实标注为止……不做折叠/置灰/催促整理这类替读者做判断的产品行为」。`kg_analysis.py` 模块 docstring 的「边界」段重复了这一句（「不折叠、不置灰、不催促整理」）。
- 原设计 §二「明确不做：治理动作」，以及产品/API 参考里的「面板仍不执行删除／隔离治理」。

本规格逐条撞上这些话：问题清单在替读者做判断；按钮会调起删除；「诊断数据」区默认折叠；S4 会把「更新分析」置灰。建议改为：

> 本视图给出带证据的问题与建议：判据确定、可解释、可复核，每条问题都附上判据用到的数字，并可标为正常；不出单一总分。处置不由视图执行——视图只把用户带到既有入口，删除、重新解析、合并确认、补上关联都走既有确认框与后端权限。原始统计默认收起但随时可展开；动作按钮只在按下去不会有任何变化时置灰，并在旁边写明原因。逐指标的口径与新鲜度标注要求不变。

**② S1（种子归一）与 S2（板块稳定性）做不做，是否合并成一次重排。**

建议：两项都做，同一批交付，让已部署库只重排一次；S2 选方案 C，即热启动 Leiden，冷启动按分量 + canonical id 序，外加板块 id 续用。

代价：

- 每个已部署库要重新合并一次，全部板块换一次；
- 推翻原设计 §3.32 的「逐字不变」；
- S1 要迁移已存合并决定的 seed，包括没有 seed、按 canonical id 回退的旧行；用户拒绝过、却会变成同 seed 的那几对要特殊处理；
- 最小种子含空格的合并组，canonical id 会一次性变掉，要核实持久化内容里有没有存 `K-` id。

S1 只去掉原文里的空白、连字符、下划线，点号、括号造成的差别（「Llama 3.1 / Llama 31」）仍留给人确认（§4.4）。如果不做 S1，窄的那 14 组改走 F4 的人工确认。

**③ 阈值先在生产库只读量分布，再定。**

建议：是。初值只在一个 84 个来源的本机库上标定过，F3 在本机根本没有正样本。我会准备一份只读演练脚本，交给生产侧执行（`default_transaction_read_only=on`，错峰运行）。量以下各项：

- F1 的 `shared_share` / `giant_share` 分布；
- F2 的候选对数与 J 分布；
- 每个概念出现在几个来源里的分布，用来定「通用概念」的界——4.9 万个来源上，30 可能太小；
- F3 各子信号的分布；
- F4 窄、宽两半各有多少组；
- F5 的数量，以及补上关联的历史；
- S1 之后会变成同 seed 的已拒绝对数；
- 新增计算的耗时与 RSS。

量完回来定阈值，再开工 P1。

**④ 豁免（标为正常）是否持久化。**

- **A 后端持久化**（建议）：存进 `kg_analysis_marks`。跨设备生效，所有成员看到同一份；标为正常需要图谱写权限；要随迁移，并纳入分享与同步的口径。

无论选哪个，§4.5 的「补上关联已尝试」标记都要存在后端。
