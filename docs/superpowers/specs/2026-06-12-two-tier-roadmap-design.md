# 两层知识库场景 Roadmap 设计（P0–P3）

日期：2026-06-12
状态：已与用户对齐排序与首个动工项（P0 + P0.5 并行）

## 1. 场景假设（来自用户，作为后续所有设计的基准）

- **底层知识库（base）**：垂直领域权威库（如模拟电路的全部教材、论文）。由**专家委员会**维护，整体质量很高；领域内所有人可访问。偏**一次性构建**，建成后以检索为主，**极少量新增且需强人工审核**。用途：为问答提供权威 grounding，避免模型幻觉。
- **顶层知识库（personal）**：个人自建、与具体场景强相关的个性化库（芯片设计经验文档等）。
- **冲突仲裁**：顶层与底层信息相悖时，**以底层为准**。
- **晋升机制**：个人知识要进入底层库范畴，必须经过评审。
- **最难场景**：严格推理。

## 2. 现状 review 结论（2026-06-12）

架构方向与场景假设高度吻合，骨架已落地且有 40+ 专项测试：

| 场景要素 | 现状 | 成熟度 |
|---|---|---|
| 两层 tier | notebook 级 `tier`（base/personal）；`federated_retrieve` 跨 base ∪ 当前 personal；排序 base×1.20（不污染 [0,1] relevance/tau） | ✅ |
| 新增强审核 | base 库 strong-review gate：抽取入库落 `reviewed`，curator 签核前不进检索 | ✅ 机制在 |
| 晋升评审 | propose→approve/reject，批准时 seed 去重+证据合并入库 | ✅ 机制在，无权限检查 |
| 冲突以 base 为准 | fast 模式：prompt 软约束；graph 模式：边级 `base_override` 硬校验 | ⚠️ 默认路径是软的 |
| 严格推理 | `mode="graph"`（opt-in 实验性）：rustworkx 有界 BFS + LLM 投票边校验 + `chain_trust`=最弱环 | ⚠️ 骨架 |
| 防幻觉 | evidence-first 逐句 `[k_i]` 引用、refine 自校验、L4 拒答评测题 | ✅ 设计主轴 |

四个关键差距：

1. **严格推理仍是实验骨架**：Formula 仅文本无结构；`contrasts_with` 边未特殊处理、`conflict` 状态无自动赋值逻辑；无推理专项评测。
2. **委员会治理缺失**：零鉴权、单用户 `user-local` 硬编码兼任 curator，晋升审批无角色检查。多用户 Phase B/C/D spec 已有但按"分享协作"设计，需按"委员会角色"重校准。
3. **规模未验证**：现验证停留在数本教材级；目标底层库（≈50 教材+2000 论文）约 80–120 万对象、~4 GB 向量矩阵，超出当前每 notebook 内存矩阵架构。
4. **冲突仲裁默认软约束**：fast（默认）路径无 claim 级矛盾检测，base 优先靠 LLM 自觉。

数据事实（主库实测）：

- 边分布：about 27,689 / supports 6,068 / derived_from 4,160 / depends_on 791 / contrasts_with 556。
- 推理边连通性：formula 71.1% 在推理子图内；`derived_from` 两跳链 2,054 条、三类推理边两跳链 4,433 条。**推导链路线在数据上可行，瓶颈是链的质量与完备性，不是有无链。**
- 已知质量债（docs/kg-denoise-effect-analysis.md）：0.90 自动合并阈值误并真概念（drain/source/gate）；claim 膨胀 +48% 无去重；1,117 个概念未入簇；Gray/RF 的 doc_type 误标致习题入库。
- **现库 3 个 notebook 全为 personal——两层机制从未在真实数据上运转过。**

## 3. 已确认的三个关键决策

1. **严格推理 = 推导链严格**（选项 A）：答案沿教材级公式/定理推导链走通，每跳有出处、链上无断环。走**图+文本推理**路线，**不引入符号/数值计算引擎**。
2. **断链行为 = 标记推断桥**：KG 中链走不通时允许 LLM 补缺失跳，但补桥跳显式标记 `[推断]` 并对 chain_trust 施加惩罚；断链点记入**知识缺口队列**，作为委员会"少量新增+强审核"的工单入口。
3. **评测 = 双轨**：从已抽 KG 推导链**反向半自动出题**建 30–50 题回归集（防改动退化，几乎零专家成本）；真实设计/审查难题逐步积累为**硬核集**（测真实能力）。

## 4. Roadmap

```
P0 质量收口 ──┐
              ├──→ P1 严格推理可用化（评测依赖库质量）──→ P3 规模化
P0.5 base演练 ─┘
P2 委员会治理（代码区域独立，可与 P1 并行）
```

### P0 — 底层库构建质量收口（首个动工项之一）

理由：底层库"一次性构建、质量极高"，构建前不清质量债，返工成本随库规模线性放大。

| 事项 | 内容 | 验收 |
|---|---|---|
| 过度合并修复 | 自动合并阈值 0.90→0.94+；**所有**自动合并候选必须过 LLM 预审或可单测护栏；`_discriminative_conflict` 对立组扩充（drain/source/gate 类） | A/B 对比：已知误并案例清零；簇抽检 |
| Claim 去重去噪 | 先诊断 +48% 膨胀根因（gleaning 二遍？无跨窗去重？），再修：候选手段为 seed_claim 跨窗去重 + probes 近重复探针闭环 | claim 总量回归合理区间；probes claim 降质指标收敛 |
| 聚簇陈旧修复 | 重跑 rebuild_unified_kg，1,117 个未入簇概念归位 | 入簇率达标 |
| doc_type 修正重抽 | Gray/RF 改 textbook 重抽（跳习题/索引/参考文献），用现成 `scripts/denoise_reextract_nb.py` | 习题/索引噪声清零（denoise 报告同款指标） |

### P0.5 — 首个真实 base 库演练（首个动工项之二，与 P0 并行）

成本半天级，把两层机制从测试态变运行态，产出**真实问题清单**校准 P0/P1/P2 范围：

1. 现有模拟电路教材 notebook 标 `base`（`POST /notebooks/{id}/tier`）。
2. 演练清单：
   - 强审门：向 base 新增一篇文档 → 确认落 `reviewed` 不进检索 → curator 批后进入。
   - 联合检索：从 personal notebook 问答 → 确认 base 命中带 tier 标、权重生效、引用 UI 显示 base 标记。
   - 晋升：personal 一条知识 propose→approve → 确认去重入库。
   - 冲突 baseline：构造一条与 base 相悖的 personal claim → 记录 fast/graph 两模式实际表现（P1 矛盾检测的对照基线）。
   - 推导问答：graph 模式跑若干推导类问题 → 记录断链实例（P1 断链桥的真实案例输入）。
3. 产出：演练报告落 `docs/`（问题清单 + 断链/冲突实例）。

### P1 — 严格推理可用化

| 事项 | 内容 |
|---|---|
| 断链推断桥 | graph 模式 LLM 补缺失跳 → 显式 `[推断]` 标记 + chain_trust 惩罚因子；答案中"有据跳/推断跳"视觉区分 |
| 知识缺口队列 | 断链点持久化（缺失边、上下文、出现频次），审核工作流形态复用晋升队列 |
| 矛盾检测硬化 | `contrasts_with` 边推理特殊处理；base vs personal 的 claim 级冲突程序化识别，**默认 fast 路径也生效**——冲突仲裁从 prompt 软约束变硬约束 |
| 评测双轨落地 | 反向出题工具（从 derived_from 链生成回归集 30–50 题）+ 硬核集格式与积累流程 |
| graph 模式转正 | 从 opt-in 实验提为推导类问题一等路径（自动路由或显式入口，spec 时定） |

### P2 — 委员会治理

解冻多用户 Phase B spec 并重校准为**角色模型**：reader（全员只读 base）/ contributor（可提晋升）/ committee（审批+维护 base）。晋升、边审核、缺口处理全部权限化；增加审计日志。验收：多角色 E2E。

### P3 — 规模化

百万对象级压测 → 据结果决定 sqlite-vec / pgvector 与 base 库共享部署形态。前置条件：存储解耦 P0（已完成，PR#24）。在真实全量构建启动前完成即可。

## 5. 明确不做（YAGNI）

- 不引入符号/数值计算引擎（决策 1 已排除；若未来出现"计算严格"需求另起 spec）。
- 不迁移 Neo4j / llm-graph-builder（既有存储决策维持）。
- 不在 P0–P1 阶段做 BM25/FTS5、websocket 协作等基础设施级增量。
- tier 维持两级（base/personal），不引入多级层次。

## 6. 后续流程

P0 + P0.5 并行动工：各自走 writing-plans 出实施计划（P0.5 为演练 checklist 性质，计划轻量）。P1 在 P0.5 演练报告产出后细化 spec。
