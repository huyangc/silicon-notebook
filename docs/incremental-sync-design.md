# 笔记本内容跨环境增量同步设计

状态：设计定稿，分四个 PR 交付；本文随每个 PR 更新「交付进度」一节。
数据表的整体组织见 `architecture.md` §2.1.1。

## 1. 目标与非目标

目标：源环境按天导出笔记本内容的增量，目标环境幂等引入，最终整个系统具备
「增量导出、迁移、引入」的能力。

约束（用户裁决，2026-09-22）：

- 两个环境的 embedding 模型与维度相同，向量可以原样搬运。
- 统一认证服务是两套，但 silicon-notebook 的用户是同一批人。
- 同步是**单向**的：源环境写、目标环境读；目标环境对同步来的笔记本只做交互。
- 只同步笔记本本体、材料、向量、KG、Knowhow 表、记忆；用户与笔记本实时交互产生的
  数据（问答、报告、反馈、全局问答、活动留痕、许愿墙）不同步。

非目标：双向同步、冲突合并、跨环境问答历史迁移、目标端反向回写。

## 2. 现状摸底要点

以下事实决定了方案形态，改动前先核对它们仍然成立。

- 业务表主键全是 `前缀 + 完整 uuid4 hex` 文本（`repository_facade._new_id`），两端独立写入
  不会撞键。
- notebook 级的表带 `notebook_id`，约三分之一的子表（source_elements、knowhow 列/行/格、
  memory 修订/来源/向量等）经父表归属，切片时要顺着父表走；读/管/写三种权限的唯一定义点是
  `repositories/*/access_sql.py`。
- 97 张业务表里 52 张没有 `updated_at`、15 张连 `created_at` 都没有；正常运行中三十多张表会
  硬删行。**按时间戳挑新增行不能覆盖更新与删除**，必须有变更捕获。
- KG 全量重建走 `delete_notebook_graph_rows` 整体清空后用新 id 重插；`unified_kg_state.kg_reset_epoch`
  每次清空自增，是「整体替换」的判据。
- 七张表有 `ordinal bigint GENERATED BY DEFAULT AS IDENTITY`（`POSTGRES_ROWID_ORDINAL_TABLES`），
  是环境本地的分页游标，**不导出**，目标端重新分配。
- 外部认证首次登录时用户 id 现场生成为 `user-<随机 hex>`，email 是
  `<id>@users.silicon-notebook.local` 占位。两端同一个人的 id 与 email 都不同，
  **只有 username 可作映射键**。
- `notebook_sharing.copy_notebook` 已定义「笔记本内容闭包」：按固定顺序分块复制 29 张表与
  `storage/notebooks/<id>/` 目录，失败只补偿目标侧。它是导入器相位契约的底稿。
- `app.migration.shadow` 已有 SQLite 侧的触发器变更捕获（`capture.py`）与 105 张表的复制
  清单（`manifest.py`：复制键、拷贝顺序、blob/path 列、表分类）。PG 侧变更捕获照它移植。
- `knowledge_object_sources`、`community_members` 与两张 kg 暂存表没有主键，做不了幂等
  upsert；global_ask 两张表与 `ask_jobs.asked_at` 的时间戳是 TEXT。
- FTS 与 trgm 都是表上的 GIN 索引，随行插入自动维护，没有独立的重建步骤。
- 文件不在库里：上传件与附件在 `storage/notebooks/<notebook_id>/`，`kg_index`/`kg_viz`/
  `kg_index_partitions` 是从 KG 行派生的工件。

## 3. 数据分层与表清单

清单以 `backend/app/migration/sync/manifest.py` 为唯一真源，守卫测试要求它对
`POSTGRES_BUSINESS_TABLES` 全覆盖：新增业务表没有分类就响亮失败。每张表一条
`TableSyncSpec`，字段含义：

- `mapped_columns`：引用用户或组 id 的列，每列标注映射种类 USER（按 username 映射）、
  GROUP（组按 name 匹配，匹配不到则创建）或 PRINCIPAL（只用于 notebook_grants.principal_id，
  按行内 principal_type 选表，everyone 不映射）。
- `severed_columns`：引用不同步层表的列，导入时置空。当前是 memory_items.agent_profile_id、
  sources.agent_profile_id、knowledge_objects.source_candidate_id。memory_items.source_answer_id
  刻意保留为文本指针（§11）。
- `target_owned_columns`：对已存在行不覆盖的列（§5）。
- `seed_only`：只在目标端首次创建该笔记本或组时写入，之后不更新也不删除目标端已有行。
  当前是 notebook_members、notebook_grants、groups、group_members。

`synced_tables()` 按 shadow manifest 的 `copy_rank` 给出导入顺序，守卫测试用 PG 迁移里的
外键边证明父表先于子表；声明的列名由建临时 SQLite 库做 PRAGMA 校验。下面是分类原则与
当前归属；表名以 manifest 为准。

### 3.1 同步层（SYNCED）

源端变更捕获、导出包、目标端 upsert 都只作用于这一层与 §3.2。带用户或组引用列的表
（notebooks、sources、knowhow_tables 等）归 §3.2，此处只列无引用的表。

| Knowhow | knowhow_columns、knowhow_rows、knowhow_cells |
| 记忆 | memory_provenance |

### 3.2 边界层（SYNCED_WITH_MAPPING）

同步，但行内含用户或组引用，导入时经 §4 的映射改写；映射不到的行按表内规则处理。

| 表 | 映射列 | 映射不到时 |
| --- | --- | --- |
| notebooks | created_by | 硬失败，整个笔记本不导入 |
| notebook_members | user_id | 跳过该行并记日志 |
| notebook_grants | principal_id（PRINCIPAL）、created_by | principal 映射不到跳过该行并记日志，everyone 不需要映射；created_by 映射不到置为导入执行者 |
| groups | created_by、owner_id、invite_created_by | 组按 name 匹配已有组，匹配不到则创建；owner_id 映射不到取该组目标端 admin 成员，仍无则置为导入执行者；invite_created_by 置空 |
| group_members | group_id（GROUP）、user_id、added_by | 成员映射不到跳过；added_by 置为导入执行者 |
| notebook_bases、notebook_object_schemas、notebook_assets、knowhow_tables、knowhow_milestones | created_by | 映射不到置为导入执行者 |
| knowhow_cell_code | updated_by | 映射不到置为导入执行者 |
| sources | uploaded_by | 映射不到置空并记日志（0045 之前的行本来就为空） |
| knowhow_changes | actor | 映射不到置为导入执行者 |
| memory_items | created_by、confirmed_by | created_by 映射不到硬失败；confirmed_by 映射不到置空并记日志 |
| memory_revisions | changed_by | 映射不到置为导入执行者 |

knowhow_changes 与 knowhow_milestones 是编辑历史，归本层，可随开关关闭只同步当前态。
`knowledge_objects.owner` 是治理面板里可编辑的自由文本标签，不是用户 id，不映射。
`object_schemas` 文档最初未点名，按内容归属归 SYNCED：notebook_id 非空的行是笔记本内容，
builtin 行幂等 upsert 后与目标端一致。

## 4. 身份映射

- 映射键是 `users.username`。导出包携带源端用户表的投影 `(id, username, display_name, role)`
  仅供映射，不写入目标端 users。
- 导入时先构造 `source_user_id → target_user_id`：目标端按 username 精确匹配；匹配不到时，
  若 `--create-missing-users` 打开则按源端投影建一个无凭据的本地用户（外部认证首次登录时
  由现有 `external_identities` 绑定逻辑认领），否则按 §3.2 表内规则处理。
- 组按 `groups.name` 匹配，匹配不到则创建。
- 映射结果写进导入报告，每条「跳过」都带表名、行主键与原因。

## 5. 目标端写入围栏

同步来的笔记本在目标端是**镜像**：任何会改变同步层内容的操作都被拒绝，否则下一次同步会
覆盖它；交互类操作放行。

- `notebooks.sync_origin TEXT NOT NULL DEFAULT ''`：非空表示镜像，值是源环境标识。
  SQLite 与 PostgreSQL 成对迁移，`RUNNING_SCHEMA_PAIR`、shadow manifest、
  `repository_v9` fixture 同 PR 更新。
- 围栏叠在 `backend/app/api/deps.py` 的能力守卫之上：`_CAPABILITY_LEVELS` 旁多一张
  `_CAPABILITY_MIRROR_FENCE`，键集合相同。命中「挡」的能力时，守卫先按级别判定（未授权
  仍 404，不泄露存在性），再查 `notebook_sync_origin`，非空返回 `409`，`detail` 为
  `{"code": "notebook_mirrored", "sync_origin": "<值>"}`。它不改 `access_sql.py` 的读/管/写
  谓词：写权仍然是 owner-only，围栏在其上再收窄。
- 为了让「同一能力名下混着内容写与授权写」的端点能分开处置，拆出两个新能力名，级别不变：
  `notebook:grant`（admin）接管授权边端点，`notebook:manage` 只剩 `PATCH /notebooks/{id}`
  与 tier 切换；`notebook:mount`（owner）接管挂载配置端点，`notebook:configure` 只剩链接分享。
- 围栏只挡非安全方法：GET/HEAD/OPTIONS 即使挂在「挡」的能力下也不查 sync_origin，因为
  它们不会改写同步层内容（挂载候选、挂载计数、scale index 状态、合并审阅作业这些只读投影
  在镜像上必须可读）。
- 挡：sources:write、kg:write、knowhow:write、knowledge:write、catalog:write、notebook:manage、
  notebook:mount、notebook:delete（镜像只能由导入器退役）。走 `notebook_capability_allowed`
  的体内自查写路径、`user_or_agent_scope` 的写分支（Knowhow 格子代码的 Agent HTTP 端点）与
  MCP/Agent 面的内容写工具接同一围栏。
- 放行：notebook:grant、notebook:configure、scale_index:write（kg_index/kg_viz 是目标端自有的
  派生产物，§6 要求目标端重建，重建与取消必须在镜像上可用）、reports:write、
  agent_profile:write，以及问答、
  报告、反馈、全局问答、记忆候选的创建与确认（目标端用户自己的记忆是交互数据，id 不会与
  源端相撞，两边共存）。记忆是两端都写的唯一同步表：源端产生的记忆行以源端为准，目标端
  对它的确认、修改会在下一次同步被覆盖，删除会被重新插入；目标端自己产生的记忆行不在
  源端变更日志里，不受影响。复制笔记本的产物是本地库，`sync_origin` 写成空。
- 目标端自有列：manifest 的 `target_owned_columns` 登记导入时对已存在行不覆盖的列，
  notebooks 为 status、is_shared、share_token、sync_origin。授权边表只在首次创建笔记本时
  写入源端授权，之后不覆盖。
- 前端对镜像笔记本隐藏或禁用上述入口，并在来源面板顶部标注「镜像自 <sync_origin>」；
  按钮反馈规则遵循 `AGENTS.md` Interactive feedback。
- 导入器自身绕过围栏：它走 repository 层，不经过服务层谓词。其它运维 CLI（batch_ingest
  等）同样不经围栏，在镜像上批量灌料是否合法由运维流程约束，不由代码挡。
- 围栏与写事务之间有一个窗口：守卫读到 sync_origin 为空之后、写入落库之前，导入器把该
  笔记本标成镜像，这次写入会在下一次同步被覆盖。与 `deps.py` 里既有的 TOCTOU 裁决同口径
  （内容写属普通竞态，不做事务内复检），知情接受。

## 6. KG 与向量

- 模型相同，五张向量表按行原样搬运（bytea）。目标端 `EMBED_RUNTIME_DIM` 必须与源端一致，
  导入前置检查读两端配置并比对，不一致硬失败。
- KG 按笔记本以 `(kg_reset_epoch, kg_mutation_seq)` 做版本：epoch 变了，导入对该笔记本执行
  「整体替换」（先按 `delete_notebook_graph_rows` 的表集清空，再整批插入）；epoch 没变，
  按变更日志增量 upsert/删除。`unified_kg_state` 行原样搬运，目标端进程内 memo 的 key 折进
  了 seq/epoch，会自动失效。
- 人工审核字段（knowledge_objects 的 status/owner/last_reviewed）随行同步；目标端不允许
  改（§5）。
- `kg_index`/`kg_viz`/`kg_index_partitions` 不拷贝，目标端按现有 scale build 流程重建；
  导入完成后对涉及的大库排队一次重建。

## 7. 源端变更捕获

- 新表 `sync_change_log(seq bigint identity PK, table_name, key_json jsonb, operation,
  notebook_id, changed_at timestamptz)`，只登记复制键，不复制载荷（与 shadow capture 同理）。
- 对同步层与边界层的每张表挂 AFTER INSERT/UPDATE/DELETE 触发器，与业务写同事务。触发器
  由迁移创建；manifest 是触发器集合的唯一来源，守卫测试比对库内触发器与 manifest。
- `notebook_id` 从行本身取；没有该列的表（source_elements、knowhow 列/行/格、memory 修订/
  来源/向量等，约占同步层三分之一）在触发器里经父表查出，父子对应关系登记在 manifest。
  四张无主键表先补复合主键，才能进 manifest。
- 日志按 `(table_name, key_json)` 在导出时压缩：同一键多次变更只保留最终态；KG 整体替换
  时按笔记本折叠为一条 `kg_epoch` 事件。
- 保留策略：导出成功后记录 `exported_through_seq`，早于它 N 天的日志由运维命令清理。

## 8. 导出包与导入相位

导出包是一个目录：

```
sync-<source_env>-<from_seq>-<to_seq>/
  manifest.json      # 源环境标识、schema pair、seq 区间、表清单、行数、EMBED_RUNTIME_DIM
  users.jsonl        # §4 的用户投影
  rows/<table>.jsonl # 按 manifest 拷贝顺序；ordinal 列不导；bytea 走 base64
  deletes.jsonl      # (table, key_json) 列表
  kg_epochs.jsonl    # 需要整体替换的 (notebook_id, epoch)
  files/notebooks/<notebook_id>/...   # 只含本次新增或变更的文件
  checksums.json     # 每个文件与每张表的 sha256
```

全量导出是 `from_seq = 0` 的特例，行来自表扫描而不是日志。

导入相位（借 `copy_notebook` 的相位契约）：

1. 预检：schema pair 相等、`EMBED_RUNTIME_DIM` 相等、包校验和通过、源环境标识与已有
   镜像一致、目标端没有同名非镜像笔记本。
2. 身份映射（§4），产出映射表与跳过清单。
3. 文件：先落到 `storage/notebooks/<id>.sync-tmp/`，校验后原子 rename。
4. 行：对 `kg_epochs` 里的笔记本先整体清空 KG 层；再按拷贝顺序 `INSERT … ON CONFLICT (pk)
   DO UPDATE`；最后重放 `deletes`。每张表一个事务，进度写进 `sync_import_progress`，可断点续跑。
5. 收尾：把涉及的笔记本 `sync_origin` 置为源环境标识；对大库排队 scale 重建；写导入报告。

## 9. 验收与对账

- 逐表行数与 `checksums.json` 比对（复用 `sqlite_to_postgres` 的行校验和思路）。
- 目标端每个镜像笔记本记录 `sync_applied_through_seq`；运维命令能列出落后的笔记本。
- 导入报告以 JSON 落盘并在 CLI 打印摘要：处理的表、行数、跳过与原因、映射结果。
