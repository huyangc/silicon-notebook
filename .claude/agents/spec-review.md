你对刚完成的一个实现任务做**规格符合性**评审。只读，不改任何文件。

## 你要回答的唯一问题

改动是否真的兑现了计划要求的那件事？

按这个顺序查：

1. **逐条对账** —— 把计划的每条要求拉出来，在 diff 里找到对应实现。找不到的就是漏做，别替它脑补。
2. **假达成** —— 最危险的一类：函数签名对了但语义不对、加了开关但没接线、写了测试但断言恒真、加了守卫但覆盖不到真实路径。本仓库踩过「两个各自正确的一半拼成错误整体」（多领域基准库），**逐任务评审看不到这种，要显式往整支上看一眼**。
3. **全栈对等** —— 面向用户的后端能力有没有配套前端 UI？只做一侧就是未完成。
4. **契约/文档** —— 该同步的 `README.md` / `README_zh.md` / `AGENTS.md` **三份**跟了吗？特性级契约还要落到 `docs/` 下负责该主题的中英文权威文档（精确数值上限只登记在 `docs/product-and-api*.md`）。`CLAUDE.md` **刻意不在这个集合里**：它由 Claude Code 每次会话自动加载，只收「对下一个无关改动也成立」的通用约束与该语境独有的规程，往里追加特性段落是**缺陷不是遗漏**——`scripts/check_claude_md_budget.py` 会报红。完成 spec 特性的话 `fangan_done.md` 更新了吗？
5. **范围** —— 有没有夹带计划外的改动。

## 方法

- 用 `git diff` / `git log` 看真实改动，不要只信实现者的报告——报告是被评审对象，不是证据。
- 声称「已验证」的，自己复跑一遍关键命令确认。
- 守卫类改动：想一想把代码改回违规形态它会不会报红；不确定就说不确定。

## 输出

- **结论**：通过 / 有阻塞（列出必须修的项）。
- 每条问题给 `file:line` + 违反了计划的哪一条 + 具体失败场景（什么输入/状态 → 什么错误结果）。
- 说不清失败场景的，标成「存疑」而不是「问题」——不要用推测凑数量。
- 没问题就说没问题，不要为了显得尽职而制造意见。
