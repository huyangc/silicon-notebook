# 更新说明(release-notes)

这里的每个 `*.md` 是一条**写给普通用户看**的更新说明。打包时 `scripts/build_release_manifest.py`
把它们收进 `release-manifest.json`；用户升级后首次打开页面，会看到自己上次看过的版本之后新增的说明。

## 何时添加

- 改动**用户能感知**（新功能、行为变化、入口位置变化、明显的体验修复）就加一条。
- 纯内部改动（重构、测试、文档、性能且无可见差别）不加。
- 一个改动一个文件；不要把几件事塞进同一条。

- 一个特性分多个 PR 交付时，只在**让用户真正用得上**的那个 PR 里加；前面铺路的 PR 不加。
- 只有管理员能看到的变化也算用户可感知；正文开头写明「管理员：」。

## 怎么写

- 中文，一两句话，说清「现在可以做什么 / 有什么不同」，别写实现细节。
- 读者是普通用户：用 [`docs/ui-vocabulary.md`](../docs/ui-vocabulary.md) 的界面词，不出现内部术语
  （`scripts/check_ui_vocabulary.py` 会扫描本目录并在违规时报红；它按行检查含中文的行，纯英文行不检查，所以请用中文写）。
- 正文支持 markdown（加粗、列表、站内链接）；保持简短。

## 给 agent 的写作要求

本仓库的 PR 大多由 agent 完成，说明也由 agent 起草。这条说明会原样弹给所有用户，所以它面向的
不是评审者，而是**不看代码、不看 PR 的普通用户**。交付前逐条自查：

1. **写用户看到的结果，不写你做了什么。** 用户关心「我现在能做什么、哪里变了」，
   不关心改了哪个模块、为什么这么改。把 PR 标题或提交信息改写一遍，几乎一定是错的。
2. **按界面上真实显示的字写。** 提到按钮、菜单、页面时，用界面上的原文并说清在哪里
   （如「笔记本列表右上角的『已分享』」），先到代码或界面里核对，不要凭印象命名。
3. **只写已经交付且验证过的行为。** 不写计划中、默认关闭、需要管理员另行开启却没说明的能力；
   有前提条件（如需要配置模型服务）就写明前提。不夸大，不用「大幅」「全面」「彻底」之类无法核实的词。
4. **修复写「症状消失」。** 描述用户曾经遇到的现象，如「上传较大的 PDF 时不再卡在『解析中』」，
   不写原因、不写报错原文。
5. **不出现任何开发者痕迹。** 不写 PR/issue 编号、提交哈希、文件名、函数名、接口路径、配置项名、
   英文缩写，也不写 codex、评审、测试、重构、迁移等开发过程词汇。
6. **一两句话，一件事。** 超过三行多半是在解释实现；几件事分开成几个文件。
7. **链接只指向站内页面**（如 `/manual`），不放外部链接、图片或 HTML。
8. **写完跑一遍** `python scripts/check_ui_vocabulary.py`，它只能挡黑名单词，挡不住上面几条，仍要自己读一遍。

示例：

| 不要这样写 | 应该这样写 |
| --- | --- |
| feat(report): add docx export with heading levels (#812) | 报告现在可以导出为 Word 文件，标题层级和引用编号都会保留。 |
| 修复 `global_ask` 流在隐藏页 rAF 不触发导致卡死的问题 | 切到别的标签页再回来时，全局问答不再停在「思考中」。 |
| 重构检索管线，召回率大幅提升 | （纯内部改动，不加说明；若用户确实能感知到，写具体现象，如「按型号搜索时能找到更多相关段落」） |

## 文件名即 id

- 文件名（去掉 `.md`）就是说明的 id，只允许字母、数字、`.`、`_`、`-`，且以字母或数字开头，
  例如 `global-ask-share.md`。不合规的文件名会让打包失败。
- **改名等于一条新说明**（会再次向用户展示）；不要为了整理而改名。
- 正文不能为空。
- 不要修改旧说明来「宣布」新东西——新东西加新文件。修错别字可以，说明的展示顺序不受影响。

## 展示顺序与版本

说明按「把文件加进主线的那个提交」排序（`git rev-list --count --first-parent`），与文件内容无关；
后续编辑不改变它。生成清单需要完整 git 历史，生产包应从 master 构建。
