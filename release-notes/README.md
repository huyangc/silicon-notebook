# 更新说明(release-notes)

这里的每个 `*.md` 是一条**写给普通用户看**的更新说明。离线打包（`scripts/pack.sh`）和在 git 检出上
`npm run start` 时，`scripts/build_release_manifest.py` 会把它们收进 `release-manifest.json`。

用户能在两个地方看到说明：

- **「系统已更新」弹窗**：用户升级后首次打开页面时弹出，只列 `change` 和 `feature` 两级，每条默认只显示标题，
  点开才看正文，最多 5 条。其余的折叠成一行「另有 N 项修复与改进」。没有这两级的说明时不弹窗。
- **「更新记录」页**（账号菜单 →「更新记录」，`/updates`）：列出全部说明，`internal` 默认隐藏，
  勾选「显示后台改进」后才显示。

`audience: admin` 的说明只给管理员看，两处都一样。

## 先问：用户需要知道吗？

判断标准是**用户需要知道，或者需要做点什么**，而不是「理论上能感知」。按下表选级别：

| level | 什么时候用 | 弹窗 |
| --- | --- | --- |
| `change` | 用户原来的用法变了，或需要用户动手（例如旧 Token 要重新签发、入口挪了位置、某类链接会失效） | 弹，排最前 |
| `feature` | 新入口、新能力，用户会主动去用 | 弹 |
| `fix` | 很多人遇到过的明显毛病消失了 | 不单列，只计入「另有 N 项」 |
| `internal` | 权限或隐私边界收紧、后台数据整理、少见的边界情况；用户不需要做任何事，大多数人也遇不到 | 不弹，只进更新记录 |

- 纯内部改动（重构、测试、文档、性能且无可见差别）**不写**，连 `internal` 也不用。
- 拿不准选 `change` 还是 `internal` 时，问自己：用户不看这条，会不会因此困惑或吃亏？不会就是 `internal`。
- 只有管理员能看到或需要操作的变化写 `audience: admin`，正文不用再写「管理员：」。

## 一个特性只写一条

- 一个特性分多个 PR 交付时，**只在让用户真正用得上的那个 PR 里加**，前面铺路的 PR 不加。
- 后续 PR 继续完善**同一个特性**，而说明还没上线时，直接改那个文件，不新增文件。
  说明上线后才有的新变化，才另加新文件。
- 加文件之前先看一眼本目录里有没有讲同一件事的说明。有就合并进去，别让用户先后读到两条互相修正的话。

## 文件格式

```markdown
---
level: change
audience: all
title: 报告可以导出为 Word 文件
---
标题层级和引用编号都会保留。
```

- 文件头的三个键 `level`、`audience`、`title` 都必填；值不加引号。格式不对、键名或取值不合法时，打包会失败。
- **标题**是弹窗里唯一默认显示的内容：一句话说清结果，不超过 30 个字。
- **正文**可以为空；要写就写一两句补充（前提条件、在哪里找到、需要怎么做），不超过 160 个字。
  长度由 `backend/tests/` 里的守卫检查。
- 正文支持 markdown（加粗、列表、站内链接）。

## 给 agent 的写作要求

本仓库的 PR 大多由 agent 完成，说明也由 agent 起草。这条说明会弹给所有用户，所以它面向的
不是评审者，而是**不看代码、不看 PR 的普通用户**。交付前逐条自查：

1. **先过「用户需要知道吗」这一关**，再选级别。大多数权限收紧、边界修正都是 `internal`，甚至不用写。
2. **写用户看到的结果，不写你做了什么。** 用户关心「我现在能做什么、哪里变了」，
   不关心改了哪个模块、为什么这么改。把 PR 标题或提交信息改写一遍，几乎一定是错的。
3. **按界面上真实显示的字写。** 提到按钮、菜单、页面时，用界面上的原文并说清在哪里
   （如「笔记本列表右上角的『已分享』」），先到代码或界面里核对，不要凭印象命名。
4. **只写已经交付且验证过的行为。** 不写计划中、默认关闭、需要管理员另行开启却没说明的能力；
   有前提条件（如需要配置模型服务）就写明前提。不夸大，不用「大幅」「全面」「彻底」之类无法核实的词。
5. **修复写「症状消失」。** 描述用户曾经遇到的现象，如「上传较大的 PDF 时不再卡在『解析中』」，
   不写原因、不写报错原文。
6. **不出现任何开发者痕迹。** 不写 PR/issue 编号、提交哈希、文件名、函数名、接口路径、配置项名、
   英文缩写，也不写 codex、评审、测试、重构、迁移等开发过程词汇。
7. **不列边界条件。** 正文只写大多数人会碰到的情况；「包括…」「也不…」「除非…」这类罗列，多半说明你在解释实现。
8. **链接只指向站内页面**（如 `/manual`），不放外部链接、图片或 HTML。
9. **写完跑一遍** `python scripts/check_ui_vocabulary.py`，它只能挡黑名单词，挡不住上面几条，仍要自己读一遍。

示例：

| 不要这样写 | 应该这样写 |
| --- | --- |
| feat(report): add docx export with heading levels (#812) | `feature`，标题「报告可以导出为 Word 文件」 |
| 修复 `global_ask` 流在隐藏页 rAF 不触发导致卡死的问题 | `fix`，标题「切到别的标签页再回来时，全局问答不再停在『思考中』」 |
| 共享笔记本里知识对象详情不再显示其他成员记忆的定义、步骤、出处和相关节点 | `internal`：用户不需要做任何事，也很少遇到 |
| 重构检索管线，召回率大幅提升 | （纯内部改动，不写；若用户确实能感知到，写具体现象，如 `fix`「按型号搜索时能找到更多相关段落」） |

## 文件名即 id

- 文件名（去掉 `.md`）就是说明的 id，只允许字母、数字、`.`、`_`、`-`，且以字母或数字开头，
  例如 `global-ask-share.md`。不合规的文件名会让打包失败。
- **改名等于一条新说明**，已经看过的用户会再看一次，所以不要为了整理而改名。
- 已上线的说明可以改文件头和正文（例如调整级别、合并重复的说明、精简措辞），
  也可以删掉内容已并入别处的说明。这些都不会让已经看过的用户再看一次。
  但不要借改旧说明来「宣布」新东西：新东西加新文件。

## 展示顺序与版本

说明归属于「把文件加进主线的那个提交」（`git rev-list --count --first-parent`），与文件内容无关，
后续编辑不改变它。用户看过的版本之后加进来的说明才算「新的」。弹窗里 `change` 在 `feature` 前，
同级别新的在前；更新记录页按新到旧排列。生成清单需要完整 git 历史，生产环境应从 master 构建或检出。
