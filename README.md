# silicon-notebook

[中文说明](./README_zh.md)

`silicon-notebook` is a source-grounded knowhow notebook for semiconductor engineering teams. It turns PDF, Markdown, DOCX, PPTX, CSV, XLSX, and legacy binary XLS material into searchable source elements, structured knowledge, cited answers, private Memory, knowhow tables, and deep reports.

Model evidence markers written as either `[k1]` or localized `【k1】` (including comma-separated groups) bind to the same clickable numbered citations in Ask and Deep Report.

The current target is a local real-team beta: FastAPI with a selectable SQLite or PostgreSQL repository backend, plus Next.js on the frontend. The shipped-default SQLite quick start requires no Docker, GPU, database server, or local model server; selecting PostgreSQL requires an accessible PostgreSQL server. OpenAI-compatible chat, embedding, rerank, and MinerU services are optional URL-based integrations; deterministic fallbacks keep the core pipeline usable when they are not configured. The modular-extension foundation now provides a dependency-light `domain` contract layer, a startup-frozen Extension SDK registry, live least-privilege capability decisions, and one shared baseline-preserving retrieval-contributor host for Ask and Report. Selected-source graph and generated-question recall are the first two built-in contributors. The graph lane keeps its original attestation, rollout, scope-drift, independent-budget, baseline-manifest, and whole-lane fail-closed contract. Generated-question remains at its original pre-MMR/fusion candidate boundary: `off` is no-I/O, `shadow` returns the exact baseline, and `on` only appends original chunks after host admission. An unavailable capability disables only its contribution; it never bypasses the shared host or hides output from other contributors. A host with no applicable contribution still returns the exact baseline before any work. Point-specific proposal ports are separate from the core authority reader: built-in proposals revalidate from request memory, while other accepted proposals use one notebook/source-bounded batch read. Private Memory is actor-filtered in SQL before either contribution-authority or generated-question scan limits, including compatibility requests without scope. Non-chain contributions use stable ID order; ProviderChain links use declarative `after`/`before` DAG edges with stable-ID tie breaking, never integer priority. The parser ProviderChain now has a dormant three-link topology and a two-phase probe/admit/materialize contract, but production ingestion remains physically disconnected and uses the legacy dispatcher exclusively until the one-step PR-05 switch. Capability requirements and plugin dependencies remain separate manifest concepts. Modular-architecture PRs require two independent subagent reviews and green CI before squash merge, following the delivery plan under `docs/`.

## Highlights

- Structured source ingestion with element-level evidence, formulas, tables, and retained document images when MinerU is configured; source detail loads a bounded element window and expands on demand instead of rendering an entire large document at once. Formula evidence is typeset in source details and Knowledge Graph source cards, LaTeX stays visible on render failure, and wide display equations scroll inside their owning panel.
- Grounded multi-turn Ask with compact citations, last-activity conversation history (including in-flight first turns that remain reopenable across immediate session switches), and browser-local question/answer timestamps revealed on hover or pinned by click. Citation cards can open the exact source element through the active notebook even when it belongs to a mounted public reference library; paper-title headings additionally identify the original uploaded filename when the two differ, never a MinerU intermediate name. Question time is the browser submission instant; answer time is the authoritative persisted completion instant. Citation cards and anchors can also surface a captioned "本段附图" image panel, visually set apart from the cited text since the model never viewed it, shared by Ask and Deep Report references. Ask supports `chunk`, `reasoning`, and experimental `graph` retrieval modes. Reasoning questions are understood without corpus influence before retrieval; clear intent auto-continues, while direction-changing ambiguity pauses for confirmation and then governs every retrieval stage. Which sources a run may read is decided entirely by the user's source checkboxes — the model never infers a source set from the question wording. Confirmed mandatory-topic seeds beyond the first-round width are executed later within the step budget instead of being discarded, and any still-uncovered directions are disclosed in the trace. Questions that map one named tool's capability onto another get one mandatory topic per named tool, with target-side retrieval pairing the target tool's name with functional wording. The live reasoning trace covers the whole run — from question understanding through answer generation — not just the retrieval stages.
- Reasoning Ask and answer synthesis strictly parse model JSON first, then conservatively repair only complete object-shaped syntax faults such as missing quotes/commas; truncation, unknown fields, type confusion, and rewritten strings remain failures. The Ask NDJSON stream emits content-free idle heartbeats so long model calls survive ordinary reverse-proxy idle timeouts while the detached job keeps its existing disconnect semantics.
- User-selectable Reasoning Ask effort (`overview` / `standard` / `deep` / `thorough` / `exhaustive`) controls bounded ranked-retrieval work. Direct whole-table Knowhow lists and physical row/record counts use cursor enumeration with coverage such as `100/100`; conditional, distinct/type counts (for example “how many kinds”), and grouped requests disclose that exact completeness is unsupported, while safety ceilings and bounded hybrid synthesis are reported as partial rather than “all”. The exact limits are listed in the [Product and API reference](./docs/product-and-api.md#reasoning-effort-and-complete-collection-requests).
- Reasoning Ask can also list, not just rank, the library's own document roster (title, type, stored summary) plus whole-library formula / table / image / code-block collections and concept / claim / formula / procedure knowledge-object collections on request, each carrying a returned/known-total completeness badge and a bounded original-source citation. Rows admitted to answer synthesis receive their own `[k]` binding, so the final answer can prove which listed items it used; a truncated list is clearly marked partial and can keep being listed within the same reasoning run. Result cards keep this status summary visible but start collapsed, so users open item details only when needed. Details in the [Product and API reference](./docs/product-and-api.md#collection-enumeration-tools). At the `exhaustive` effort tier, reasoning Ask can also grow a bounded outline scratchpad across its reflection rounds and, once the outline resolves into two or more sections still carrying evidence, write the answer section by section from it instead of in one pass — aimed at survey-style and multi-topic questions. Stable section ids preserve prior evidence bindings across outline revisions; bindings are limited to candidate keys the model has actually seen, and an eight-key overflow can receive one evidence-only correction only within the normal reasoning-step ceiling (ordinary in-budget outline updates remain free to restructure). Partially or conservatively supported sectioned answers are capped at the existing overview evidence badge rather than mislabeled as having no notebook evidence. When the server already holds a structural reason to expect a structured answer — a document roster this run listed to completion, or several confirmed retrieval directions — one bounded line invites the model to turn it into an outline; the invitation states the fact and says to ignore it when a single pass will do, so the model still decides. Details in the [Product and API reference](./docs/product-and-api.md#outline-scratchpad-and-section-by-section-synthesis).
- Concept / Claim / Formula / Procedure extraction governed by one typed edge contract, historical-edge filtering, a read-only contract audit, unified graph visualization, citation-to-node deep links (including nodes outside the bounded core view), and personal-to-base promotion. Optional bounded cross-element relation completion uses mode-specific persistent source-generation keyset watermarks plus indexed same-source candidates; unfinished pages resume through bounded jobs and after restart, and a mode change atomically publishes the new recoverable cursor before retiring the old one. The feature remains rollout-gated and disabled by default. Concept rebuild and isolated-node relink (「重新合并」/「补上关联」 in the Knowledge Graph view) run as background, per-notebook single-flight jobs sharing one maintenance slot; a click while either is in flight is rejected instead of queued, and the browser polls to refresh the graph automatically once the job completes. Manual merge review treats rejection of a pending candidate as a durable separation between the displayed concept groups and removes it without rebuilding the unchanged graph; confirmations trigger reclustering, while reversing an already confirmed decision remains a graph-changing rebuild case. A rebuild revalidates live decisions in its pending-publication transaction so a concurrent rejection cannot be regenerated. The Graph Analysis panel turns its precomputed statistics into conclusion-first reliability, merge, topic-structure, and source-review signals; editors can generate or refresh those products in place through the same background concept-rebuild workflow, while read-only members retain report access.
- Graph object types use an administrator-managed global baseline with per-notebook customization. Notebook owners can override inherited labels, fields, descriptions, or status and create notebook-only types; removing an override restores inheritance, while read-only members can inspect the effective definition without changing it. Model-suggested types remain review-only until the owner explicitly activates them.
- Notebook-bound, creator-private Memory with explicit preview/confirmation, retained Ask citation provenance (source, location, excerpt, and original-file identity), and scoped external-Agent access over MCP. That surface covers retrieval, Ask, knowhow, citation dereferencing, and — behind separate owner-only scopes — filing, re-parsing, and deleting sources plus triggering builds; an Agent may only delete sources an Agent added, while the knowhow cell-code write is deliberately scope-driven rather than owner-only, so it also works for a read-only member. A newly issued token is shown beside a public machine-readable onboarding link, letting the user hand an Agent the link and token separately so it can configure MCP itself. The Agent surface also reads the notebook's accumulated understanding (`get_notebook_profile`) and appends private, untrusted-marked usage observations (`add_observation`) that only feed the caller's own search notes — reviewable and clearable from the understanding panel's "Agent 记录" section — and each user can set answer-style preferences (language, organization, detail, terminology) from the account menu that shape wording only, never retrieval scope. That document publishes the deployment's endpoint verbatim, notes the `/mcp` → `/mcp/` redirect a direct backend answers, and uses a `${SILICON_NOTEBOOK_AGENT_TOKEN}` Authorization header, which an interpolation-capable client such as Claude Code resolves at connect time instead of storing the credential; clients without that capability persist the literal header and their configuration file must be treated as a credential store. Long-running tools — `ask_notebook` in `reasoning` mode runs for minutes — emit a periodic MCP progress heartbeat over a streaming (SSE) transport, so a client's idle timeout stops abandoning calls the server is still completing; the client's own per-call ceiling still has to be raised on the client side.
- "AI 对这个库的理解" keeps a low-cost, background-consolidated summary of a notebook — what it broadly holds, its recurring topics, known gaps, and, privately per member, retrieval phrasing that has worked and questions the library did not answer — surfaced through a viewable/editable panel and quietly folded into reasoning Ask's and Deep Report's own retrieval prompts, never into the answer itself. A separate, deployment-wide library of closed-vocabulary retrieval tactics ("打法") is distilled offline from finished runs across every notebook and every user, with no notebook or user identity anywhere in it; it only ever affects *how* a run searches, never *what* it may read, and its optional prompt injection is off by default while the deployment accumulates observations. When injection is on, deep-and-above reasoning runs additionally get a model-invoked "回想" (consult) step that pulls tactics the passive block could not fit plus the member's own undelivered search notes, and a deterministic one-line hint when a retrieval channel keeps coming back empty; distillation now also attributes per-action success by intersecting each step's recorded result ids with the answer's actual citation anchors. See [Retrieval strategy experience](./docs/product-and-api.md#retrieval-strategy-experience).
- Opt-in command-catalog extraction for tool manuals: a zero-model cost preview, one background job per source guarded against duplicate starts, the whole document read as bounded segments (nothing dropped, and a segment with no claimable command name costs no model call at all), one model call per parameter batch, and verbatim grounding against the segment's own text — each batch of parameters judged against the batch that was actually asked for, so parameters answered from another batch are dropped and ones that never came back are reported as missing; a command documented without flags has its positional arguments extracted under the same grounding. Entries that fail grounding are kept with their reason, an abnormal rejection rate fails the run with a readable message instead of shipping a near-empty catalog, and confirmed commands land in a knowhow table that is only ever appended to — an existing row is reported as a conflict, never overwritten. Extraction requires the source to be parsed first, and a reparse expires that run's candidates rather than letting them be confirmed into content the document no longer contains. See the [Product and API reference](./docs/product-and-api.md#command-catalog-tool-manuals).
- Free-form knowhow tables with Markdown cells, column- or row-oriented spreadsheet import with actionable validation, bounded batch-reformat review, readable audit actors, content-aware stable columns, reasoning-backed library-wide empty-cell completion suggestions, deterministic projection whose cell knowledge objects enter graph/reasoning retrieval by default, history, milestones, and isolated code attachments with immediate save attribution.
- Intent-first two-stage deep reports with a frozen shared scope/completeness contract, SQL-aggregated bounded "资料基础" and citation-coverage disclosures, optional reviewable comparison frames, research depth additionally scaling the outline stage's evidence-probe width and its sufficiency-verdict model refinement (lower depths probe less, conclude deterministically, and plan faster, with probe progress visible throughout), per-section deep dives seeding the reasoning run with the outline's confirmed retrieval directions instead of replanning them, and, for every multi-section report at any depth, retrieve → report-wide synthesis blueprint → parallel section drafting. Section drafting, report-wide synthesis, and the final editor have separate deployment-configurable output budgets, while process-wide report admission and per-report section fan-out protect the database pool independently of model capacity. Unknown source identities remain separately visible while concentration uses a conservative upper bound. Only single-section reports keep section streaming; meaningful synthesis failures/skips and ledger availability are visible and fail open, while the expected single-section `not_requested` / `0/N` receipt stays quiet. A run with no successful section ends as failed rather than a false completion; failed generation with a retained confirmed outline can be retried in place. The final editor receives a valid bounded cross-section context, audits, and never rewrites the body. Completed reports retain exact browser-local completion timestamps, relative age, and full generation duration; legacy reports never invent missing timing.
- Multi-account ownership, public reference libraries, share links, copy/read-only membership, and group knowledge sharing. Group management is a full collection-level workspace where the unique, transferable group owner manages members, approvals, and which notebooks the group can see; group admins can issue, rotate, and revoke a reusable invitation link, and a signed-in recipient joins as an ordinary member automatically. The previous owner remains a group admin after transfer. The app also supports sign-in-free public links for finished deep reports and Ask conversations, plus administrator controls and a paginated, sortable user-usage table.
- Structured JSONL logs, bounded production diagnostics, offline batch ingestion, replay, migration, and backfill tools. The admin log viewer's default tab is a per-user Activity timeline (asks, sources, and reports merged, keyset-paginated, scope/stream/detail columns); the original per-day LLM-call viewer remains a second, unchanged tab.
- Retrieval candidates retain all producer provenance (semantic, lexical, PPR, KG source, or community); mixed chunk/graph selection can reserve a bounded graph-only seat without increasing the answer budget.
- Frontend production modules live under `frontend/app` and `frontend/features`; tests and test support live under `frontend/tests` and `frontend/test-support`. Ask and Deep Report also share a request-scoped retrieval runtime for embedding reuse, bounded report leaf fan-out, and content-free stage observability.
- KG extraction persists immutable source-generation facts and normalized evidence-element bindings before global fusion. A generation-keyed selected-source snapshot and per-source scale companions read only authorized graph rows, keeping a one/few-source query independent of whole-library graph size. Ask and Deep Report share one quality-gated activation seam: historical evidence `B` finishes first, graph evidence `G` has a separate budget and is appended only after a trusted attestation approves the rollout. Invisible `shadow` is the default; it changes no answer, public response, reasoning trace, or UI. Scope drift, unavailable artifacts, graph failure, or baseline eviction fails closed to `B`. Whole-scope/all-selected requests—including a one-source notebook with its sole source selected—remain on the byte-identical historical path. Existing deployments can run the restartable offline `scripts/prepare_selected_source_graph.py` once to migrate, backfill, audit, and publish current companions for every notebook; only after those checks pass does it atomically enable the four shadow settings in the deployment env file.
- The interface defaults to **auto mode** — upload and ask right away, and generate a Deep Report with one click; the app only asks for clarification when a question is genuinely ambiguous. **Advanced mode**, toggled from the avatar menu, unlocks the full retrieval-effort, research-depth, and source/reference-library scope controls described above. See [Product and API reference](./docs/product-and-api.md#interface-mode-autoadvanced).

## Quick start

### Requirements

- Python 3.13 or newer
- Node.js 20 or newer and npm
- git

A C/C++ toolchain is needed only when pip cannot use prebuilt wheels for packages such as `numpy`, `rustworkx`, or `hnswlib`.

### Install

```bash
git clone <repo-url> silicon-notebook
cd silicon-notebook

python3 -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
python -m pip install --upgrade pip
python -m pip install -r backend/requirements.txt

( cd frontend && npm install )
```

### Configure

```bash
cp .env.example .env
mkdir -p .local
cp model-services.example.toml .local/model-services.toml
```

For model-backed answers and extraction, edit `.local/model-services.toml`, bind workloads to physical services, set each service's `max_concurrency` and optional chat-only fixed `top_p`, and place only the secrets named by `api_key_env` in `.env`. Valid TOML edits are hot-reloaded without restarting the backend.

To run explicitly with deterministic/offline fallbacks, leave this empty in `.env`:

```text
MODEL_SERVICES_CONFIG=
```

`.env.example` is the authoritative list of non-service settings and secret slots. `model-services.example.toml` is the service, binding, and capacity template. See [Deployment and configuration](./docs/deployment-and-configuration.md) for remote access, CORS, model scheduling, authentication, MinerU settings, and upgrade guidance.

Retrieval and model-input ceilings are named contracts rather than call-site
numeric slices. Deployment-owned budgets are listed in `.env.example`; exact
Deep Report rails and API behavior live in the product/API reference.

### Run

```bash
npm run dev
```

Open <http://127.0.0.1:3000>. A fresh database creates the built-in `admin` account; the local default password is `admin`. Binding to a non-loopback address requires a non-default `SILICON_NOTEBOOK_ADMIN_PASSWORD`. Users change their own password from the avatar menu; administrators reset a user's password from the user-usage page (the built-in `admin` password stays environment-derived).

Startup migrates the selected datastore. The default is `DATABASE_URL=sqlite:///.local/silicon_notebook.db`; a provisioned PostgreSQL 16 database may instead use `DATABASE_URL=postgresql://user:password@host:5432/database`.

Production uses one backend worker so the in-process model scheduler remains the deployment-wide capacity boundary:

```bash
npm run start
npm run stop
```

`npm run start` installs backend and locked frontend dependencies, builds in the foreground, launches both services as terminal-independent background processes, and then exits without checking readiness. Logs remain under `.local/logs/`; verify `/api/ready` yourself and use `npm run stop` to stop the services. Prebuilt deployments may set `SKIP_INSTALL=1`.

For a self-contained target with no npm/node or root access, build an offline bundle with `bash scripts/pack.sh` and follow [packaging/DEPLOY.md](./packaging/DEPLOY.md).

### Verify

```bash
curl -s http://127.0.0.1:8000/api/health
bash scripts/check.sh
```

Verification is tiered: G0 runs change-focused tests; G1 `scripts/check.sh` is the edit-time and PR/push offline gate (stable backend, contracts, frontend tests and the typechecking production build) with default 12 backend workers, four frontend test workers per runner, and an Apple Silicon warm target of at most 60 seconds; G2 `scripts/check_extended.sh` adds real-index/performance tests, cold graph/index contracts, and repository-wide semantic scans and runs once daily at 18:17 UTC (02:17 Asia/Shanghai) or manually; G3 `scripts/check_postgres.sh` remains the independent PostgreSQL integration gate. CI also runs `level-1-frontend-node26`, which re-runs the same frontend wrapper on the current Node.js major on G1's triggers, covering the gap between the documented Node ≥ 20 floor and G1's pinned 22. CI lane timings are observational only.

Backend test setup reuses one current empty SQLite schema per pytest worker only for ordinary repository tests and uses a pytest-only fast password hash there. Migration/snapshot contracts and the authentication helper tests retain the real production paths, and every test still receives an independent mutable database file.

Codex-only execution note: run `scripts/check.sh` outside the Codex sandbox on the first attempt because lifecycle tests bind loopback ports and manage subprocesses. GitHub network operations (`git fetch`, `git push`, and `gh auth/repo/pr`) must likewise request outside-sandbox execution directly instead of first failing inside the sandbox; ordinary local read-only Git inspection stays sandboxed.

Database-specific coverage now targets the direct PostgreSQL backend. Retired tests for the SQLite backend implementation, SQLite-to-PostgreSQL import/forward-shadow, and cross-backend parity are no longer part of the active suite.

## Product flow

1. Create a notebook. The app immediately opens an `Untitled notebook`; it does not ask for metadata first.
2. Import source files. The dialog shortens long staged filenames, keeps action-area breathing room, rejects a file above the deployment's per-file size cap before upload, enforces the 20-file request guard, and disables over-quota batches with an actionable reason; drag-drop is handled explicitly, and files skipped at staging time (unsupported type, size, or batch cap) are listed inside the dialog with per-file reasons instead of disappearing silently. The same-origin production proxy derives its whole-request transport envelope from the same backend-issued `SOURCE_UPLOAD_MAX_MB` and fixed batch rail, so Next.js's generic 10 MiB default cannot override the application limit. Parsing then creates structured source elements and searchable chunks.
3. Ask questions immediately through chunk-native retrieval. Build a KG on demand, or enable automatic extraction for every upload. A question is capped at 4,000 characters at submission (`/ask`, `/ask/stream`, `/ask/intent` and the MCP `ask_notebook` tool all refuse a longer one, and the composer blocks submission at the same limit instead of clipping the text) — a shared conversation serves each question verbatim to anonymous readers, so that page is only bounded because submission is. Renaming a conversation is capped the same way at 200 characters, for the same reason: the shared page serves the title verbatim too.
4. Browse and govern extracted knowledge, inspect the full-screen graph, and mount public reference libraries when federation is needed.
5. Save useful answers into private notebook-bound Memory, maintain structured knowhow tables, or generate a deep report.
6. Share a notebook by link: small notebooks are copied; large notebooks are joined read-only. A group admin can instead share it with a whole group (project / department / domain), which puts it in each member's **群组** list partition and lets them mount it. Live collaborative editing is not part of the beta. A shared library's workspace header names where it came from ("只读／可管理 · 来自群组《X》") without ever hiding the library's own name, and when you yourself leave a group, delete one, or revoke a share while an affected library is open, the UI moves you out on the spot; a revocation made by someone else has no push channel and is re-checked when you return to the tab. Deleting a group only withdraws access; the libraries themselves stay with their owners.
7. A finished deep report can additionally be published as a **sign-in-free** read-only page: the owner issues the link and can revoke it at any time. That page carries the body and the citation list (title, location, excerpt) only — no source ids, and it cannot open the original material. The body renders through the same pipeline as the in-app view (formulas, tables, clickable citation numbers), and a number jumps to its excerpt on the same page. The research question is shown whole (creation caps it at 4,000 chars and the composer shows the same guardrail; only a report predating that rail can exceed it, and it is then explicitly marked truncated); citation titles, original filenames, and excerpts stay length-bounded but are explicitly marked "已截断" when a cap bites, rather than losing their tail silently.

A markdown source that references local image files (e.g. exported notes with `![alt](img.png)`) can be prepared beforehand with the standalone `scripts/embed_md_images.py notes.md` helper, which inlines each local image as a base64 data URI so the ingestion pipeline can decode and store it as a source asset without depending on the original file path. The add-source dialog can also do this directly in the browser: drop in a zip archive or a whole folder that keeps a markdown file's images alongside it (the shape a Notion/语雀/HackMD export already has), and it is unpacked, paired by relative path, and inlined client-side before upload, with a persistent receipt for anything skipped. When a blockquote whose first line is the `**图片描述**` marker directly follows an image line, every quoted line in it is folded into that image element as its description and enters retrieval alongside the caption — so an image with no alt caption but a written description is searchable too.

Inside a notebook, the workspace stays two-column: imported sources on the left and **问答** (Ask), **知识库** (Knowledge), **记忆** (Memory), and **深度报告** (Deep Report) in the main area.

The source-import dialog reads a sanitized parser capability registry from the backend and uses it to drive upload validation and the supported-format hints; the routing pipeline itself (self-hosted MinerU, MinerU public cloud, built-in fallback, and their availability) is deliberately not shown to users. Routing remains automatic: a configured self-hosted MinerU path is never silently replaced by the public cloud path, and upload validation uses the same registry projection as the browser.

Each imported source has a retrieval checkbox shared by Ask and new Deep Reports. All visible sources are selected by default; the selection is the hard active-notebook ceiling and the only thing that decides retrieval scope—the model never proposes, narrows, or widens it. Selecting the whole current set (including a one-source notebook) keeps the normal graph/reasoning path and snapshots the current hidden Memory/Knowhow participants, while actually excluding a source activates narrowed-scope safety and excludes those hidden projections. The snapshot freezes source-partitioned candidates and results; visible or hidden participant drift disables unsafe whole-graph channels. Narrowed indexed search applies the source predicate before semantic Top-K and rechecks it after hydration; an older index without the compact source map falls back to bounded source-filtered lexical retrieval until rebuilt or folded. Mounted reference libraries are the second, independent dimension of the same scope: one checkbox per *whole* library, also selected by default, so a question limited to one local document is no longer answered out of a borrowed 84-paper library. The two dimensions never fold together — unchecking a reference library narrows only cross-library retrieval and never disables the current notebook's own graph, PPR or private Memory. Clearing every source makes the local retrieval scope empty; unchecking every reference library makes the library scope empty. With both empty, Ask and new-report creation are refused.

The default-built large-source graph companion uses source-first bounded reads. Its reader verifies partition contents, reuses a single selected source's persisted sparse graph directly, and applies bounded sparse composition only when several sources are selected; it never falls back to a whole-library graph.

Selected-source graph activation is also protected by an offline paired quality gate. It compares baseline and shadow runs under the same frozen model, sampling, corpus, and source bindings; hard isolation or baseline-preservation failures, per-case quality regressions, and cost overruns produce a rejected content-free attestation. Ask and Deep Report share this activation seam: the default invisible `shadow` returns the historical baseline and is observable only through content-free internal events; an attested active rollout may only append source-local graph evidence after that baseline.

Deleting a source immediately shows a deleting state, blocks duplicate clicks, and suppresses stale list responses. The backend locks the source before projection cleanup, uses the source reverse index when available, caps affected-object delete statements at 500 ids, and removes referenced image assets in one database round trip. Historical notebooks do not trigger a whole-notebook reverse-index rebuild inside the request; their keyset-paged database-native fallback may still scan legacy KG rows, so operators should prebuild or repair the index offline with `backfill-source-index` for large libraries. That offline rebuild now persists a notebook-level cursor and counters: every bounded page commits atomically, restarts resume the last committed page, and a KG-generation change fails closed before a fresh rebuild.

Detailed product behavior, retrieval semantics, MCP tools, and endpoint paths are documented in [Product and API reference](./docs/product-and-api.md).

## Architecture at a glance

```text
Browser
  → Next.js frontend
  → FastAPI /api and Streamable HTTP /mcp
  → application services and repository ports
  → SQLite or PostgreSQL + local source/index/log storage

Optional external services
  → OpenAI-compatible chat / embedding / rerank
  → MinerU HTTP, isolated CLI, or cloud fallback
```

- SQLite defaults to `.local/silicon_notebook.db`; PostgreSQL is a direct alternative. Uploaded files and generated artifacts stay under `.local/` for either database.
- The production backend is deliberately single-worker because model queues, breakers, health, and cancellation state are process-local.
- Baseline `chunk` retrieval is active-notebook-only. KG-assisted and reasoning paths may federate through explicitly mounted base notebooks.
- Source-local fact rows are owned by `(notebook, source, extraction generation)` and survive global-object folding; reparse/replacement swaps them in the same transaction as the global KG write. Notebook copies remap the facts, bindings, and terminal ledger together and mint a copy-local completed KG generation, so audit and offline repair never depend on the source notebook's operational run history.
- Text wrapped in **ASCII double quotes** is searched whole and never tokenized: the span enters lexical candidates as one indivisible term, counts as a single unit of keyword coverage (a document scattering those words earns nothing for it), and additionally earns an exact-locate probe. Quoting is a strong preference, not a hard filter. ASCII quotes only, at least 3 characters inside, and more than 4 distinct quoted spans in one text disables the syntax for that text; the ask composer and deep-report input echo the recognised phrases as you type so a constraint that did not take effect never passes silently.
- Lexical retrieval keeps the exact query as a ranking bonus but recalls independent Latin/number terms, overlapping CJK trigrams, and separator-joined identifiers (e.g. `set_db`, `config.yaml`) as whole terms instead of forcing the whole query to be contiguous; SQLite safely quotes FTS5 clauses and PostgreSQL applies the same bounded term union with LIKE metacharacters escaped so an identifier like `set_db` stays literal. Indexed Chunk and KG retrieval use bounded `ANN ∪ FTS` candidates; indexed Relation retrieval adds bounded, direction-balanced relations adjacent to FTS-matched KG endpoints.
- Indexed large-library retrieval keeps post-ANN database hydration bounded by the candidate window and single-flights ANN handle loading across concurrent reasoning subqueries. Chunk scale indexes also persist a compact ANN-row-to-source map so narrowed retrieval filters inside HNSW before Top-K rather than letting excluded rows consume candidate slots. By default, every published scale index, enabled ANN handle, and safely reusable single-index PPR core is loaded behind `/api/ready` before user traffic is admitted; cross-notebook combined graphs remain lazy to avoid multiplying 10M-node graph copies.
- Scale/viz artifacts also persist their stable degree order and by-source edge index, so a bounded graph view reads only the selected nodes' adjacency segments. Multi-library PPR composition builds the ordered combined CSR once while preserving the previous scores and ranking. Heavy and light maintenance jobs use separate fixed worker pools: queued work no longer creates one waiting thread per submission. Conflict governance has independent object and relation admission and refuses an oversized pass in full rather than reporting a truncated scan as complete.
- Scale-index actions distinguish immediate builds from off-peak scheduling. A manual immediate build supersedes an older queued build for the same notebook without dropping later follow-up work; completion events refresh the live notebook status even after foreground polling ends, so historical Ask warnings disappear when the index is published.
- The candidate review queue has been retired; current knowledge governance operates on stored knowledge objects.
- DATABASE_URL selects the formal repository backend through one repository factory. Exactly one active repository backend is selected centrally from `DATABASE_URL`. SQLite and PostgreSQL are both available direct backends; SQLite remains the shipped default.

### SQLite / PostgreSQL switching

Shadow SQLite source-open classification is intentionally narrow: only a non-transient `sqlite3.OperationalError` raised by `open_fresh_live_sqlite` is a source-binding identity failure. Locked, busy, and interrupted opens remain transient whole-batch retries; later SQLite operational errors retain their schema/query classifications.

The application never dual-writes through its normal repository path. `SHADOW_DATABASE_URL`
names only the PostgreSQL target used by the explicit forward-shadow migration CLI; setting it
alone starts nothing and never changes the active backend. Changing `DATABASE_URL` does not copy, migrate, or synchronize existing data.

While `DATABASE_URL` remains SQLite, the operator can run a guarded, one-way
SQLite→PostgreSQL shadow: preflight binds and confirms both database identities, `start-forward`
installs run-scoped capture/guards and copies a consistent 70-table baseline, and one supervised
foreground worker continuously applies the retained SQLite change log. `status` exposes redacted
lag/lease/poison state and `verify --level full` performs a barrier-aware consistency check. The
worker uses an exclusive database-clock lease, retries transient PostgreSQL failures, stops on a
deterministic poison event, and conservatively retains at least seven days and 100,000 events
behind verified progress.

This phase does **not** implement cutover, reverse replication, or automatic `DATABASE_URL`
changes. Keep SQLite active, keep both backups current, and treat PostgreSQL as a read-disabled
shadow until the separately reviewed cutover phase. The complete command sequence and failure
rules are in [Operations](./docs/operations.md).

The separate, dry-run-first `scripts/migrate_sqlite_to_postgres.py` remains the owned
stopped-snapshot importer and local-activation tool. It is not continuous replication; use
`scripts/shadow_sqlite_to_postgres.py` only for the SQLite-active forward shadow described
above, and never run the two workflows against the same target.

Baseline snapshot/COPY additionally requires an owner-only real snapshot directory, qualifies every business statement to the run-bound schema, revalidates enabled live SQLite capture under a short write fence at critical bindings, uses bounded named server cursors and statement timeouts, and validates the complete migration-derived v30 table/column/constraint/operational+GIN-index/extension catalog at start and finalization. Snapshot/fence reads use a dedicated fresh connection to the current SQLite path—not the repository's thread-cached connection—and bind the resolved path plus device/inode before/after open and again before publication/PG commit. The final SQLite fence is acquired only after long PG proof/ANALYZE work and remains held until the PG H0 transaction commits.

- On the shipped SQLite default, search uses SQLite FTS/vector storage. The PostgreSQL backend uses `pg_trgm`/`ILIKE`; float32 vectors remain `bytea`, so pgvector is not installed or required.
- `pg_trgm` must be installed in the `public` schema. Check it without exposing credentials:

  ```sql
  SELECT e.extname, n.nspname
  FROM pg_extension e
  JOIN pg_namespace n ON n.oid = e.extnamespace
  WHERE e.extname = 'pg_trgm';
  ```

  `pg_trgm | public` means the prerequisite is ready. If the query returns no row, the first migration automatically attempts `CREATE EXTENSION pg_trgm`; an existing `pg_trgm` in any other schema fails closed.
- On a large PostgreSQL deployment, inspect and install the notebook-aware lexical GIN indexes with `PYTHONPATH=backend python scripts/build_postgres_retrieval_indexes.py` and the same command plus `--apply`. The online builder uses `CREATE INDEX CONCURRENTLY`, is resumable, and leaves the legacy global indexes in place by default. It changes only candidate pruning, not lexical predicates, scores, limits, or result ordering; see [Operations](./docs/operations.md#postgresql-notebook-aware-lexical-indexes). For the largest notebooks, a GiST `<->` early-stop probe for the knowledge-object name arm activates automatically once its index exists (`POSTGRES_LEXICAL_KNN_ENABLED`, default on; same doc section for the index DDL and the rollback).
- The importer requires an empty UTF-8 PostgreSQL target, reads its URL from `POSTGRES_MIGRATION_URL` (never a URL CLI argument), takes an online SQLite backup-API snapshot including committed WAL state, upgrades only a working copy to the paired schema, streams bounded `COPY`, preserves ordinal values, converts legacy JSON vectors to float32 `bytea`, verifies every table with content checksums, and commits each verified table with a per-table checkpoint so a stopped import (crash, dropped remote connection, reboot) resumes from the last completed table instead of restarting; finalize (ordinal reseed, index rebuild, `ANALYZE`) is idempotent. It explicitly excludes the SQLite-only shadow control/change-log tables and records that exclusion in its receipt. It accepts bounded session bulk-load tuning (`--maintenance-work-mem`, `--max-parallel-index-workers`) for large targets. Its default preview/apply modes do not change `DATABASE_URL` and it never copies `.local/storage`.
- An online import is a rehearsal snapshot only: SQLite writes committed after its snapshot are not synchronized. For a stopped local deployment, the explicit `--activate-env ... --confirm-service-stopped` mode re-snapshots SQLite and rechecks every PostgreSQL table against the credential-free receipt before atomically replacing `.env`; it preserves the former SQLite URL as inert `SHADOW_DATABASE_URL` and writes a restricted rollback copy. The CLI does not stop or restart services. Start with `--workers 1`, then verify `/api/ready`, login, counts, search, representative reads, and one canary write before sending traffic.
- Returning to SQLite cannot replay PostgreSQL-only writes. Lossless rollback therefore requires no post-cutover writes or an externally reconciled and verified migration in both directions.
- `scripts/batch_ingest.py` supports SQLite and PostgreSQL for `ingest`, `kg`, `index`, `all`, `embed`, `metadata`, `question-index`, `reparse`, `backfill-source-index`, `backfill-chunk-elements`, and the explicit offline `backfill-source-facts`. `question-index` is an explicit opt-in that generates independently embedded search questions pointing back to original chunks; it requires the rollout mode plus `chunk_question_generation` and `chunk_embedding` bindings, and it never creates citation evidence. `backfill-chunk-elements` builds the element -> chunk reverse index (`chunk_elements`) so the per-query evidence lookup becomes a bounded point lookup instead of a whole-notebook chunk scan; new writes maintain it transactionally, historical rows are projected only by this explicit offline phase, and notebooks that have not been backfilled keep the legacy path with identical results. The source-fact command creates restartable source-local historical projections without model calls, explicitly separates live facts from historical projections, and preserves incomplete reasons across operational retries; ambiguous provenance remains visibly incomplete, and `scripts/audit_source_facts.py` independently reconciles KG generation/version/count while reporting only counts and bounded source ids. Direct PostgreSQL maintenance is offline-only: stop the API/background writers and pass `--confirm-service-stopped`; the flag is an operator assertion, not a service-stop mechanism. A database-wide advisory lock prevents overlapping PostgreSQL maintenance CLIs. `vectors-to-blob` remains SQLite-only because PostgreSQL vectors are already `bytea`. Every `kg` extraction shape, including `--limit` and `--retry-partial`, uses the same durable notebook job as the page Analyze action; batch final clustering/indexing completes before that job succeeds. The page's continue action retries partial runs safely, and CLI `kg --retry-partial` does the same, retaining the old graph until a non-empty, zero-failed-window replacement commits. For unattended runs, `kg --skip-model-failures` narrows a model outage from the whole task to one source (it returns to the unanalyzed state, so re-running the command retries it) while keeping a backstop: `--max-consecutive-model-failures` consecutive source failures still stop the task (omit it to derive `max(32, 2 × workers)`; an explicit value at or below `--workers` is rejected). The startup availability probe is deliberately not covered — if the service is already down, the run fails fast. It is off by default, warns when enabled, and reports how many sources were skipped.

Exact preview/apply/retry commands, the SQLite↔PostgreSQL selector values, the final cutover checklist, storage handling, and rollback limits are in [Operations](./docs/operations.md#sqlite--postgresql-cutover-and-rollback); the step-by-step execution checklist is the [migration runbook](./docs/postgres-migration-runbook.md) (Chinese, like the other runbooks in `docs/`; this English section remains the complete reference). Deployment settings are in [Deployment and configuration](./docs/deployment-and-configuration.md).

Read-only research, status, and review are exempt. Every change lands through a pull request reviewed by codex, with each round's raw output posted verbatim to the PR; a PR may be merged once that review is non-blocking **and** CI is fully green **and** a review for the PR's remote head commit is visible on the PR itself — review automation that silently never fired looks exactly like one that passed, so local state is not evidence. ## Current boundaries

- SQLite is the shipped default; PostgreSQL 16 is a supported direct backend. The repository includes a verified one-way SQLite→PostgreSQL snapshot importer; it does not provide live synchronization, PostgreSQL→SQLite replay, or MySQL migration.
- No Docker is required or provided as the default first-version workflow.
- Highest-fidelity formulas, images, and complex scanned PDFs require MinerU; `MINERU_MODE=off` uses the local PyMuPDF4LLM layout/Markdown fallback (with pypdf only as a last resort). Remote MinerU HTTP calls retry transient failures twice by default (three total attempts; `MINERU_MAX_RETRIES`). If a cloud URL parse still fails, the backend downloads the PDF and completes through the local fallback; the source UI warns about possible quality loss and offers reparse/delete actions. MinerU handles PDF, DOCX, PPTX, and XLSX/XLSM; each degrades through its own staged local chain — PDF via PyMuPDF4LLM then pypdf, DOCX via mammoth (heading levels, lists and table structure preserved) then python-docx, PPTX via python-pptx (slide tables, chart titles and speaker notes included) then raw slide XML, workbooks via openpyxl. The quality warning covers the lossy fallbacks — PDF, DOCX and PPTX — and not workbooks, whose openpyxl fallback keeps every cell value. A MinerU workbook result is also accepted only after a local row **and cell** coverage check (both dimensions required, since a page-rendering pass often keeps every row while dropping the columns past the page width), so a pass that silently drops rows or columns falls back to openpyxl instead; the same check gates cloud uploads, and embedded images are persisted only once a result is accepted. Formats MinerU cannot parse (Markdown, CSV, text) are always parsed locally and are never uploaded to the mineru.net cloud path. Legacy binary `.xls` (pre-OOXML BIFF) has no MinerU path at all and is always parsed locally via `xlrd`, the format's only pure-Python reader; other legacy binary Office formats (`.doc`, `.ppt`) remain unsupported — save as `.docx`/`.pptx` instead.
- Knowledge extraction and model-backed answers require the relevant workload bindings; offline mode does not synthesize knowledge.
- Graph Ask remains opt-in/experimental; `chunk` is the default.
- Generated-question recall is deployment opt-in and defaults off; `shadow` records content-free comparison counts without changing results, while only explicit `on` may supplement a low-recall chunk result with original chunks.
- In answer, report, and Memory Markdown a single `~` is a literal (ranges and approximations such as `7~5nm` or `~3GHz` render as typed); strikethrough must be written as GFM's `~~text~~`.
- Memory is manual opt-in and creator-private.
- Sharing is copy, read-only membership, or group sharing — not live collaborative editing. Group members may ask questions and write their own deep reports; group admins manage the shared library's content (sources, builds, grant edges), while mount configuration, link sharing, and deletion stay with the owner, and a plain member can request to contribute their own library to a group for admin approval.
- Web/network source search remains a disabled future affordance.
