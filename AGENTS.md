# Agent Development Instructions

This file is the working contract for future agents and developers in this repository. Keep it updated whenever setup, product flow, architecture, or constraints change.

When making changes that affect setup, product behavior, architecture, or development constraints, update all four files together:

**Whenever you complete a feature defined in `silicon_notebook_fangan.md`, you MUST append/update the corresponding entry in `fangan_done.md`** in the same change. Specifically:

## Full-Stack Parity (Backend ⇄ Frontend)

**No half-features.** In this product, every user-facing backend capability MUST ship with a corresponding frontend UI in the same change. It is not allowed to implement only one side.

- If you add a backend endpoint or data type that produces something a user should see or act on (a new knowledge type, list, action, status, field, analytics view, etc.), you MUST also add the frontend surface to view/use it — and vice versa (no frontend control that calls a missing endpoint).
- A feature is "done" only when: backend endpoint exists, `frontend/app/page.tsx` (or its components) exposes it, `scripts/check.sh` is green, and `cd frontend && npm run build` passes.
- Concretely, do NOT leave any object type "approvable but not browsable", any endpoint with no UI entry point, or any UI button wired to a non-existent route.
- Purely internal/infrastructure endpoints (health checks, migrations, observability logs) are exempt — they are not user-facing. When in doubt, treat it as user-facing and build the UI.

## Product Flow

The app uses a two-level notebook structure:

1. Outer page: notebook collection/library.
2. Inner page: individual notebook workspace.

The notebook collection page should keep the current NotebookLM-inspired structure while staying visually distinct:

- Tabs such as `全部`, `我的笔记本`, `精选笔记本`.
- Search, view switch, sort, and `＋ 新建` controls.
- Grid, compact, and table-like list preview modes.
- The first card is `新建笔记本` when not searching.
- Notebook card upper-right menus must open real edit/delete actions.
- Collection/notebook search must include notebook metadata, source metadata, parsed source elements, and knowledge objects.

When the user creates a notebook:

- Do not ask for title, purpose, or description up front.
- Immediately create an `Untitled notebook`.
- Open the notebook.
- Show the source selection/import UI immediately.
- Later ingestion and LLM analysis should infer title, description, domain, summary, and knowledge objects from imported sources.

Inside a notebook:

- Hide the global collection top bar.
- Keep visible `silicon-notebook` differences with a more engineering-console feel rather than a direct NotebookLM copy.
- Reset scroll to the top when switching into or back from the notebook workspace.
- The upper-left notebook title should be editable in place and save through the notebook update API.
- Keep the notebook header compact: do not render the notebook description under the title; show that description in the Ask welcome state when no conversation is active. Top toolbar actions must keep their labels intact across desktop widths.
- Centered floating dialogs are draggable by their header via the shared `useFloatingWindow` hook — inline `page.tsx` modals go through the `FloatingModalCard` wrapper, which owns only the card (drag offset + card ref) and hands the header its `dragHandleProps`. Dragging is disabled at the narrow-screen breakpoint (`isFloatingDisabledWidth`), where modals keep their fixed layout, and a press on a header control (close ×, buttons) never starts a drag. New centered modals adopt this rather than reinventing drag; side-anchored drawers, anchored popovers, and full-screen views stay put. The model-service status modal additionally re-polls its live 并发/排队/最久等待 every ~2s while open (an in-memory scheduler read, no model calls); its probe-driven 延迟/上次检查 stay event-driven.
- Left column: user-imported source files only. User-facing source counts exclude hidden `source_type` `memory` / `knowhow` projection sources; physical `size.sources`, copy/storage thresholds, and scheduler accounting keep physical-row semantics. `has_unindexed_content` must preserve a derived-content scale-index update decision when the visible imported-source delta is zero.
  - Show how many sources are in the current notebook.
  - Keep source cards compact and readable for long mixed Chinese/English titles and summaries.
  - Source cards should open a source detail preview with element-level parsed text and expose a delete action.
  - The add-source dialog must keep staged rows stable: compact overlong filenames in the middle while preserving the ending/extension and expose the full name as a tooltip. Its confirmation button must include the staged batch in the effective document-limit check, become visibly disabled when the batch cannot fit, and show an actionable reason; keep comfortable space below the last action row.
  - Source detail element text should wrap within the modal width, including long Markdown paths, LaTeX fragments, and mixed Chinese/English text; keep horizontal scrolling local to tables/formulas rather than the entire detail panel. Direct KaTeX inputs must strip full-value Markdown math delimiters (`$...$`, `$$...$$`, `\\(...\\)`, `\\[...\\]`) first, and malformed input must fall back to visible raw text rather than an empty/error-only visualization.
  - On desktop, source detail uses a conventional close control and supports dragging by the header; keep narrow-screen geometry fixed and the detail body independently scrollable.
  - Do not enable web/network source search yet; keep it as a disabled future affordance only.
- Main column: source-grounded knowhow tools, exposed as four tabs: **问答** (Ask), **知识库** (Knowledge), **记忆** (Memory), and **深度报告** (Deep Report).
  - Ask provides KG-grounded Q&A with per-sentence `[k_i]` citations and multi-turn conversation. Knowledge browses/governs extracted objects by type. Deep Report exposes the current two-stage report workflow, outline review, progress, export, cancellation, and deletion. The earlier Scenario query / Case search / Checklist tools are retired.
  - Deep Report planning is intent-first and confirmation-gated. Creating a report first performs corpus-blind question understanding and persists an `understanding` contract (original objective, editable resolved question, mandatory topics, entities/comparison axes/constraints/exclusions/output, assumptions, confidence, and bounded blocking ambiguities), then always pauses at `status=intent_ready`. Required ambiguities must be answered; a clear question still requires owner confirmation. Read-only members wait for the owner. Only `POST /notebooks/{id}/reports/{report_id}/intent` may confirm the resolved question and resume corpus access: it must atomically claim `intent_ready → planning`, deterministically preserve every already-reviewed contract field, and add the confirmed wording/answers without a hidden second LLM reinterpretation. That frozen input is authoritative for all later retrieval, outline, and generation; `auto_generate` may skip outline confirmation after this gate but never skips intent confirmation. Confirmation answers may enrich the internal retrieval/drafting question but must never leak into the visible report title. After confirmation, probe KG and direct `SourceElement` coverage per mandatory topic, then let corpus evidence refine vocabulary/order without replacing or narrowing a required topic. Every mandatory topic keeps at least one section binding through outline review (the UI locks its last binding and the PATCH API rejects bypasses), and every approved retrieval direction must execute even if the reasoning planner replans. Outline cards expose mandatory questions, editable retrieval directions, and KG/raw-element coverage. Direct `SourceElement` hits are first-class `[k]` evidence in both reasoning Ask and reports; selecting a report citation reveals its bound source/location excerpt. Small libraries may score their element rows directly; a non-copyable large library must never full-scan element text/vectors, but must recover a bounded exact-element candidate set from already bounded chunk ANN/FTS hits and hydrate only their `element_ids`. Citation display in Ask and reports prefers the grounded `source_paper_meta.paper_title` only when `is_paper=true` and the parsed title is nonblank, otherwise it retains the ordinary source title/file name. A report section is `grounded` only after its emitted anchors bind to sufficiently relevant evidence; never trust the model's boolean alone or collapse two concrete chunks/elements merely because they share a source. The final editor may summarize and flag missing intent/contradictions, but must not rewrite sections or add facts.
  - Ask federation is mode-specific. Baseline `chunk` retrieval is active-notebook-only; optional KG overlay/PPR can add federated KG context and base-backed chunks. `graph` and `reasoning` use federated KG paths. Citations retain their tier, and answer synthesis defers to base on contradiction. The `mode` field selects `chunk` (default), `reasoning`, or the opt-in/experimental `graph`; retired `fast`/`global` ids map to `chunk` only for persisted-session compatibility.
  - Indexed KG retrieval must keep every post-ANN database hydration step bounded by the current candidate window. Isolated-node ranking probes return only candidate ids through indexed per-candidate `EXISTS` checks; they must never materialize complete adjacency rows. Canonical folding uses `cluster_fold_rows` for the scored ids rather than the full notebook cluster map, and lazy ANN handle opening is single-flight per scale-index instance and artifact kind. These are result-preserving constraints: do not change scores, thresholds, PPR, or recall to recover latency.
  - The twelve built-in KG edge ids and their directed endpoint pairs have one authoritative registry in `app/services/kg/edge_schema.py`; extraction prompts, output validation, edge trust, graph/PPR/canonical hydration, relation retrieval, query-time composition, and persisted-artifact versioning must derive from it rather than repeat local matrices. Producers are fail-closed for the four core types. Query consumers reject illegal core-to-core pairs and unknown edge ids while retaining known edges that touch administrator-defined extension node types. Historical invalid rows remain stored for audit but are excluded from graph consumers. `scripts/audit_kg_edge_contract.py` is read-only and reports grouped counts plus ids only, never evidence text.
  - Optional post-extraction relation completion is bounded and rollout-gated. `KG_RELATION_COMPLETION_MODE=off` is the default; `shadow` runs proposal/verification without writes and `write` inserts only pending relations. Both active modes additionally require an explicit notebook allowlist or stable hash rollout. Completion pages a source through an indexed `(source_id,id)` keyset and a mode-specific persistent source-generation watermark; each job hydrates only its bounded object/evidence-id window, uses indexed per-candidate relation `EXISTS` plus bounded same-source FTS/ANN overfetch, section quotas, pair/batch/character rails, server-issued ids, and an independent verifier. Unfinished states re-enqueue and startup recovers current pending generations; if effective mode changes, one generation-CAS transaction publishes the newly active mode's recoverable cursor before marking the old pending cursor `stale`. It never full-scans a notebook/book or falls back to brute force when indexes are unavailable. The final short write transaction rechecks source/run generation and object/element ownership, persists the exact server excerpt seen by the verifier, and uses stable relation ids for retry idempotence; reparse/delete races write zero stale rows, while invalid zero rails fail closed without advancing.
  - Retrieval provenance is producer-level and accumulative: semantic, lexical, PPR, KG-source, and community producers append typed support records when candidates merge. Never infer origin from a final score. Chunk/graph mixed selection may reserve `CHUNK_GRAPH_RESERVE` graph-only candidates that already clear the existing relevance floor, but it must not enlarge token/item budgets or change the oversized-first-chunk exception. Additional reserves go through the same `select_with_reserves` rule list rather than a parallel selector: reserves share one budget, a reserve set to `0` must stay completely inert (so the shipped `CHUNK_GRAPH_RESERVE=0` default keeps behaving exactly as before), and no reserve may evict a chunk another reserve is holding.
  - Questions naming an exactly lookup-able identifier additionally run the zero-model exact-lookup channel (`EXACT_LOOKUP_ENABLED`, on by default): exact substring match locates the section, `chunks_by_section` fetches that node plus its subtree, and `EXACT_SECTION_RESERVE` protects those chunks during mix selection. The gate is `exact_probe_terms`, a deliberately NARROWER view of `identifier_terms`: `_`/`.`-joined names always qualify, hyphen-only forms must carry a digit (`GPT-4`, `v1-2` in; `state-of-the-art`, `real-time`, `end-to-end`, `high-level` out). Recall and probing are different contracts — one extra OR-ed lexical term is free, one extra probe is not — so the wide definition must stay wide on the recall side; the narrow one exists because those hyphenated words occur in a large fraction of analytical questions (a deep report's per-section question reliably contains one, i.e. one wasted probe per section, measured at 16 ms / 50 hits on a 20k-chunk library) and, when one matched a chapter heading, put that entire 12-chunk chapter into the evidence set at relevance 1.0. That gate is the cost contract — a question with no probe-worthy name must issue zero additional queries — and every probe stays bounded by the `EXACT_LOOKUP_*` settings. Hits fold onto their nearest identifier-named breadcrumb prefix BEFORE section slots are allocated and are ranked per group: ranking raw breadcrumbs let one command's sub-sections take every slot (`set_db > Arguments` 4 hits / `> Examples` 3 / `set_db` 2 / `report_timing` 2 with three slots dropped `report_timing` entirely), and "a command's sub-sections out-number its main section" is the normal shape of a reference manual. A group whose key is identifier-named is fetched as a subtree; anything else is hydrated **by matched chunk id**, never re-queried by `(source, section_path)` under a LIMIT — heading breadcrumbs are a Markdown-parsing property, so MinerU-parsed PDF/DOCX sources leave dozens of bare `Arguments` headings sharing one section key, and the path re-query returned the first 12 of them while discarding the hit the probe had actually found. Both adapters must escape `%`/`_`/`\` in LIKE patterns (command names contain `_`, LIKE's single-character wildcard, so an unescaped needle silently loses precision rather than failing), and the exact probe must never decompose its needle through `lexical_recall_terms`. Channel chunks score keyword-only against the probed NAMES rather than the caller's query — one producer, one meaning; scoring the caller's query made mix report 0.2857 (below `tau_high`) and reasoning 1.0 for the same evidence — and deliberately skip `RELEVANCE_FLOOR`, because the admission criterion is the exact section anchor, not fuzzy relevance; membership reaches the selector as an explicit chunk-id set rather than a new `RetrievalSupport` origin. Active notebook only — mounted base libraries are out of scope.
  - Lexical candidate generation is part of the indexed retrieval contract. SQLite FTS5 must quote every user-derived clause as data, keep an optional exact-query phrase bonus, and OR independent Latin/number terms plus overlapping CJK trigrams; never quote a multi-term query only as one mandatory contiguous phrase. Separator-joined identifiers (`_`/`-`/`.` runs such as `set_db` or `config.yaml`) are additionally recalled as whole quoted terms — trigram phrases give exact substring matching — bounded by an ASCII-letter requirement, a 4-char floor, the exact-phrase length cap, and a 16-term quota; when identifier terms overflow the shared term budget, a bounded CJK tail quota is reserved so the CJK half of a mixed query keeps lexical recall. Queries with no such identifier keep the historical term set bit-for-bit. PostgreSQL must decompose the same bounded term set before native trigram candidate generation, and must escape LIKE metacharacters in its `ILIKE` arm so a term such as `set_db` stays literal instead of widening into `setXdb`/`set db`; the trigram operator and `similarity()` keep the raw term, because escaping is a LIKE-only concern. Indexed Chunk and KG retrieval union bounded ANN and lexical windows. Indexed Relation retrieval unions ANN hits with a bounded set of live relations adjacent to lexically matched KG endpoints through the source/target indexes; preserve FTS endpoint rank and reserve budget for both relation directions so a high-degree source cannot starve target-only hits. Keep candidate identity separate from semantic-score maps so lexical-only candidates remain keyword-only instead of receiving a synthetic zero semantic score.
  - Large-library cold loading is a readiness prerequisite. With `STARTUP_PRELOAD_SCALE_INDEXES=true` (the default), startup strictly loads every live published scale index, every currently enabled KG/chunk/relation ANN handle, and the safely reusable single-index PPR transition/chunk-id core before `/api/ready` admits traffic. A required artifact failure or a live-index count above `SCALE_IDX_CACHE_MAX` keeps the service not-ready; never silently make the first user pay that artifact load. A direct single self-index graph with the delta gate off reuses the ScaleIndex node list/map/idf and prepared PPR core instead of copying tens of millions of entries; this core lives with the dedicated ScaleIndex LRU, not the evictable general VectorCache. Do not eagerly materialize every cross-notebook mounted combined graph at startup: the current composition path would multiply full node maps/CSR edges and can OOM, so those combinations remain lazy until they get a bounded/shared representation. The strict guarantee is for the published artifact set present during startup: a runtime build/fold publishes a new generation through the existing online path, and adding a new indexed notebook can exceed the configured LRU; stable deployments should size `SCALE_IDX_CACHE_MAX` before that change and restart to re-establish the readiness guarantee. `STARTUP_PRELOAD_SCALE_INDEXES=false` is only an explicit recovery escape hatch for repairing a bad index; production remains single-worker so multi-GB caches are not duplicated per worker.
  - Scale-index scheduling treats a manual `when=now` request as an atomic upgrade of an older idle request for the same notebook: only a newly claimed immediate build removes that queued entry, a concurrent already-running build preserves its follow-up, a later idle request remains queued, and daemon-start failure restores the displaced request. The idle scheduler must claim entries independently instead of clearing the batch: busy entries stay queued and one launch failure cannot drop or starve the rest. Persisted `AskResponse.index_required` records answer-time degradation only; the answer panel must combine it with live `ScaleIndexStatus.exists`, and `index_done` must refresh the active notebook after bounded foreground polling has ended so the historical warning disappears as soon as an index is published.
  - Ask mode ids are protocol; their display names are UI. `chunk` / `reasoning` / `graph` and the group ids `general` / `strict` are what `POST /ask` accepts and what persisted sessions and bookmarks store — treat them as stable and never rename one to improve wording. The user-visible names are owned solely by the front-end registry `frontend/app/ask-modes.ts`: `chunk` → 通用问答, group `strict` (the picker entry, default engine `reasoning`) → 深入分析, `reasoning` → 逐步推理, `graph` → 关联追溯. Read them through `groupLabel()` / `modeLabel()`; no other front-end file may hardcode a display name, and prose mentioning one interpolates it. `ask-modes.test.mjs` recursively scans `frontend/app` and fails both on a current display name appearing outside the registry and on a retired name (严格推理 / 深挖推理 / 图谱多跳) reappearing, so a rename is a one-line registry edit. `scripts/check_ask_modes_contract.py` separately pins the id set against the backend registry.

  - Ask question timestamps use the browser-captured submission instant, persisted with the answer rather than substituting server answer-completion time. Hover reveals the browser-local label below the question; click pins it until an outside click. Today shows time only; another day in the current Monday-based week shows weekday plus time; outside the week shows date plus time, never date and weekday together. The current year is omitted and other years are included. A visible pinned label must refresh when the local calendar day changes.
  - Ask answer timestamps use the authoritative answer-write instant (`answers.created_at`), exposed as `AskResponse.answered_at`; reopening legacy payloads backfills it from the answer row without a migration. Answer cards use the same browser-local formatting, hover reveal, click-to-pin, outside-click dismissal, and local-midnight refresh rules as question cards.
  - Conversation history is ordered and timestamped by latest activity, not creation time; the activity clock must retain sub-second precision and SQLite ordering must compare absolute instants across UTC-offset changes. Once `/ask/stream` emits `started`, the durable conversation must appear in history immediately (including a new first turn with no model answer yet), become the current `conversation_id`, and remain reopenable after switching sessions—even if that switch wins the race before `started`. History publication, list-request generation, and terminal-summary refresh are notebook-scoped rather than visible-run/session-epoch-scoped; older orchestration callers follow the newest same-notebook list request (including through a failed intermediate request), while a delayed request from a different notebook must not invalidate the active notebook. The authoritative refresh must not be deferred until `final`, and the Ask composer/mode controls stay disabled while a selected session/notebook's latest detail is still loading so a late detail response cannot take over a newly submitted run.
  - Reasoning mode should surface backend agent progress in the Ask panel while the request is running. Use `POST /notebooks/{id}/ask/stream` for live NDJSON `progress` events, render the trace as a streaming one-line summary by default, provide click-to-expand details, and keep the final `reasoning_trace` visible on the answer; do not regress to a bare static "thinking" placeholder for reasoning requests.
  - The reasoning trace must cover the whole run, not just retrieval. The question-understanding preflight runs before any durable job exists, so the UI synthesizes its own leading trace steps (understanding in flight → understood / awaiting clarification → confirmed) and the backend steps stream in after them, rather than the phase getting its own separate status line outside the trace. That phase's client-measured wall clock is reported back as `intent.understanding_ms` (bounded, optional, never an input to retrieval) and becomes the persisted `intent` step's `duration_ms`, so a replayed trace does not silently drop it. The engine streams its `intent` step before Memory retrieval and records a `memory` step when private memories were recalled. That step reports RECALL, not attribution: memory routinely reaches the prompt without being cited, so gating it on bound anchors would under-report a lookup that did happen, and deferring it until synthesis would move it away from where it occurred; attribution is carried by the answer's `[k]` citations, and its wording must never claim the answer used those memories. A zero-hit lookup is recorded as a timed `skip` instead — the candidate query and embedding call still ran, and dropping their duration would contradict whole-run timing. The engine also records a `synthesis` step after answer generation — that generation call is usually the longest single slice of a run and must be neither invisible nor excluded from the trace total; its citation count comes from bound anchors, never from the retrieved-evidence cards. Live trace panels are gated on whether the engine actually streams a trace (`AskMode.streaming`, mirrored as the frontend's `streamsTrace` and locked by `scripts/check_ask_modes_contract.py`), never on its display group: a non-streaming engine in a strict group would otherwise show an empty "waiting for backend events" panel for the whole request.
  - Reasoning mode is intent-first. The official UI calls `POST /notebooks/{id}/ask/intent` before creating a durable Ask job; this preview may use the latest prior user questions, but not corpus-derived assistant answers, and must not read notebook/base corpus or create a conversation/job. Clear intent auto-confirms, while direction-changing ambiguity pauses for user answers. Because clear intent has no human review, its original user wording remains the authoritative first retrieval seed and any model-normalized wording is supplemental; after blocking ambiguity is answered, the reviewed resolved question becomes authoritative. Freeze mandatory topics/retrieval directions, entities, comparison axes, constraints, exclusions, assumptions, expected output, and answers without a second interpretation pass. Use that contract for Memory, PPR, initial subqueries, evidence retrieval, and answer synthesis; retain the original user question as the visible/saved turn. The whole authoritative question runs first, then reviewed directions are round-robin seeded within the configured topic budget so each mandatory topic gets coverage before extra aliases. The reasoning planner must not silently replace these seeds; later reflection may only add evidence-driven queries. Invalid confirmation returns 422 before a durable job exists, and aborting the preflight propagates a cancellation event to the intent model call.
  - Reasoning retrieval effort and collection completeness are separate protocol contracts. `retrieval_effort` has stable ids `overview` / `standard` (default) / `deep` / `thorough` / `exhaustive`; their per-query ranked take is `4/8/8/12/16`, final `floor/aspect/cap` is `8/2/12`, `20/3/36`, `24/4/48`, `32/5/64`, `40/6/96`, maximum `steps/initial-subqueries` is `4/2`, `8/5`, `16/6`, `32/8`, `50/10`, KG/chunk prompt characters are `4000/12000`, `6000/30000`, `8000/50000`, `12000/80000`, `16000/120000`, and the direct source elements (formulas/tables/images/…) admitted into the final synthesis prompt (`answer_element_items`) are `4/6/8/12/16` — chosen by retrieval relevance descending (tie-break element id), not insertion order, and still consuming the shared chunk-context budget. The same five profiles also carry the collection-enumeration tools' budget: `enum_page_size` is `50` at every effort, `enum_pages_per_run` is `2/4/6/8/12`, and `enum_rows_per_run` is `100/200/300/400/600`. Final ranked selection is `min(cap, max(floor, aspect × executed-query-count))`; a model may stop early but never raise a ceiling. Candidate recall never scales with effort but is independently deployment-configurable: `CHUNK_RECALL` defaults to 200 and separately bounds indexed Chunk/KG ANN and lexical windows; `RELATION_RECALL` defaults to 200 and separately bounds Relation ANN and the total lexical relation-id window, whose source/target directions retain reserved shares. These defaults are not request-level hard ceilings. Intent records `ranked` / `complete` / `aggregate` / `hybrid`; explicit completeness for Knowhow must use stable cursor enumeration, not a larger Top-N. All five efforts share 25 rows/page, 50 pages, 1,250 physical rows/request, 8 tables/request, 8 selected columns/table, 1,000 characters/cell model excerpt, 256,000 characters/structured payload, 100 rows inline in answer prose, and 20 rows initially visible per result card. Cursor exhaustion plus stable table catalog, row counts, column metadata, and selected table scope is required for `complete=true`; touching any row/page/table/column/payload rail or observing concurrent mutation returns `complete=false` with `explicit_partial` and must never claim “all”. A 100-row Knowhow table therefore returns `100/100`; a lower effort may reduce analysis but never lowers explicit-completeness enumeration limits. Exact-completeness enumeration of physical rows currently covers Knowhow only; the model-invoked `enumerate_elements`/`enumerate_kg_objects` reflect tools separately cover the whitelisted source-element kinds and KG object types (see the Architecture Baseline entry below); Memory and any other collection remain relevance-ranked and must disclose that boundary. That disclosure is suppressed only when FOUR deterministic conditions hold together: `result_scope != "aggregate"`, the intent contract's `constraints`/`excluded_topics`/`assumptions` are all empty, at least one collection result card returned rows, and that card's coverage is `complete`. The bias is deliberately toward over-warning: a card's coverage proves that one physical collection was walked end to end, never that the physical collection is the subset the question asked for, and no deterministic test exists for the latter.
  - The exact-completeness executor is deliberately narrower than the intent labels: confirmation reclassifies scope from the final edited wording and authoritative clarification answers, and only direct whole-table physical-row/method lists, direct row/record counts, and their hybrid analysis may enumerate. Conditional subsets, distinct/type counts such as “how many kinds”, and group-by requests without a deterministic plan must fall back and disclose that exact completeness is unsupported. The lightweight catalog returns at most 8 table descriptors and no cells, code attachments, or health payloads; an explicitly named table is prioritized before applying that window, while aggregate counts/sequences still cover the whole notebook. Responses separate per-table, batch, and synthesis coverage: a 200/200 enumeration with a 100/200 model preview is “enumeration complete, analysis partial”, while an 8-table batch truncation does not make an individually exhausted selected table partial. KG objects/relations, confirmed Memory, and query-time chains share the KG character budget; structured preview, chunks, and direct elements share the source budget; the final evidence block may not exceed their sum.
  - Reasoning mode wires the exact-identifier channel in twice, and both are zero-model. This wiring reaches the `reasoning` ask mode and, because the report engine reuses `ReasoningRetriever` verbatim, every deep-report section's retrieval; `graph` mode does not wire it in. (1) A deterministic seed pass runs once immediately after the initial retrieval whenever `exact_probe_terms(question)` is non-empty — mirroring the PPR seed pass, it does not bet on whether the agent picks the action. It scores its hits by the joined identifier names it actually probed, not by the raw question — producer-native scoring is this retriever's existing convention (a PPR hit is not scored "relevance to the raw question" either), and scoring the exact match against every unrelated token in a long question sank a genuine hit's relevance low enough to lose the character-budget cut and, as the sole anchor, the grounded/overview threshold (a measured regression). It records an `exact_lookup` trace step whose detail carries the names actually probed (already truncated to `EXACT_LOOKUP_MAX_IDENTIFIERS`), the yield, and `phase`. It is placed after the PPR seed pass so PPR's dedup and counts stay bit-identical. A question with no identifier issues zero calls and adds zero trace steps. (2) The reflect model may choose the `exact_lookup` action with an `exact_term`, scored the same producer-native way. The action shares the seed pass's `exact_probe_terms` gate — an arbitrary low-selectivity string, and equally an ordinary hyphenated English compound, is refused with a skip rather than becoming a library-wide substring scan, because that gate is a measured cost contract and must not be delegated to the model — shares one per-run ledger keyed by name so the seed pass's names cannot be re-requested, executes only the names new this round, and is capped at `_MAX_EXACT_LOOKUPS = 3` agent invocations (the seed pass does not consume that quota). Every skip — channel disabled, missing name, non-identifier shape, duplicate, or over the per-run cap — feeds a teaching note back into that same ledger (not just a TraceStep), deduplicated by reason/name so a model repeating the same invalid input does not grow the ledger without bound; e.g. a non-identifier term teaches back "「2.1」不是可精确查找的名称(要像 set_db、config.yaml 这样带下划线或点;只用连字符连接的词还需带数字,如 GPT-4)" — phrased as what to supply next, because a note that only says "invalid" gets the model to retry with another equally invalid ordinary word — so the next reflection can act on the reason instead of silently retrying. `exact_term` is cleaned (unwrapped, not truncated) at parse time so the `reflect()` fail-closed 2000-character field cap can actually reject an oversized value; truncation to the lexical layer's phrase cap happens only at the point of use. Both paths go through `_filter_candidates` and an `allow_exact_lookup` instance policy flag mirroring `allow_ppr`: knowhow completion sets it `False` for the same reason it disables PPR/community below — its JSON-envelope query would otherwise make the seed pass unconditionally (and uselessly) probe the envelope's own field names on every completion request. The action name and prompt line are static rather than flag-dependent, following the precedent set by `ppr_retrieve`: with `EXACT_LOOKUP_ENABLED=false` or the policy flag off, the action is skipped at execution with zero I/O instead of being removed from the prompt/whitelist, so the action contract does not drift with deployment configuration. - Every knowhow table carries a full change history (`knowhow_changes` + `knowhow_milestones`, schema v26). All 15 write methods append one change row via the module-level `record_change` as the **last** step of their write transaction, storing the affected entities' before/after plus the **post-change whole-table fingerprint** (reusing the transfer guard's `_FINGERPRINT_SQL`, covering table meta / columns / rows / cells / cell code and deliberately excluding timestamps); an architecture guard (`test_knowhow_history_coverage_guard.py`) fails any un-allowlisted write transaction so a future write path cannot silently skip hooking. Revert is pure delta reverse-replay inside one write transaction: verify the current fingerprint equals the head change's fingerprint (else abort), replay each change's `before` from head down to the target (rows/columns **reuse their original id** so citation jumps and code attachments survive), verify the resulting fingerprint equals the target's (else roll back the whole transaction), then append a `revert` change — history is append-only, so "revert of a revert" is inherent. Single-cell restore is an ordinary save (`origin="revert"`) that keeps the merged-cell fan-out invariant, not the whole-table revert path. Milestones are zero-snapshot names on a seq; pruning history deletes only the oldest contiguous prefix (by seq, not `created_at`, so clock skew cannot punch holes) and always keeps the head row. The orphan-image sweeper's live-reference set extends to change-log payloads, so an image that ever entered a cell is essentially never auto-collected — the cost being that "prune history" only frees it once the last reference no longer sits on the retained head row. ### Database Backend And Switching Contract

- At the `open_fresh_live_sqlite` call boundary, a non-transient `sqlite3.OperationalError` is a source-binding identity failure. Locked, busy, and interrupted opens remain transient whole-batch retries; SQLite operational errors after that open boundary retain their existing schema/query classifications.
- The single factory is the only backend-selection branch. PostgreSQL uses its own persistence bundle, checksummed migrations, bounded Psycopg pool, row/advisory locks, and transaction isolation for cross-process access; it must not copy SQLite's process-local write lock. Both backends auto-migrate at startup and fail closed without falling back to the other backend.
- PostgreSQL stores float32 vectors as `bytea`; pgvector is not installed or required. It requires `pg_trgm` in the `public` schema. Production remains `--workers 1` because the model scheduler, breakers, and cancellation registries are process-local.
- `SHADOW_DATABASE_URL` remains inert by itself. The temporary `migration/shadow` boundary currently provides the exact SQLite v37/PostgreSQL v15/epoch-1 preflight/control/guards, run-bound atomic SQLite snapshots, bounded resumable 64-table baseline COPY through atomic H0, and a fail-stop single-consumer forward apply engine. The engine reads the global SQLite log strictly from checkpoint+1 without filtering away gaps, validates every run/epoch/table/op/key, hydrates current rows only for upserts in a short source snapshot, keeps deletes key-only with zero hydrated bytes, and preserves all seven SQLite rowid ordinals. Repeated stable keys in an accepted prefix coalesce to the last event and are emitted in global last-seq order; raw seq/checkpoint continuity is unchanged, while the final actual apply for an identity overrides any synthetic dependency contribution; only dependency-only identities contribute one reference-counted synthetic row and its bytes. A short read window ending below the allocated high-water is an immediate suffix gap before hydration/apply; a full window below high-water must probe the adjacent sequence in the same snapshot and fail if it is absent. Batches are hard-capped at 4,096 events/64 MiB: only one final bundle may exceed the byte cap, and a same-key replacement that grows past the cap must roll back and defer when another actual bundle is already accepted. FK parents come unconditionally from that same verified current-state snapshot through a 64-row-per-event closure; the fixed v15 graph's branch-counted bound is exactly 9 row slots. Dependency rows count toward bytes and deduplicate across the batch; never scan or trust suffix change-log metadata to authorize them. Target savepoints defer only FK/UNIQUE ordering SQLSTATEs; CHECK/NOT NULL poison immediately. Migration-derived plans cover exactly 86 PG15 unique surfaces: nullable columns park at NULL; non-FK/non-CHECK text/bigint use deterministic candidates scoped by indexable equality for non-NULL values and `IS NULL` for NULL values on the other unique columns plus the fixed predicate (`C`-collated text max plus `chr(1)`, or an indexable bigint MIN/MAX fast path choosing min−1/max+1 and scanning the first gap only when both int64 bounds are occupied); and only a statically proven no-incoming-FK leaf whose conflict key has an accepted current-final apply may delete/reinsert inside the same target transaction. Parked state is per unique surface and row identity; each stagnant pass parks every independently parkable conflict, and a successful final apply clears every parked surface for that identity. Deferred work is capped at eight passes, 32 actual statements per apply, and 16,384 actual statements total; every candidate query counts toward that budget, and ordering, statement, pass, and `ProgramLimitExceeded`/`DataError` candidate-search or candidate-update capacity exhaustion stays non-poison; `QueryCanceled` remains transient and retries the whole transaction. A final-window unparkable UNIQUE failure instead poisons its earliest actual event seq. `run_forever` doubles from 256 events/8 MiB through the hard caps after ordering-blocked; hard-cap exhaustion stays non-poison. After claiming the worker, the apply transaction must recheck existing poison for that run/direction before any business DML. Poison publication must likewise lock and inspect any existing run/direction poison after binding/checkpoint validation: an exact replay is ACK-loss success, while any differing record is stale and must never create a second poison. The target transaction follows migration→control→run→worker→checkpoint lock order, takes `SHARE ROW EXCLUSIVE` on the migration ledger plus all 64 business tables, revalidates the run-bound exact v15 catalog plus snapshot source/target and live target identities, requires `progress.applied_seq == checkpoint.last_seq` at snapshot and again before business apply, and commits business rows, redacted run progress, and contiguous checkpoint together. Ambiguous commit recognition and poison publication repeat the same identity binding. Transient pool/connection/deadlock/serialization/lock/statement-timeout failures retry the whole transaction with capped jittered backoff; SQLite path/file binding failures use a dedicated identity exception rather than message-based conversion classification; proven conversion, schema, identity, constraint, and continuity failures record exactly one redacted poison at the actual blocking seq and never skip or advance. Every valid batch outcome emits exactly one metric; batch-event count is the actual accepted/observed raw-event count rather than lag, and retry counts are retained whenever observable. Metrics contain only run/direction/checkpoints/lag/counts/bytes/duration/retries/poison count, never table labels, keys, row values, URLs, worker ids, or exception text. Never wait for PG while holding a SQLite transaction. The explicit operator CLI owns preflight/start-forward/status/verify; a foreground worker holds one database-clock lease, finishes the current atomic batch on SIGTERM/INT, and runs conservative retention only behind FULL verification, active barriers, replay checkpoints, poison, seven days, and 100,000 tail events. This is an operational SQLite-active forward-shadow path only: cutover, reverse replication, and automatic `DATABASE_URL` changes remain unimplemented. Changing `DATABASE_URL` does not copy or synchronize data, and PostgreSQL-only writes are never replayed into SQLite.
- Shadow verification must record `Hv` in a SQLite read snapshot, release SQLite before waiting for PostgreSQL, pin a `REPEATABLE READ, READ ONLY` target snapshot at `Ht`, then scan the retained `(Hv,Hseen]` source log in a new SQLite transaction and exclude only those proven concurrent stable keys. Keep the PostgreSQL verifier barrier until the report commits. After parsing, **element embedding runs in a background daemon thread concurrently with foreground KG extraction**; `extracted` (UI green) is gated on extraction completion only. SQLite uses WAL + `busy_timeout` so concurrent writers do not lock. The repository still accepts a `scheduler` callback so scripts/tests can run synchronously.
- Manual notebook KG build/rebuild is a durable, notebook-scoped task in `kg_build_jobs`, with at most one `running` row per notebook and observable `probing→extracting→stopping→finished` state. KG LLM calls must use the task-scoped client, `KG_LLM_TIMEOUT_SECONDS`, and bounded `KG_LLM_MAX_RETRIES` (`0..3`); persistent unavailability/auth/rejection aborts only that notebook's current task, stops new source/window requests, writes `stopping` directly from the first aborting window before either window/source drain, and cancels/drains outstanding futures. Full-build source inventory and submission are bounded keyset pages on both backends. Rebuild's live availability probe must bypass and not populate the LLM response cache before deleting existing KG. Preserve committed source results and make every source's object/relation chunks one transaction; a failed latest extraction run is unfinished even if legacy partial rows exist, and every terminal extraction-run status update must invalidate the notebook's pending-source memo after commit. Startup recovery must fail orphan running extraction rows and restore every orphan source from `extracting` to `parsed`, including pre-run interruptions. An interrupt must settle that same row: a `KeyboardInterrupt`/`SystemExit` reaching a build (Ctrl-C or a signal on an offline run) aborts the run control and then cancels and **drains** the submitted source futures before the task reaches a terminal state — the single-flight guard is released the moment that row settles, so a live backend could otherwise start a new build for the notebook while the dying process's workers still write graph rows and source status. It then publishes `stopping` **without** a `circuit_opened` event (an operator interrupt is not a model outage, and must not be counted as one), and writes the terminal `worker_interrupted` failure before propagating — but only emits the failure event when that write actually settled a `running` row, so a signal landing after a successful `finish` cannot publish a `kg_build_failed` event carrying `status="succeeded"`; leaving the row `running` deadlocks that notebook behind the one-running-per-notebook index and shows an analysis that never finishes. Offline CLIs deliberately may not clear such a row (startup recovery belongs to the server lifespan), so `scripts/batch_ingest.py` routes SIGTERM/SIGHUP into that same interrupt path — but only around the full-notebook build that owns a durable row and drains; non-durable pooled phases (`--limit`/`--retry-partial` extraction, `all`, `reparse`, `ingest`, `metadata`) keep default immediate SIGTERM/SIGHUP behavior; when Python receives Ctrl-C/SystemExit they cancel queued futures and drain accepted work before the maintenance advisory lock/repository is released. It leaves an already-ignored SIGHUP ignored so `nohup` runs still survive a disconnect, restores prior handlers on return, and reports an already-running task as actionable operator guidance with exit 2 rather than a raw integrity error. The frontend must guard start callbacks by notebook/workspace/request ownership, resume and keep polling the durable running state without a synthetic time cap, show the safe failure message/progress, and expose `继续分析未完成内容`; explicit rebuild remains the only destructive retry. Emit only safe `kg_build_started/progress/circuit_opened/stopping/succeeded/failed` task metadata, never provider diagnostics, prompts, source text, tokens, or credentials.
- On both supported backends, `batch_ingest --workers` controls source/document jobs only and falls back to `KG_JOB_CONCURRENCY`. Every chat, embedding, and rerank call from every batch phase must use the same `RuntimeModelProvider` and per-service `ServiceScheduler` as online requests. The bound service's TOML `max_concurrency` is the sole model-capacity setting; never add batch/environment model-capacity overrides or multiply capacity by source workers. Scheduler waits must not hold database connections or write transactions. PostgreSQL source, durable/limited KG-target, metadata, re-extraction, vector, relation, and reverse-index inventories use deterministic `C`-collated keyset pages; user-document repair/build phases exclude hidden `memory`/`knowhow` projection sources.
- `batch_ingest kg --retry-partial` is the explicit repair path for sources whose latest KG run reports `windows_failed>0` while graph objects already exist. Default incremental runs keep skipping completed graph-bearing sources. A partial retry must retain the current source graph and extraction history while model windows run; another partial/model failure or an empty replacement is counted as an incomplete batch attempt and leaves that graph readable, while only a non-empty zero-failed-window result replaces the source objects/relations in one database transaction. `--limit` may bound this repair set, and final rebuild/index behavior stays unchanged.
- The content-addressed LLM response cache (`chat_json`, its own SQLite file, default on) is **opt-in**: a call reads and writes the cache only when the caller passes a `response_validator`; validator-less callers (Ask, paper-metadata, summaries, schema induction, query rewrite) run uncached — correctness is preserved, only the perf win is forgone. Opt-in closes the poisoning class where a degenerate `[]`/error reply was frozen for the whole TTL and replayed on retry/reparse. KG extraction (`extract_window`/gleaning/refine) passes shape validators and stays cached (the dominant-cost path). The key is model + `base_url` + exact request content + effective generation params, never the api_key; health/availability probes pass `bypass_cache`. The admin evict endpoint takes `tag` XOR `clear_all`: supplying both is rejected (400), never silently treated as clear-all. UI upload dedup is same-notebook-only by content hash (mirroring `batch_ingest`); re-uploading the same bytes under a different suffix reuses the existing source and keeps its original parse (to change parsers, delete the source and re-upload).
- Ask must stay off heavy maintenance work: no synchronous whole-notebook embedding backfill, no synchronous unified-KG rebuild, and no full source-element scan for citation validation.
- `follow_chain` must remain a bounded, production-compatible query-time primitive: add no startup migration, new index, or historical backfill; reuse the existing `(notebook_id, source_object_id)` / `(notebook_id, target_object_id)` indexes, and hard-limit the raw rows read per endpoint before filtering. Two frontier rounds have per-node fan-out/result caps, no whole-graph load, and no writes. A truncated endpoint whose direct-edge absence cannot be proven must suppress that inference. It also fails closed on a start id outside the current candidates, non-whitelisted/mixed relations, missing relation quote, rejected/unknown-review edge, unusable node, cycle, direct-edge duplicate, `chain_trust < 0.5`, or incompatible `validity_scope`; trust is weakest-hop × tier/review/primary-evidence × hop penalty and stays separate from candidate query relevance. Relation anchors preserve stored `source→target` direction. New relation evidence should bind to `SourceElement` when possible, while legacy quote-only rows degrade to source-level display and all older KG data remains usable by existing retrieval paths.
- `app/services/collection_catalog.py` (the map) and `app/services/collection_enumeration.py` (the executor) back reasoning Ask's `enumerate_elements`/`enumerate_kg_objects` reflect tools, gated together by a single `reasoning_retrieval.enumeration_wiring_active()` predicate (`REASONING_ENUM_TOOLS_ENABLED`, default true) that also controls whether the collection map is injected, whether the actions are advertised, and whether the no-knowledge-graph early return may be waived — those five surfaces (map injection, reflect prompt wording, schema branch, allowed-action membership, early-return waiver) must move together or the model sees a tool it cannot call, or a run is admitted with no tools in it. The map counts are bounded, index-assisted, and zero-LLM; the executor is a stable cursor walk over the exact same source set the map counted, never a wider relevance Top-N. Five new bounded repository ports back this: `SourceStorePort.source_change_signal_rows` (one opaque per-source change-signal token per notebook), `SourceStorePort.element_type_count_rows` (batched `GROUP BY source_id, element_type` restricted to the enumerable whitelist), `SourceStorePort.element_page_rows` (one keyset page of one source's elements of one type), `SourceStorePort.source_display_rows` (bounded source title/paper-title lookup), and `KnowledgeStorePort.knowledge_object_page_rows` (one RAW keyset page of one notebook's knowledge objects of one type, carrying `status` but applying no predicate — the ordered index does not contain `status`, so a predicate in that query would turn one page into an unbounded residual filter on a notebook with a long governance history). The executor applies the map's own `USABLE_STATUSES` object to the rows it read, over-scans within `max_rows × 4` raw rows per action, and reports an honest `truncated_reason="budget"` partial with a resumable cursor when that ceiling fires; the cursor skips past the unusable stretch it already read so a resumed chain always advances. The predicate therefore still has exactly one definition — only the layer that evaluates it moved. All three enumeration budgets (`enum_rows_per_run`, `enum_pages_per_run`, `structured_payload_chars`) are pooled per REQUEST, not per action: each action is granted only the remainder, so several enumerations in one run cannot exceed the documented request-wide payload ceiling. The closing stability check re-resolves the participant set through `participant_ids` (the same `resolve_participants` / `mount_sql.py` entry the opening call used) and compares the SET before recomputing the fingerprint/seq vector over the freshly resolved ids: a library mounted or unmounted mid-walk is invisible to a digest recomputed over the opening id list (an empty new base contributes no signal, and an unmounted base's signals are still there), and such a walk must report `concurrent_change`, never "all". Narrowing an element enumeration to one document is expressed by `enumerate.source_title` (internal source ids are never shown to the model) and resolved server-side against the map's own plan by exact trimmed/case-folded match, bounded; zero or multiple matches skip the action rather than widening it, and a plan longer than the resolver's cap is declined outright rather than resolved from its prefix — uniqueness is a property of the whole scope. `replace_elements` advances the source's `updated_at` in its own write transaction on BOTH backends, so the change signal flips atomically with the element generation and a just-parsed source is countable and listable immediately — the first-parse under-count window this feature previously disclosed is eliminated, not documented. (`sources.updated_at` is read in exactly one place, that signal query; nothing orders, displays or keys on it.) An explicitly named `source_id` is still queried directly rather than inferred from the plan. Page round trips per action are bounded and the bound is ENFORCED (`_Walk.bound_queries`, breach raises `EnumerationInvariantError` and fails open as one skipped action): `max_rows + max_pages` for elements — zero-count sources never enter the plan, and a planned source yields rows — and `participants + max_pages + the raw over-scan ceiling` for KG objects, which has no per-partition count to skip on and pays top-up reads for the status filter. Each partition's first page stays free of the page allowance deliberately; charging it would again make a wide-and-thin corpus unenumerable. Because these tools need no graph, reasoning Ask's "this notebook has no knowledge graph" early return now only fires when the scope ALSO holds no enumerable collection; the `kg_required` flag keeps its meaning either way.
- Streaming Ask (`/ask/stream`) must remain progress-first: emit an immediate `started` event with the detached `job_id` and durable `conversation_id`, stream each agent trace step as it is recorded, then emit one final `AskResponse`. The ids let the frontend publish and reopen an in-flight first-turn session before any answer exists. A transport disconnect only stops delivery to that client; the worker continues and may persist its answer. Only the explicit interrupt path calls `POST /notebooks/{id}/ask/jobs/{job_id}/cancel`, sets the cancellation event, and stops the worker before saving a cancelled response. If interrupt is clicked before `started` is readable, the client must keep reading through `started`, cancel by the returned job id, and only then abort the transport; aborting first strands the detached worker. The normal `/ask` endpoint remains the non-streaming compatibility path.
- Unified-KG rebuild is explicit/observable. Opening the Knowledge Graph overlay fetches the current graph + `/unified-kg/status` and offers refresh when dirty; it must not block on rebuild.
- Cross-document concept-merge candidates must be bounded and reviewable. LLM merge review operates on small pending candidate batches, never the entire concept set at once.
- Re-running parse/extraction preserves the source row and original file, replaces source elements/chunks and their embeddings, and normally removes extraction runs plus source-derived knowledge before writing rebuilt state. The explicit batch `kg --retry-partial` path is the exception: it retains the prior source graph/history until a complete replacement is ready, then swaps graph rows transactionally.
- Deleting a source uses the same source-derived cleanup, then deletes the source row (cascading source-owned records) and local file. Do not claim unrelated artifact cleanup that the repository does not perform.

`object_type` display names have one source of truth: the backend `OBJECT_TYPE_LABELS` in `app/services/extraction_profiles.py`, shipped to the client as `KnowledgeTypeCount.label`. Any call site that can reach that API label (the Knowledge browser) must use it, so user-defined object types render their proper Chinese name too. Call sites that only hold an `object_type` string (citation popover, knowledge-graph canvas and side panel) use the built-in front-end table `KG_TYPE_LABELS` in `frontend/app/kg-type-model.ts`; `kg-type-mark.tsx` consumes and re-exports the model for shared rendering. The table stays character-for-character identical to the backend constant; `scripts/check_object_type_labels_contract.py` is a hard gate in `scripts/check.sh` and fails the build on drift, so a label change on either side must land on both. Do not reintroduce a Title-Case fallback — unknown or custom types are displayed verbatim as their `object_type`. Both tables, and any other map keyed by `object_type`, must be read with `Object.hasOwn(...)` rather than bare indexing or `map[type] ?? fallback`: `constructor` and `__proto__` resolve through the prototype chain to inherited functions/objects, which are truthy, so `??` never takes over and downstream reads silently become `undefined` (this produced `NaN` node coordinates in the graph layout).

Errors shown to a user are always Chinese, and the translation happens only in the frontend — `frontend/app/errors.ts` is the single source. Backend `detail` strings stay as they are and are never rewritten to please the UI: they are the contract for MCP agents, logs, and triage. The layer is **deny by default, and trust comes from provenance rather than from the shape of the text**. This is the one rule to keep straight, because the obvious alternative is wrong: a backend `detail` that happens to be Chinese, short, and single-line is *not* evidence that it was written for a user. Roughly forty call sites raise `HTTPException(detail=str(exc))`, and their output is structurally indistinguishable from the twenty that carry deliberate user copy — an earlier version of this module trusted "4xx and contains a CJK character" and consequently displayed `403 访问被拒绝 — nginx/1.25 request id=req-1 upstream=10.0.0.7:8000`, internal address included.

So the backend declares provenance explicitly. `user_error(status, message)` in `backend/app/api/deps.py` raises an `HTTPException` carrying the header `X-User-Message: 1`, and only a response bearing that header may have its `detail` shown verbatim. The marker is a **header** precisely so that `detail`'s JSON type stays untouched for MCP and logs. Anything raised as a bare `HTTPException` — every `detail=str(exc)`, every f-string wrapping an exception — is generalized to a status-code message on the client, with the original text going only to `console.error`. Two consequences are easy to get wrong: the header must be listed in the CORS `expose_headers` in `app/main.py` or a cross-origin deployment silently loses every backend message (same-origin development, backend tests, and frontend tests with mock `Response` objects are all green while production is broken), and a new 4xx whose `detail` is a Chinese literal must use `user_error` — `backend/tests/test_user_error.py` AST-scans for that and fails the build otherwise.

Trust is checked before shape, and shape is still checked second. `humanizeHttpError(status, detail, trusted)` passes `detail` through only when `trusted` (read from the header by `readHttpError`) and `status < 500` and `isDisplayableUserText()` agrees the string looks like a sentence — not multi-line, not tag-bearing, not brace-bearing, at most 200 characters. That second gate no longer decides trust; it catches the case where `user_error` was applied to a string that had an exception spliced into it. `trusted` defaults to `false`, so forgetting the argument fails closed. 5xx is generalized regardless of the marker: `user_error` is for client-correctable 4xx, and a 5xx means the server broke. The **diagnostic** channel is unchanged — raw body, collapsed to one line and truncated once, to `console.error` only.

Everything that is caught rather than fetched goes through `toUserMessage(error, fallback)`, and that function **only recognizes a brand, never a shape**. `throwHumanizedHttpError` and `humanizedError(message)` stamp the errors this module has translated; `toUserMessage` returns a stamped message verbatim — preserving the 401/403/404/409 distinction instead of flattening every failure into one sentence — and replaces everything else with the caller's fallback, writing the discarded original to `console.error`. This matters because the largest failure class never reaches `throwHumanizedHttpError` at all: when `fetch` itself rejects there is no `Response` to read, and backend error strings frequently arrive as JSON fields rather than status codes — the ask stream's `error` event, a persisted `ask_job.error`, a report's `error`, a source's `error_message`, a readiness snapshot's `error`, `model_errors[].message`. The backend writes `f"{type(exc).__name__}: {exc}"` into all of those, which is for logs and MCP, not for a person, and a shape-based rule let the Chinese-looking ones (`RuntimeError: 模型调用失败 upstream timeout`) straight through. The brand is a `Symbol.for(...)` rather than a module-local `Symbol` or an `instanceof` class check, because Next.js bundles the same module into both the server and client graphs and the module-local forms would produce two non-equal identities and thus false negatives; forgery is not a concern, since the values being screened are strings and JSON carries no symbols. Values that must not be rendered but must still be traceable go to `logDiagnostic(tag, value)`, which shares the HTTP path's truncation limit — never call it (or `toUserMessage`) during render, or it repeats on every re-render; log at an I/O boundary or in a `useEffect` keyed on the value.

Do not hand-roll an error branch. `frontend/app/errors-guard.test.mjs` recursively scans `frontend/app` and enforces three shapes: no `new Error(...)` whose argument interpolates `.status`; — because that first rule cannot see `setStatusText(\`服务异常：${err.message}\`)` — **no reads of `.message` at all** outside `errors.ts` unless the semantic site is reviewed; and, because that second rule could not see the backend's *diagnostic* fields either, **no reads of `.error` or `.error_message`** unless reviewed (`console.error` is exempt, being the channel those strings belong in). Reviewed entries are keyed by module path + qualified scope + access kind + target and carry a reasoned count; source positions and snippets are diagnostics only. Entries are limited to cases where the value is not raw exception text or is not displayed: a sentinel comparison, a condition, a state field already written by `toUserMessage`, or a value taken solely to hand to `logDiagnostic`. The guard also pins positively that `reportError`, the ask stream's `error` event, `job.error`, and `extractErrorMessage` (a thin alias of `toUserMessage` shared by ~20 knowhow call sites) still route through the layer.

**Anomaly severity tiers.** Small anomaly indicators attached to a source (parse failure, extraction gaps, missing paper metadata) are classified by *consequence*, not cause, into three severities: `integrity` (stored knowledge may be wrong or silently incomplete and usually cannot self-heal — red pill, `AlertOctagon`), `retrieval` (knowledge is intact but retrieval is degraded — usually one action fixes it — amber pill, `AlertTriangle`), and `info` (in-progress or expected state, not an anomaly at all — neutral grey, red/amber forbidden). `frontend/app/anomaly-severity.ts` (`sourceAnomalies()`) is the single classification entry point and `frontend/app/anomaly-badge.tsx` (`AnomalyBadge`) is the single render path, styled by the `.anomaly-badge--*` classes in `globals.css` off the `--danger`/`--danger-bg`/`--danger-border`, `--warning`/`--warning-bg`/`--warning-border` tokens plus `--warning-solid`. `--warning` is text-only (deliberately darkened to clear AA contrast on `--warning-bg`); `--warning-solid` keeps the original brighter amber for solid fills that predate this tiering (progress-bar segments, legend dots) — new anomaly copy never introduces a fourth amber. The answer-level "unbuilt retrieval index" banner is the same `retrieval` tier by consequence but is *not* source-attached: it does not flow through `sourceAnomalies`/`AnomalyBadge`, rendering instead as a dedicated `.answer-index-degraded` element that merely shares the retrieval-tier tokens. Any new anomaly small-print must add a mapping in `anomaly-severity.ts` and render through `AnomalyBadge`; a hand-rolled inline `style={{color: ...}}`, a bare `⚠`/`⛔` glyph, or a fresh ad-hoc color token is exactly the pre-tiering form this replaced and must not reappear — `frontend/app/anomaly-guard.test.mjs` is the regression gate, scoped to the tokens/patterns unique to the removed forms (it deliberately leaves the unrelated, still-legitimate `var(--color-warn, ...)` fallback used by the analytics modal and the retrieval-index status hint untouched). Compact rows (the source list) surface only the actionable tiers — `sourceAnomalies(source).filter(a => a.severity !== "info")` — so `info` (e.g. "待补全", "非论文") shows only in the source detail view, keeping narrow-screen rows from overflowing with badges that need no action.

**长任务按钮的忙碌态.** 凡是点一下就会触发长任务的按钮——排后台 job(体检修复的补齐向量/重新解析、KG 构建、检索索引构建)、同步等完的重活(来源重新解析、补上关联、查重)、或大体积传输(上传文件)——点完必须**立刻**变成不可点,并把文案换成**按该动作语义**写的进行态(「补齐向量」→「补齐中…」、「重新解析」→「解析中…」、「重建索引」→「重建中…」),不用笼统的「处理中」。纯图标按钮没有文案可换,改用 `.busy-spin` 转圈图标并同步更新 `title`/`aria-label`。这不是锦上添花:`backfill-vectors`、`reparse` 这些端点后端**没有单飞守卫**,POST 立即返回而修复在后台跑,按钮不变化用户就会反复点,每点一次后端就再排一份同样的活。两种形态都合法——① `disabled={busy}` + 文案切换;② 忙碌时整排 CTA 换成「取消」或干脆不渲染(「索引与构建」正常态用的就是这种)——但**必须二选一**,不能什么都不做。忙碌位的解除要**按证据**而非按时间,且证据要按**修复的形状**选,不能一刀切(唯一真源是 `frontend/app/checkup-view.ts` 的 `repairRelease` / `isRepairing`,纯函数、`checkup-view.test.mjs` 有单测):一轮只修一批的(`reparse` 的样本上界 ≤20 篇)存「触发那一刻该组的 count」,count 一变就恢复可点,让用户接着修下一批;一次修全库的(`backfill_vectors`)**不能**用 count —— 看板 H4/H5 的口径排除活跃租约,job 逐源补齐时 count 就一路递减,拿它解锁会在 job 还剩大半时放行、又排一次全库补齐,正是 `backend/app/services/checkup.py` 里 H4/H5 注释点名要防的「并发 backfill 重复模型调用」;它只在该组从体检结果里消失时解除。忙碌位还必须随体检结果收敛(摘掉已不在结果里的分组键),否则旧条目会被后来重新出现的同名问题继承、把新卡片锁死。有界轮询窗口关闭与切库是共用兜底,绝不让按钮卡在禁用态。已知取舍(刻意保留、有反向护栏用例钉住):backfill 全失败时 H4/H5 不归零,按钮会锁到窗口结束(≤10 分钟)——因为 backfill 没有持久 job 状态,而提前放行的代价(重复付费模型调用)高于等待。`disabled` 写了还不够:`.sort-button` / `.icon-button` / `.ghost-button` 都显式写死了 background/color,浏览器默认的 `:disabled` 变灰对它们无效,`globals.css` 里那条共用 `:disabled { opacity: .55 }` 是让禁用**看得见**的必要条件。`frontend/app/long-task-button-guard.test.mjs` 是回归门:它按 `onClick` 绑定的源码文本(不是行号)认出各长任务入口,断言每个都带非平凡的 `disabled`(`disabled={false}` 这类恒假值同样报红),并断言 `CHECKUP_FIX` 与 `CHECKUP_FIX_BUSY` 两张表逐键配对、进行态文案与静态文案逐条不同。守卫刻意不覆盖走形态②的那几颗(正常态的 `runScaleIndexOp("rebuild")`、看板里的 `startKgBuild`/`startKgRebuild`),也不覆盖**新增**的长任务入口——后者的兜底是本节约定与人工评审,不是这份测试。

## LLM Configuration

Chat, embedding, and rerank services are deployment-owned. `MODEL_SERVICES_CONFIG` points to a TOML file whose `[services]` entries declare protocol, endpoint, model, `api_key_env`, and the physical service's sole capacity setting `max_concurrency`; `[bindings]` maps every stable workload id from `model_registry.py` to a compatible service. Secrets live only in `.env` variables referenced by `api_key_env`. Do not restore role-specific endpoint/model/key variables or any user-owned model setting.

`RuntimeModelProvider` is the process-owned access boundary. Business code requests a stable workload adapter from it; the provider resolves workload → physical service, submits through that service's one `ServiceScheduler`, then and only then invokes the reviewed raw transport. No application service, repository, batch phase, probe, or compatibility property may construct or expose a raw chat/embed/rerank client, call a provider transport directly, or introduce a second semaphore/executor as a nominal global cap.

Per physical service, `ServiceScheduler` enforces `max_concurrency`, a total queue cap of `10 × max_concurrency`, a per-actor queued cap of `2 × max_concurrency`, fixed priority dispatch `interactive:report:background = 8:2:1`, and round-robin actors inside each priority lane. Queue deadlines are 30 seconds for interactive work, 300 seconds for report work, and 1800 seconds for background work. One fatal provider result or three consecutive transient results open the service breaker for 30 seconds; half-open admits exactly one probe. Separate service ids have separate capacity, queues, and breakers.

The supported production topology is one backend process (`uvicorn --workers 1`). All model services remain URL-based; the backend neither loads nor starts inference models. MinerU is a separate parser adapter and retains its supported remote `http`, isolated `cli`, and pypdf `off` modes. An empty `MODEL_SERVICES_CONFIG` intentionally enables deterministic/offline fallbacks; a non-empty invalid configuration fails startup.

`EMBED_DIM` must match the bound embedding model. Timeouts, retries, output budgets, embedding batch size, KG source-job concurrency, adaptive window sizing, and local ANN/CPU thread counts are workload/compute tuning only; none may override `max_concurrency`.

Legacy deployment migration is owned by `scripts/migrate_legacy_model_env.py`, and release packaging must include and execute-test it with the bundled `.venv/bin/python`. It must remain dry-run by default. `--apply` must back up the input and any replaced output, atomically write a credential-free TOML, rewrite only managed model assignments, preserve unrelated `.env` content, and never print secrets. It may replace an existing output without `--force` only when that file is byte-identical to the checked-in example. Keep its role fallbacks and physical-service deduplication aligned with the retired configuration behavior, including every former rewrite-client workload, derive bindings from the registry's stable workload ids, and validate generated output through `SystemModelServiceRegistry`. Capacity inference is only a migration starting point and may be explicitly overridden per legacy role; runtime must still have exactly one `max_concurrency` on each physical TOML service. Native DashScope rerank remains a supported migration target for old `RERANK_API_STYLE=dashscope` deployments.

### Model Service Status and Diagnostics

- `GET /api/model-services/status` is read-only and must never probe upstream services. It returns sanitized system service identity, workload bindings, configured capacity, running/queued counts, breaker state, and last-known health. It must never expose endpoints, credentials, provider payloads, source/prompt/response text, IPs, or raw exceptions.
- The Model Services UI is configuration-free. Ordinary users can inspect status only. Admins may explicitly probe one configured service with `POST /api/admin/model-services/{service_id}/test` or all configured services with `POST /api/admin/model-services/test-all`; status reads and page loads never auto-probe.
- Every scheduled model call receives a safe `support_id`. Client-visible model failures identify a sanitized service/model label plus that id; users give the id to maintenance staff, who correlate it with server logs and service status. Logs may retain operational provider diagnostics but must never log credentials or full private prompt/response bodies through scheduler/status events.
- Health observations are deployment-service-scoped and written monotonically by occurrence time. Manual probe and observed runtime outcomes share the same service identity/fingerprint guard, so stale completions cannot overwrite a replacement configuration; on an exact occurrence tie, observed failure wins over manual success.
- Schema v24 irreversibly rewrites every stored `user_profiles.model_settings` value to `{}`, deletes legacy per-user model health rows, and stores current health by deployment service id. Personal model-settings APIs, draft tests, save/edit controls, and configuration pages are retired and must not reappear.

## Logging / Observability

Structured logs go to `.local/logs/*.jsonl` (gitignored) plus brief console lines, via a single `EventLogger` (`backend/app/core/event_logging.py`). Add observability at the existing chokepoints, not at each call site:

- `requests.jsonl` — HTTP middleware in `app/main.py` (method/path/status/latency/`request_id`; slow calls flagged via `SLOW_REQUEST_MS`; `X-Request-Id` response header).
- `events.jsonl` — source pipeline in `SQLiteRepository.process_source` / `_set_source_status` (per-stage timings + status transitions + failure stack).
- `llm.jsonl` — `LLMInteractionLogger` wrapping `OpenAICompatibleClient` (`app/core/llm.py`); chat detailed, embeddings summarized, errors recorded.

Rules: reuse `EventLogger` for any new structured log (it handles JSONL append + console + never raising); never log raw embedding vectors; chat prompt/response are truncated to `LLM_LOG_MAX_CHARS`. The browser/API debug log viewer (`/dev/logs`, `/api/debug/logs/...`) is opt-in because full LLM records may contain prompt/response text from private sources; enable only with `DEBUG_LOGS_ENABLED=true`. Config env vars: `LLM_LOG_ENABLED`, `LLM_LOG_PATH`, `LLM_LOG_MAX_CHARS`, `EVENT_LOG_ENABLED`, `EVENT_LOG_DIR`, `SLOW_REQUEST_MS`, `DEBUG_LOGS_ENABLED` — keep `.env.example` aligned.

Production DFX is a binding internal-infrastructure contract. The supported production shape is Ubuntu 24.04 started from the repository with `npm run start` and one Uvicorn worker. Production start installs `backend/requirements.txt` into `PYTHON_BIN`'s environment and recreates frontend dependencies from `package-lock.json` with `npm ci` before building; only explicitly prebuilt deployments may use `SKIP_INSTALL=1`. It rejects occupied ports from listener rows even when their PIDs are hidden, then launches terminal-independent background frontend/backend processes and exits only after curl verifies backend `ready=true` plus frontend access twice while both launched PIDs remain alive. Pre-success failure/timeout/interruption sends SIGTERM to both direct children together, waits one bounded grace window, SIGKILLs survivors, and reaps both before returning; `npm run stop` owns normal shutdown. Operators run `python3 scripts/diag.py incident` **during** a visible hang, retrying with `--pid <backend-pid>` only when automatic discovery cannot select the already-running worker. The unified dispatcher has exactly seven commands: `incident`, `slow`, `latency`, `locks`, `open`, `db`, and `base-recall`; bare invocation remains `slow`. Existing standalone engine scripts and their old operator/cron paths must keep working, but do not reintroduce retired commands.

The default `incident` result must remain one copyable UTF-8 block no larger than 32 KiB, use one deadline capped at 10 seconds, and rank no more than three evidence-backed hypotheses while preserving explicit missing/degraded evidence instead of inventing a cause. The runtime atomically refreshes `.local/diagnostics/runtime.json` every two seconds; a heartbeat older than six seconds is stale. `SIGUSR1` is a non-terminating all-Python-thread faulthandler dump with no local-variable capture. `.local/diagnostics/thread-dumps.log` retention remains bounded to 8 MiB after successful capture, and temporary DB snapshots remain bounded beneath `.local/diagnostics/db-snapshots/`.

The runtime diagnostics directory must be owner-controlled mode `0700`; `runtime.json` and `thread-dumps.log` must be owner-owned, single-link regular files with mode `0600`. Open and replacement operations stay descriptor-relative to a validated pinned directory. Any unsafe existing artifact or directory-path replacement must fail closed and increment diagnostics degradation without following links, blocking on special files, or truncating an attacker-selected target.

Runtime snapshots and copyable reports are metadata-only. Never capture, persist, or print request bodies, user-controlled raw filenames, source text, Ask questions/answers, prompts/model messages, Memory/Knowhow content, or authorization headers, cookies, tokens, credentials, secrets, raw process command lines, or local variables; never persist or print SQL text or SQL parameters. Exact opaque notebook identifiers may exist only in the machine-local runtime snapshot for read-only correlation; reports pseudonymize notebook/request/job identifiers consistently and omit every other raw opaque id. Even sanitized output must be reviewed before sharing outside the trusted team.

## Feature Completion (Finish With a PR)

Every completed feature ends with a pull request — do not merge straight to `master`, and do not hand the wind-down back to the user.

Standard wind-down, once the feature branch (usually a worktree) is done, the full test suite is green, and final review passes:

1. 3-way merge the latest `master` into the feature branch (so the PR diff shows only the feature, not a spurious revert of newer `master` commits); resolve conflicts; re-run the suite green.
2. `git push -u origin <branch>`.
3. `gh pr create --base master --head <branch>` with a body covering background / approach / measured results / testing (end with the Generated-with-Claude-Code line).
4. Report the PR link to the user.

Never squash- or force-overwrite `master`'s newer commits — use a real merge, or rebase first.

A pull request must be reviewed by codex before it is merged, and every round's **raw** review output is posted verbatim to the PR — including rounds that raise nothing, and rounds run by hand. Post the trigger (automatic or manual), the exact command, the head SHA, and the exit code with output size alongside it, so the reviewer can confirm the run happened and was not paraphrased away. A round counts as successful only when the exit code is zero **and** the output is non-empty; a review killed by SIGTERM also exits zero, and trusting the exit code alone posts an empty comment that reads as a pass. P0/P1 findings block and stop for a human decision; P2/P3 do not block and may be declined with a stated reason; output whose priority tags cannot be parsed blocks conservatively rather than defaulting to a pass. A finding may be rejected on the merits — codex reviews the diff and does not always know the harness's runtime facts — but a rejection must carry its reasoning and evidence on the PR, a comment recording the trade-off in the code, and a regression test pinning the behavior that was kept. Merging always requires explicit human approval.

Review automation itself is a per-developer Claude Code hook rather than a repository artifact, so it is not in this tree and a fresh clone will not have it. The rule stands regardless: without the hook, run the review by hand. `CLAUDE.md` documents the mechanics — trigger points, the manual command, and the escape hatches.
